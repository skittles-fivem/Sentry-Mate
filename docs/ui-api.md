# Sentry Mate API: what the pages need

This is the `/api/v1` the pages in [`parity/ui-parity.md`](parity/ui-parity.md) need. It merges the needs of every page into one set of resources, without duplicates. Each resource names the pages that use it.

## Conventions (every endpoint)

- **Ids are strings.** Car, drive, charge, state, update, place, visit, token, key and import ids are all strings. Drive and charge ids pass 2^53, so a JSON number would lose digits.
- **Units are metric, named in the field.** `_m`, `_km`, `_kph`, `_kw`, `_kwh`, `_wh_per_km`, `_c` (degrees Celsius), `_kpa` (tyre pressure; stored bar x 100), `_v`, `_a`, `_pct`, `_ms` (durations and times). The API never converts. The UI applies the person's unit preferences.
- **Times** are milliseconds since the epoch, UTC (`*_ms`). Every car-scoped response also carries the car's `time_zone`, and anything grouped by day, week, month or year is grouped in that zone (ISO weeks). A car's zone is the one an admin set for it; when none is set, the zone its newest position is in (looked up offline in the time zone boundaries built into the server: the position goes nowhere), else the server's `default_time_zone`. `/cars` items say which (`time_zone_source`).
- **Lists are paged by cursor.** `limit` (default 50, max 500) and `after` (an opaque string from the previous page's `next`). A list response is `{ items: [...], next: string | null }`. Optional `total` only where it is cheap.
- **Period filter** on every time-based resource: `from_ms` and `to_ms`. A row belongs to the period by its start time unless the resource says otherwise. Rows that cross an edge are clipped where noted, never dropped.
- **Several cars:** report resources accept `cars=all` or `cars=1,7` where the page offers it; each row then has `car`.
- **Access:** every car-scoped route checks the account's car list. An unknown car and a car the account may not see give the same answer: `404 { error: { code: "no_such_car" } }`.
- **Errors** use one shape: `{ error: { code, message, fields? } }`. `400` bad input (with `fields`), `401` not signed in, `403` not allowed (role), `404` unknown or hidden, `409` conflict (stale `version`), `422` invalid value, `429` with `Retry-After`.
- **Changes** need the CSRF header, are recorded in the audit log, and admin-only changes say so below. An entry names what was changed: a CAN Bridge key move is `key-assigned` (the car it went to) and `key-unassigned` (the car it left), with `target` `key:<car>:<key>`; `key-preferred`; `can-key-renamed`; `token-created` and `token-revoked` with `target` `token:<car>:<id>` (`token:<id>` for a new car's token). Every admin route writes a code of its own with a summary in words (never a method and a route); see [Audit log](#audit-log) for the codes, their groups and item kinds. The plain `change` code is left only on old stored entries, and those read back mapped. `POST /places/preview` changes nothing and writes no entry, and the same `/me/preferences` change by one account within 10 minutes is one entry.
- **Sources:** every row says where it came from. `sources` is a list (never empty on a row) of `{ kind: "smo" | "tesla_api" | "teslafi_api" | "teslamate_local" | "import", site?, label }`: `smo` is SMO (the Screenmate CAN Bridge's signed logs), `tesla_api` the Tesla Owner API this server reads, `teslafi_api` TeslaFi's polls this server reads, `teslamate_local` the owner's local TeslaMate (its MQTT topics), `import` history brought in from another site (`site: "teslamate"` or `"teslafi"`). `label` is a short line a page can show ("Data from SMO", "Data from the Tesla API", "Data from TeslaFi", "Data from local TeslaMate", "Imported from TeslaMate", "Imported from TeslaFi"). A row that several inputs saw lists them all (always SMO first in the list; which input's values win where they cover the same time is the car's `source_order`, by default SMO > Tesla API > TeslaFi > local TeslaMate, imports after every live input), and `source_label` says it in one line ("Data from SMO and the Tesla API"). Live values carry `sources` too (one entry), and so do `/cars` items (what the car has data from), `config` values (empty when an admin typed the value), `/series` and other column answers (what gave the points), `/storage` days and `/overlaps`. Estimated values carry a `basis` (for example `energy_basis: "measured" | "estimated"`). A drive or charge with Tesla API data alone has `energy_basis: "estimated"` (the API's power read every few seconds to a minute, summed).
- **Values filled from an import:** where the live inputs (SMO, the Tesla API, TeslaFi's API, local TeslaMate) all have nothing for a value at a time, the import shown for that span (TeslaMate's or TeslaFi's, as [Overlaps](#conventions) chooses) fills it, with `source=all` only and while the car's `import_gap_fill` (else the server's `import_gap_fill.enabled`, on by default) says so. A filled row is still its own source's row (its `source` word is kept); its `sources` add the import ("Data from SMO; imported from TeslaMate") and `value_sources: { field: [source] }` names each filled field (an empty object when the row has only its own values). Drives fill `start` (never `end`: a live drive without one is one whose data stopped, and keeps its "Data stopped here"), `start_odometer_km`, `end_odometer_km`, `start_soc_pct`, `end_soc_pct`, `start_range_km`, `end_range_km`, `outside_avg_c`, `cabin_avg_c`, `climb_m` and `descent_m`; charges `position` (and `odometer_km`), `start_soc_pct`, `end_soc_pct`, `start_range_km`, `end_range_km`, `outside_avg_c` and `battery_avg_c`. Distance, energy, costs and `energy_basis` are never filled, so totals and consumption stay the live row's own. The Logbook, the Timeline's drive rows (`sources`, `source_label` and `value_sources` as on Drives) and Trip use the same filled drives; Trip names what it took from an import in `value_sources` (`odometer_km`, `markers` for the start marker's position). Columns (`/series`) carry `value_sources: { field: [source] }`: every input or import that gave that column a value. `/now` is the car's newest values and is never filled (an import is history).
- **Old `source` word (deprecated, kept for one release):** rows still carry `source`: `can` when SMO is among `sources`, `teslamate` for an imported row, `tesla_api` for a row from the Tesla API alone (a new word). `/overlaps` keeps `shown: "can" | "teslamate"` and the `can` and `teslamate` counts beside the new fields. The packs read these today; they should move to `sources`, `shown_source`, `live` and `imported`. A later release drops them.
- **`source=` filter** on lists, series and totals: `smo`, `tesla_api`, `teslafi_api`, `teslamate_local`, `import` (any site), `import:teslamate`, `import:teslafi`, or `all` (the default). The one-word `source` of an imported row is its site (`teslamate`, `teslafi`). The old words still work: `can` is `smo`, `teslamate` is `import:teslamate`. A row matches `smo`, `tesla_api`, `teslafi_api` or `teslamate_local` when that input is among its `sources`.
- **Null means unknown.** A missing value is `null`, never `0`. Live values carry their own `at_ms`.
- **CSV:** every list resource also answers `Accept: text/csv` or `?format=csv` with the same filters.

| `/api/v1/audit` | GET (admin) | `{ items: [{ at_ms, account, action, group, target, car, summary, address }], next }`, newest first. `group` is the code's group (`"other"` for a code the server does not know), `car` the car the `target` item belongs to (or null), `address` where the request came from (null for the server's own entries). See [Audit log](#audit-log) for the parameters, the codes and the item kinds. | Settings: Server and access |

- **Passwords.** `POST /setup`, `POST /setup/fresh`, `POST /accounts` and `PUT /me/password` refuse only an empty password and one over 1,024 bytes (`422 invalid` on the field); any other is taken, for the first admin as for everyone. `PATCH /accounts/{account}` refuses one over 1,024 bytes the same way, but takes an empty `password` as "keep the current one" (`200`, the password and the account's sign-ins unchanged). Pages warn before they send one that `passwordAdvice()` (`ui/shared/password.js`, the same reasons as the server's `password_advice`) has reasons for (shorter than 12 characters, close to the account name, one of the most common, repeating itself) and let the person use it anyway. Argon2id, the sign-in throttles, HTTPS only and two-step sign-in are what keep a weak one out of reach.
- **Asking again before a change.** Account changes (`POST`/`PATCH`/`DELETE /accounts[/{account}]`, `DELETE /accounts/{account}/two-step`, `PUT /two-step-policy`) take the acting admin's own password (`confirm_password`, or the `X-Sentry-Mate-Password` header: its bytes are read as UTF-8, and HTTP drops spaces at its ends; or `X-Sentry-Mate-Password-Encoded`, the password percent-encoded as `encodeURIComponent` writes it, which carries any password and is what a browser has to send when the body is not JSON, since `fetch` cannot put every character in a header. A header that is not UTF-8, or not percent-encoded UTF-8, is `400` on `confirm_password`. Pages send `confirm_password` in the body wherever the body is JSON, on `DELETE` too); `PUT /me/password`, `DELETE /me/two-step` and `POST /me/two-step/recovery-codes` take one's own `password`. When the acting account has two-step sign-in on, each also needs `code` (from the authenticator app, or a recovery code; or the `X-Sentry-Mate-Code` header), the same as exports and interfaces for everyone do: without it, or wrong, `401 wrong_code`. A code works once; one `PATCH` that changes several things takes one code. Missing and wrong codes count toward the code throttle.
- **Signing in from outside** while the two-step rule keeps an account without it at home: the right password gets the same `401 wrong_credentials` as a wrong one (and counts as a failed try), so the answer never confirms a guess. The audit log still records `sign-in-refused`.
- **A password change signs everyone else out**, sign-ins still running at that moment included: a sign-in whose password was checked before the change gets `401 wrong_credentials` (or `sign_in_expired` at the code step) instead of a session.
- **Right passwords are limited too:** at most 20 sign-ins with a right password per account and minute (home and outside counted apart), then `429 throttled`; and one password check at a time per account, so no account (or loop of its own sign-ins) can keep the server's few password checks busy for the others.

## Integrations: TeslaFi

The TeslaFi input, for owners who pay for TeslaFi: this server reads TeslaFi's own polls of the car (about one a minute while it is awake; as fast as every 15 s with the `often` pace) from TeslaFi's API with the owner's TeslaFi token, as a third live input beside SMO and the Tesla API. It is off until an admin adds a token: before that the server makes no connection to TeslaFi at all. It only reads: the server can ask `feed.php` (TeslaFi's latest poll) and `feed.php?command=lastGood` (the last poll of the car awake) and nothing else, never a wake (`wake_up`, `wake`, a `wake=` parameter) or a command, and no answer ever returns the token. It connects only to `www.teslafi.com` on 443, the token in the `Authorization` header (never in a URL), redirects never followed, over TLS 1.3 (TLS 1.2 only if TeslaFi's host offers no 1.3: `tls` says which one was used). Data from TeslaFi is labelled `teslafi_api`, "Data from TeslaFi"; where SMO or the Tesla API cover the same time, theirs win, value by value (SMO, then the Tesla API, then TeslaFi). Everything here is admin only, reads included; every change writes an audit entry, and every change but the car matches asks for the admin's password again (and the two-step code); the car matches (`PUT .../accounts/{teslafi_account}/cars`) take the admin session alone, as they store and show no token.

Errors wait 60 s, doubling to 15 minutes; a 429 waits what TeslaFi asks (1 minute to 1 hour). A poll already handed on (the same `data_id`) is not handed on again. After a change of `time_zone` TeslaFi's times are read in the new zone at once, and no poll is dropped for seeming older than the last one read in the old zone. No pace slows while SMO or the Tesla API is live for the car. Whatever the pace: at most one request every 10 s per account, TeslaFi's `429` and `Retry-After` are always obeyed (at least 60 s, at most an hour), other errors back off from 60 s doubling to 15 min, and a poll already handed on (the same `data_id`) is not handed on twice. A new pace takes effect at once (the pollers start again, keeping the day's count and any wait).
- **Values:** TeslaFi's keys are the column names of its data download, so its answers are read with the TeslaFi import's rules: Tesla's units (miles, °C) unless the answer itself shows others, `Date` in the account's `time_zone`, `NULL` and empty strings as no value. A new VIN in TeslaFi's polls (another car on the TeslaFi account) is added as a car not matched yet; its polls never go to the car matched before.
- **Audit actions:** `teslafi-account-added`, `teslafi-account-changed`, `teslafi-account-paused`, `teslafi-account-resumed`, `teslafi-token-replaced`, `teslafi-car-matched`, `teslafi-account-removed`, and in the server's name `teslafi-token-refused`, `teslafi-account-error`. None holds the token.
- **`/network`** lists one `teslafi` row (`www.teslafi.com`, `enabled` while an account is read; off when there is none). **`/system/health`** has `teslafi: { accounts, cars, requests_today, last_error }`. `source=teslafi_api` filters rows and series to TeslaFi's data; `sources` name it `{ kind: "teslafi_api", label: "Data from TeslaFi" }`.

## Integrations: Supercharger invoices

Supercharger sessions with their costs and invoices (PDF), from Tesla's charging history for the Tesla accounts' cars, and the costs TeslaFi lists for its charges (no PDFs: TeslaFi's API gives none). Off until an admin turns it on for that input (PATCH `invoices` of `/integrations/tesla` or `/integrations/teslafi`, the password asked again): before that nothing is fetched. A session is matched to its car's DC charge (or one of no known kind at 25 kW or more) that it overlaps most in time, with 10 minutes of slack at each end, and within 400 m when the session says where it was (TeslaFi's may); the sessions of one charge add up (the car plugged in twice), except that one visit read by both inputs (a Tesla session and a TeslaFi one of the same charge at the same time) counts once: Tesla's, and TeslaFi's stays listed with the charge, `applied` false. The total becomes the charge's cost (`cost.source` `tesla_invoice` or `teslafi`, over a place price or free Supercharging) unless an admin entered one, which wins. Matching is worked out from the kept sessions whenever charges are read, never stored with a charge, so a rebuild matches again; a session with no charge is listed, not lost. The sessions and PDFs are kept sealed in the database, one per session id (`tesla-<id>`, `teslafi-<id>`). What is fetched, and how often: [security.md](security.md#supercharger-invoices). Everything here is admin only; the PDF of a matched session is also under its charge, for whoever sees the car.

## Integrations: Local TeslaMate

The local TeslaMate input, for owners who already run TeslaMate on their own network: this server subscribes to TeslaMate's MQTT topics (`<prefix>/cars/+/#`, QoS 0) as a fourth live input beside SMO, the Tesla API and TeslaFi, and can catch up from TeslaMate's PostgreSQL database now and then for what MQTT missed (off by default). It is off until an admin adds it: before that the server makes no connection to it at all. It only reads: on MQTT it subscribes and never publishes (no will, no retain), on the database it only runs `SELECT`s, and no answer ever returns a password. Data from it is labelled `teslamate_local`, "Data from local TeslaMate"; where SMO, the Tesla API or TeslaFi cover the same time, theirs win, value by value (SMO, then the Tesla API, then TeslaFi, then local TeslaMate, then imports). Rows the database catch-up brings in are stored as a TeslaMate import (`import:teslamate`, "Imported from TeslaMate"). Everything here is admin only, reads included. Adding, replacing, pausing or removing the settings asks for the admin's password again (`confirm_password`, or the `X-Sentry-Mate-Password` header, and `code` when the admin has two-step sign-in on); a test and the car matches take the admin session alone, as they store and show no password. Every change writes an audit entry.

- **Passwords:** write-only. In a PUT, `password` as a string sets it, `null` removes it, left out keeps it (`password_set` says one is saved). A kept password goes only to the host it was typed for: changing `host`, `port` or `tls` while a password is saved, without sending `password` again, is `422 password_resend` (field `mqtt.password` or `database.password`), for the database also while it is off (`enabled: false`).
- **Plain text rule:** a password (new or kept) over plain TCP (`tls: false`) needs `allow_unencrypted: true` ("Allow unencrypted (local network only)", off by default), else `422 plaintext_password` (field `mqtt.password` or `database.password`). Without a password, plain TCP is allowed (a broker on the local network with no sign-in). `pin_sha256` (the certificate's SHA-256, 64 hex digits, colons allowed) needs `tls`. `prefix`: no `+` or `#`, no leading `$`, no empty level. `host`: a host name or an IP address, no scheme or path. Other bad values are `422 invalid` with `fields` (`mqtt.host`, `database.interval_s`...).
- **MQTT:** TeslaMate's documented per-car topics (`display_name`, `state`, position, speed, power, odometer, battery level and ranges, charging values, temperatures, locks, doors and windows, `version`, tyre pressures) are mapped to the server's samples. VIN is not on MQTT in every TeslaMate version: with the database on, cars are matched by its VIN prefix; else by display name.
- **The forms:** the MQTT form starts with TLS off on port 1883. Ticking "Encrypt the connection (TLS)" sets the port to 8883 and unticking sets it back to 1883, only while the port still holds the other default (a port typed by hand stays). "Pinned certificate (SHA-256)" is shown only while TLS is ticked: its note reads "optional — only for a broker with its own self-signed certificate; leave empty otherwise" ("a database" on the database form). The hint under Host reads "TeslaMate's broker is usually on the TeslaMate machine, port 1883, no user or password. If Test can't connect, publish Mosquitto's port 1883 in TeslaMate's Docker settings." The shared words and the port rule are `TM_HOST_HINT`, `tmPinNote(part)` and `tmTlsPort(part, port, tls)` in `ui/shared/teslamate.js`.
- **Database catch-up** (`database.enabled`, off by default): every `interval_s` seconds (60 to 86,400) the server reads TeslaMate's drives, charges and positions since the last catch-up and stores them as a TeslaMate import. A user with read-only rights is enough.
- **MQTT values beside the samples:** TeslaMate's `charge_energy_added` and `est_battery_range_km` are kept as local TeslaMate's: `/cars/{car}/now` gives them as `charge.added_kwh` (while charging) and `car_est_range_km` when the Tesla API has no current reading of its own, with `sources` naming `teslamate_local`.
- **Notices** (`/notices`, admins only), each `level: "warning"`, `fix_link: "/settings/integrations#teslamate"`, `detail: { part: "mqtt" | "database", error }` (`error` the `last_error` code, null for a quiet broker): `teslamate_connection_refused` (the broker refused the connection, did not answer, or its TLS handshake failed), `teslamate_auth_failed` (it refused the user name or password, or the subscription), `teslamate_pin_mismatch` (its certificate does not have the pinned SHA-256), `teslamate_quiet` (connected, but nothing came for a day; a car asleep for days sends nothing either), `teslamate_catchup_failed` (the last database catch-up failed, whatever the cause). A notice goes as soon as its cause does (connected again, a message came, a catch-up worked, paused or removed); a `notice` event and an audit entry in the server's name go out once when a trouble begins, not on every try.
- **Audit actions:** `teslamate-local-added`, `teslamate-local-changed`, `teslamate-local-paused`, `teslamate-local-resumed`, `teslamate-local-car-matched`, `teslamate-local-removed`; written by the server: `teslamate-local-connection-refused`, `teslamate-local-auth-failed`, `teslamate-local-pin-mismatch`, `teslamate-local-quiet`, `teslamate-local-catchup-failed`. None holds a password.
- **`/network`** lists a `teslamate_mqtt` row ("Local TeslaMate (MQTT)") and a `teslamate_db` row ("Local TeslaMate (database)"), `host` the saved `host:port` (null while not set), `enabled` while that connection is used. **`/system/health`** has `teslamate_local: { enabled, mqtt_state, database_state, cars, last_message_ms, last_sync_ms }`. `source=teslamate_local` filters rows and series to its data; `sources` name it `{ kind: "teslamate_local", label: "Data from local TeslaMate" }`.

## Moving and first-run setup

Moving a server and setting up a new one need no shell: the old server makes a move code (or an export file) in Settings: Server and access, and the new server's first page takes it. It does what the `move` and `import` commands do (`docs/moving.md`; how each call maps to the `moving` crate is in `docs/plans/move-server.md`, "From the web UI"). The real server answers these over HTTPS only, like every other call: set-up codes, passwords, move codes and recovery keys never travel over plain HTTP.

The `/setup/*` calls need no sign-in: a fresh server has no account yet. Instead the browser first **claims** the server with the one-time set-up code the server prints in its log, and holds the claim in a cookie. Every other `/setup/*` call needs that claim (`401 not_claimed` without it). Once the server is set up they answer `409 setup_done` (except `GET /setup`, and `GET /setup/job` for the browser that still holds the claim, so the page can show the result; the claim lasts through the restart a restore's switch makes).

## Deliberately absent

- No endpoint wakes the car, pauses logging or sends a command: Sentry Mate is read-only to the car.
- No endpoint ever returns a Tesla token, wakes the car or sends it a command. The Tesla API input only reads.
- No raw SQL, database tuning or index statistics.
- No VIN serial anywhere: only the VIN prefix is stored.

## Decisions

Points this document left open, decided while building the dev server (`ui/devserver`). Pages can rely on them.

### Requests and answers

- **CSRF header:** every POST, PUT, PATCH and DELETE carries `X-Sentry-Mate: 1`. Without it: `403 { error: { code: "csrf" } }`. Sign-in and set-up need it too.
- **Session cookie:** `HttpOnly`, `SameSite=Strict`, `Path=/`, 30 days. The real server names it `__Host-sentry-mate` and adds `Secure`. The dev server names it `sentry-mate` without `Secure`, because it is plain HTTP on 127.0.0.1.
- **The server's clock:** every `/api/` answer carries `X-Sentry-Mate-Now-Ms`, the server's "now" in epoch ms. Pages count "5 min ago" and resolve the period presets from it (`api.now()`), so a server whose clock differs from the browser's (the dev server's virtual clock) still shows the right times.
- **The build:** every answer (the API, `/health` and the pack's files) carries `X-Sentry-Mate-Build`, a short hash of the UI packs the server serves; it changes with a new image. A tab open across an update sees it change (on any API answer, or `GET /health` when it comes back into view) and loads its next page in full instead of importing a module of the new build into the old page (`ui/shared/build.js`). The pack's files under an old `/_v/<version>/` are the current files of those paths (`no-cache`, never `404`), so that tab keeps working until then.
- **Compression and `304`:** JSON and CSV answers of 1 KB or more come in brotli or gzip when the request's `Accept-Encoding` allows it (`Vary: Accept-Encoding`); a stream (`/api/v1/events`) never. A successful `GET` with a JSON body carries a weak `ETag` (a hash of the body) and `Cache-Control: private, no-cache`; sending it back in `If-None-Match` gives `304` with no body when nothing changed (the browser does this by itself for `fetch`, unless it is told `cache: 'no-store'`). Answers that may carry a secret (tokens, keys, setup, `/me`, sessions, two-step, exports, the move) stay `Cache-Control: no-store`, untagged and uncompressed. Every other answer is `no-store`.
- **Car-scoped answers** carry `car` and `time_zone` at the top (the zone `/cars` names for the car, with its `time_zone_source`). In answers that mix cars, every row carries its own `car` and `time_zone`.
- **Ids:** cars are `c1`, `c2`, ...; places `p1`, ...; drive, charge and update ids are decimal strings above 2^53. Timeline rows use `<kind>:<start_ms>`.
- **Creating** answers `201` with the new object. **Deleting** answers `200` with a small JSON body (`{ deleted: true, id }`, or the changed object), never an empty body.
- **Versions:** objects that need `version` on a change (PATCH `cars/{car}`, `cars/{car}/settings`, `accounts/{account}`, `places/{place}`, `settings`; PUT `settings/mqtt`; optional `?version=` on DELETE `places/{place}`) return it on GET. The server makes one change at a time, so of two changes sent with the same version one wins and the other gets 409. A stale one gives `409 { error: { code: "stale_version", version } }` with the current version.
- **400 or 422:** a wrong type, an unknown field or a bad query value is `400 bad_input`. A well-formed value that breaks a rule (an unknown time zone, an empty password) is `422 invalid`. Both name the fields in `fields`, keyed by path (`units.distance`, `free_supercharging.0.from_date`).
- **Error codes** in use: `bad_input` 400; `not_signed_in`, `wrong_credentials`, `wrong_code`, `sign_in_expired`, `not_claimed` 401; `csrf`, `not_allowed`, `wrong_setup_code`, `password_needed`, `wrong_password`, `wrong_two_step`, `setup_code_expired`, `two_step_required` (the rule asks this account for two-step sign-in here and it has none), `two_step_setup` (finish setting two-step sign-in up first), `https_only` 403; `no_such_car`, `no_such_drive`, `no_such_charge`, `no_such_account`, `no_such_session`, `no_such_token`, `no_such_key`, `no_such_rule`, `no_such_trip`, `no_such_update`, `no_such_place`, `no_such_overlap`, `no_such_import`, `no_such_job`, `no_such_export`, `export_gone`, `no_such_tesla_account`, `no_such_teslafi_account`, `teslamate_not_added`, `no_such_invoice`, `no_invoices`, `no_pdf`, `no_such_pack`, `no_such_file`, `no_such_hold`, `no_such_sign_in`, `no_such_vehicle`, `no_such_fit`, `no_offline_map`, `no_such_tile`, `not_found` 404; `method_not_allowed` 405 (with `Allow`); `timeout` 408 (the request's body took too long to arrive); `stale_version`, `name_taken`, `last_admin`, `setup_done`, `import_running`, `not_uploading`, `wrong_offset` (with `offset` and an `Upload-Offset` header), `not_checked`, `not_matchable`, `not_ready`, `cars_unmatched`, `setup_busy`, `recovery_key_saved`, `move_code_used`, `move_under_way`, `moved`, `not_moved`, `finished`, `export_preparing`, `not_empty`, `account_exists`, `car_taken`, `too_many_sign_ins`, `own_certificate`, `already_assigned`, `builtin` (a built-in UI pack can't be removed), `two_step_first`, `two_step_on`, `two_step_off`, `two_step_kept`, `two_step_setup_expired`, `release_check_off`, `full_rebuild_running`, `full_rebuild_not_running`, `fit_running`, `fit_not_done`, `fit_found_no_layout` 409; `too_large` 413 (bodies over 1 MB); `bad_range` 416 (a `Range` outside an export file); `invalid`, `checksum_mismatch`, `move_code_wrong`, `move_code_expired`, `move_too_old`, `move_not_home_network`, `move_not_offered`, `not_an_export`, `export_too_new`, `export_cut_short`, `wrong_recovery_key`, `tesla_refused`, `teslafi_refused` 422; `old_server_unreachable`, `tesla_unreachable`, `teslafi_unreachable` 502; `throttled` 429 (with `Retry-After`); `server_error`, `rebuild_failed` (a car's rebuild ended failed: the message says why) 500; `not_built` 501 (a route whose server side is not written yet); `no_space` 507; `busy` 503 (with `Retry-After`), `offline_map_unreadable` 503.
- **Who may read:** "(admin)" after the methods of a row means changes need an admin. Reading is admin-only too for accounts, the audit log, upload tokens, CAN Bridge keys, `settings/mqtt`, `network`, `system/storage` (and `system/storage/detail`), `system/health`, `system/move`, `system/exports`, imports and `integrations/tesla`. A watch account may read the rest for the cars it sees; places only where its cars have been. There is no separate export permission: whoever may read a resource may also take it as CSV, GPX or PDF (the "export permission" for GPX tracks is this read access). It never meets a hidden car's id either: `car_order` and `pinned_cars` in `/me/preferences` (and the `prefs` event), and `car_order` in `/settings`, list only the cars the account sees, so a car taken off its list drops out of its order and pins.
- **Sign-in throttle:** wrong tries are counted per address (whatever the names) and per name (apart for the home network and outside it; a name no account has counts like a real one). Five wrong tries from one address or for one name, and the next try from there or for it gets `429 throttled` with `Retry-After`: for 30 s after the fifth, then twice as long after each further wrong try, up to 15 minutes. A try refused this way is not counted. A right sign-in clears the counts of its address and name; otherwise a count is forgotten a day after its last wrong try (there is no 60 s window). Wrong two-step codes, wrong passwords typed again for a change and wrong set-up codes on `POST /setup` are counted the same way, each apart. Ten wrong set-up codes from one address within 60 s on `POST /setup/claim` give `429` until the oldest of them is 60 s old; `POST /setup` counts its own (see "The set-up code").
- **UI pack uploads** (admin calls of the server, crates/web/src/packs): the upload's body is the zip, so the admin's password comes in a header (see "Asking again before a change"); choosing for everyone is a `PUT` on `/ui-packs/chosen`, removing an uploaded pack a `DELETE` on `/ui-packs/{pack}`. A pack's id is made from the `name` in its `ui.json` (lower case, a run of other characters as one `-`). A name that gives a built-in pack's id or `chosen` (that path is the choice, not a pack) is `422` on `name`; a zip without `ui.json` is `422` on `zip` and says so.

### Lists, periods and CSV

- **Cursors** are opaque strings (base64url of the last row's sort key and a hash of the filters). A cursor sent with other filters or another sort gives `400` on `after`. Start again without it. So does a cursor the server did not give out, made or changed by hand.
- **Bodies:** a `Content-Length` that is not a whole number never reaches the API: the HTTP layer refuses the request itself (over HTTP/1.1 a bare `400 Bad Request` with no JSON body, and the connection is closed; over HTTP/2 the stream is reset), so there is no error shape to read. A `Content-Length` over the route's limit is `413 too_large` before any of the body is read. An id in a body that is not text (a car, a place) is a wrong type: `400`.
- `limit` is 1 to 500, default 50. `total` is sent only where it is cheap: `/cars` without `search` or `state`, and `/accounts`.
- **Period:** `from_ms` is inclusive, `to_ms` exclusive, both epoch ms. A missing edge means the start of the history or now. Some resources default to a window when `from_ms` is missing: `series` and `activity` 24 hours, `signals` 1 hour, `trip` 7 days, `battery-level` and `health` 30 days. The window ends at `to_ms` when it is given (else now). Rows belong to the period by their start and keep their own start, end and id; only where a resource says it clips (`/parked`, `/activity`, shares) are they cut at the edges. Local days, weeks and hours use the car's `time_zone` as it is now: when an admin changes it (or, for a car whose zone is not set, when its position moves to another zone), every grouping of that car (statistics, visits and their days, charging heatmaps, storage) follows at once.
- **`cars=`** on report resources: absent or `all` means every car the account sees. A list with an unknown or hidden car gives `404 no_such_car`. The server reads `car=` the same way and beside it (the cars of both are the ones covered), and checks the two on every route: a car named in the query that is unknown or hidden gives `404 no_such_car` whatever the resource.
- **CSV:** `?format=csv`, or `Accept: text/csv` without JSON in it; `format=json` is the default, any other `format` is `400` on `format`, on every list (the audit log, accounts, sessions, UI packs, notices, export files, import holds and the integrations' accounts and status included). A CSV answer carries every matching row, not one page. Nested fields become dotted columns (`start.place.name`), lists of plain values are joined with `;`, null is an empty cell. The file starts with a UTF-8 byte order mark and comes with `Content-Disposition: attachment`. Columns (series, curves, signals) give one row per `t_ms`. Asking CSV of something that is not a list gives `400` on `format`. Text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, so a spreadsheet shows it instead of running it as a formula; numbers are written as they are.
- **Car list sorts:** `sort=last_activity` (default newest first), `name` (A to Z), `soc` (highest first), and `custom`: the person's `pinned_cars`, then their `car_order`, then the rest by last activity. `search` matches the name, the model and the VIN prefix.

### Audit log

`GET /api/v1/audit` (admins) is the server's own record of what people and the server did. Every entry is
`{ at_ms, account, action, group, target, car, summary, address }`: `account` is the account's name (`null` for an
entry the server made itself), `action` one of the codes below, `group` the code's group, `target` the item it is
about (`<kind>:<id>`, or `null`), `car` the car that item belongs to (or `null`), `summary` one line in words that
names the thing ("Matched TeslaMate car Comet to Comet", "Chose the Horizon design", "Changed Maple's time zone to
America/Chicago", "Changed: text size, units", "Checked GitHub for a newer build"; never a method and a route) and
`address` where the request came from (`null` for the server's own entries).

- **Groups**, in the order the pages show them: `sign-ins` Sign-ins, `accounts` Accounts and access, `settings`
  Settings, `cars` Cars and trips, `integrations` Integrations, `imports` Imports and moves. A code the server does
  not know (an entry from a newer server, say) passes through unchanged with `group: "other"`; pages still show it
  (`actionLabel()` in `ui/shared/audit.js`: "Other: <code in words>").
- **Filters**, applied before paging, so every page is full of matching entries: `group=<id>[,<id>]` (`other`
  allowed; an unknown group is `400 bad_input`) and `who=<account name>` (`who=*server`: the entries the server made
  itself, `account` null). With the usual `limit`, `after` (the previous page's `next`), `from_ms` and `to_ms`.
  Newest first. The pages ask for 10 at a time and load more as the list scrolls.
- **Item kinds** (`target`): `car:<car>` · `drive:<car>:<id>` · `charge:<car>:<id>` · `update:<car>:<id>` ·
  `trip:<id>` · `place:<id>` · `import:<id>` · `export:<id>` · `move:<id>` · `account:<id>` · `session:<id>` ·
  `key:<car>:<key>` · `token:<car>:<id>` (`token:<id>` for a new car's token) · `server:<what>`
  (`server:certificate`, `server:release`, `server:recovery-key`) · `settings:server|mqtt|tesla|teslafi` (the server
  settings, the MQTT settings, an input's pace) · `tesla:<account>[:<vehicle>]` · `teslafi:<account>[:<vehicle>]` ·
  `teslamate:local` (the local TeslaMate connection) · `ui-pack:<id>` (a design). For a car match
  (`tesla-car-matched`, `teslafi-car-matched`, `teslamate-local-car-matched`) `target` is the integration's item and
  `car` the Sentry Mate car it was matched to. `auditItem()` in `ui/shared/audit.js` turns a target into words and a
  link; a kind it does not know reads "Something else".
- **Old stored entries are read back mapped**, so the pages never see a raw route: a `change` entry whose
  `METHOD /route` now has a code of its own reads as that code with its summary (`POST /api/v1/release/check` reads
  `release-checked`, "Checked GitHub for a newer build"); any other stays `change` with a summary in words ("Changed
  ..."). An old `settings:teslamate_local` target reads `teslamate:local`.
- **The codes** (`ui/shared/audit-codes.json` holds the same list, written from the server's table; a web test checks
  the two agree). "The server:" marks entries the server writes in its own name (`account` null).

### Vehicle info

`/cars/{car}` `vehicle` is worked out offline (built-in tables, no lookup) from the VIN's first 11 characters, the car's own CAN configuration (the gateway's `0x7FF` pages, the pack's 0x352 and 0x332 readings, the message the VIN came in), the Tesla API's `vehicle_config`, a TeslaMate import's car row, and what an admin typed in `config`.

- **Fields**, each a fact `{ value, source, confidence, note? }` (`value`, `source` and `confidence` null when nothing says it): `maker`, `built_in` (country code), `model` (`"Model Y"`, `"Cybertruck"`), `model_year`, `plant`, `platform` (Model S and X: `"legacy"` \| `"refresh"`), `body`, `restraint`, `seats` (a hint from the restraint set), `battery_type` (what VIN position 7 says), `chemistry` (`"lfp"` \| `"nca_nmc"`), `pack`, `pack_code` (`"4 (PACK_75_KWH)"`, or the raw number), `nominal_kwh` and `usable_kwh` (`{ min, max }`, kWh: one value from the pack's own reading now, a range from the table when new), `motors`, `drive` (`"RWD"` \| `"AWD"`), `performance`, `trim` (`"Model Y Long Range AWD"`), `epa_range_km` (the EPA's rating when new, US test cycle, US-built cars only), `wheel`, `wheel_in`, `paint`, `roof`, `spoiler`, `steering` (`"left"` \| `"right"`), `region` (the map region: `"US"`, `"EU"`, `"CN"` ...), `supercharging_access`.
- **Beside them:** `vin_prefix`, `year_kind` (`"model_year"`, or `"build_year"` for Shanghai and Berlin cars, whose 10th VIN character is the calendar year built), `trim_candidates` (the EPA trims the car can be when the inputs don't settle on one), `epa_name`, `epa_id`, `wheel_options_in` (the factory sizes when the car's own is not known), `disagreements: [{ field, values: [{ value, source }] }]` (two inputs said different things; the first value is the one shown), `unknown_codes: [{ field, source, at, code }]` (a VIN position such as `"vin:8"` or a CAN signal whose code the tables don't know: no value is given, never a guess), `notes` (plain sentences).
- **`source`:** `"owner"` \| `"can"` \| `"vin"` \| `"tesla_api"` \| `"teslamate"`. A value from a table through the VIN (the EPA range, a pack's energy when new) is `"vin"` with a `note` naming the table row's source. A US-built car's `chemistry` from the VIN is only the usual pack for its model, year and drive: `"vin"` at `"low"` confidence.
- **Precedence**, per fact: what an admin typed, then the car's CAN configuration, then the VIN (the pack's brick count is not read for the chemistry until its rules are checked on real logs); the Tesla API's words come before the VIN's tables for `trim`, `wheel`, `paint`, `roof` and `spoiler`, after it elsewhere; an import comes last. Values in another site's own words (`"74d"`, `"Pinwheel18"`) are shown but never compared.
- **`confidence`:** `"high"` (Tesla's filing or service manual, the EPA's dataset, the car's own configuration), `"medium"` (several sources agree), `"low"` (one source, to be checked).

### Rows

- **In progress:** a drive, charge or gap still going has `end_ms: null`, its figures up to now, and `flags.in_progress: true`. The current state span in `/states` has `end_ms: null`.
- **Where:** a Drive's `start` and `end` are `{ lat, lon, place: { id, name } | null, address: { short, locality, region, country_code }, label }`. `label` is what to show: the place name, else the short address. A drive whose data stopped has the last known point and the label "Data stopped here". Timeline points are the same with `address` as the short text.
- **Purpose** on a Drive is `{ value: "business" | "private" | "commute", relation, note, source: "owner" | "rule" }` or null. An owner's choice wins over a rule.
- **Overlaps:** where live history (SMO or the Tesla API) and imported history both exist, lists with `source=all` show only the side chosen for that span (live at first). Where a TeslaMate import and a TeslaFi import both have rows, only one import is shown there (with `source=all` and `source=import`): at first the one with more drives and charges in the span, then more positions, else TeslaMate's. Lists, details, totals, series, the timeline and statistics follow both choices, so no drive is shown twice. A software update both imports have is one update the same way (the updates list, its count and gaps, the timeline and `/totals`): the row of the site its span shows, and outside such a span the earlier of two rows of the same version within a day. An imported drive or charge that was still going on when a stretch of live history began (the first live day, or live logging back after a gap) starts before that stretch, so the time it covers is an overlap of its own where the live side has a drive or charge starting inside it: the live row (the rest of the same drive or charge) is shown and the imported one hidden, until the span is flipped to the import, which then shows its whole row instead. `source=smo`, `source=tesla_api`, `source=import:teslamate` or `source=import:teslafi` shows that source only, whatever was chosen. An overlap row is `{ id, kind, start_ms, end_ms, shown_source, default_source, default_reason, live: { drives, charges }, imported: { drives, charges }, sites: { teslamate: { drives, charges }, teslafi: { drives, charges } }, sources, version }` (`kind`: `live` or `imports`; `shown_source`: `live`, or the imported side by its site, `import:teslamate` or `import:teslafi`, `import` on a `live` span when both sites' rows are in it) plus the old `shown: "can" | "teslamate"`, `can` and `teslamate` (kept for one release). PATCH takes `shown` in either spelling.
- **Power signs:** `power_kw` in `now` and in series is the pack's power: positive out of the pack (driving, heating), negative into it (charging, regenerating). Charge figures and the charge curve's `power_kw` are charging power, positive.
- **Tyres** are always ordered front left, front right, rear left, rear right.
- **A place's price on a charge:** the charge's curve says when its energy was taken (time-of-use rates, steps), scaled to the grid energy where known; a curve with no energy under it (its points more than 5 minutes apart, or all at 0 kW) prices the charge's energy (the grid's, else the energy added) at the price of its start, as a charge without a curve, and `cost_breakdown.gap_ms` still says how much of the curve was gaps. The cost is kept when the charge ends and a rebuild does not change it, except that a charge that has grown since (it ends later or holds more energy: its logs came late or out of order, and the first part was settled alone) is priced again as a whole at the price as it is then.
- **Price per kWh:** basis `grid` is the cost over the grid energy (AC, by the meter). Basis `pack` is the cost over the energy added to the pack (fast charging, where the grid energy is unknown). `fast_charger.billed_kwh` is what the charger delivered (about the car's inlet energy).
- **Grid energy:** a Charge's `energy_grid_kwh` (AC only) is the AC line's volts times amps, which are one phase's, times the phases in use, summed over the charge: how many phases by the line's own power where the car sends it (`ac_line_kw`), else the phase count the input gives (the Tesla API's `charger_phases`, whose 2 means three), else one. Each reading counts until the next one, for 10 s at most where the car's own seconds stop and 150 s where an API's do (an API read at its gentle pace gives one every 2 minutes).
- **Charging efficiency:** a Charge's `efficiency_pct` is `energy_added_kwh` over `energy_grid_kwh` and `losses_kwh` their difference, only when both were measured over the same part of the charge (the inputs' values cover different seconds: SMO's every second, an API's near each poll). When they were not, both are null although the two energies are shown, and `efficiency_note` says why in a sentence to show as the efficiency's title (tooltip), e.g. "Not measured over the same time: the energy added covers 5 min of this charge and the grid energy 12 min (5 min both), so no efficiency or losses are shown."; else `efficiency_note` is null (also when the grid energy is simply unknown, as on DC). `charging_efficiency_pct` in `/cars/{car}/totals` and `efficiency.value` in `/visits/summary` (`charges_counted`) count only the charges with an efficiency; their `energy_grid_kwh` stays the sum of every charge's.
- **Entered rates come back as entered:** after `PUT .../cost` with `mode: "per_kwh"`, `price_per_kwh.value` and the breakdown's `per_kwh` are the amount sent (up to 5 decimals), not the total divided back; with `mode: "per_minute"` the breakdown's `per_minute` and `minutes` are the rate sent and the charging minutes. Only `cost.amount` and `total` are rounded (to 2 decimals). A rate is kept as the rate: `cost.amount` is the rate times the charge's energy (with `energy_basis: "grid"` the grid energy, else and where that is unknown the energy added) or its minutes as they are when read, so a rate entered while the charge is going on, or before a late log made it longer, follows the charge; a `total` stays as entered.
- **Attention items** carry `detail` as an object in metric units, for example `{ tyre, pressure_kpa, recommended_kpa, source }` (`tyre_low`: the lowest tyre, `tyre` null while which wheel each sensor is is not known; `source` as the Now's `tyre_recommended_source`), `{ last_upload_ms }`, `{ soc_pct }`, `{ door }`, `{ reason, log_start_ms }`, `{ last_data_ms }`. The page writes the sentence.
- **Stale** means no upload for more than one hour.
- **Saved trips** belong to the account that saved them; a watch account may save its own. Purposes and purpose rules change car data and need an admin.
- **Upload tokens and CAN keys** are admin-only, reading included. DELETE on a token revokes it (it stays listed with `revoked: true`). The secret comes once, in the POST answer.

### Live values

- In `/cars/{car}/now`, every value read from the car is `{ value, at_ms }` or null: the signals, each `location` part, each tyre, each flag and door, each `charge` part. The snapshot's own facts are plain: `state`, `since_ms`, `at_ms` (the newest sample), `received_ms`, `delay_s`, `stale`, `buses` (each `{ bus: "vehicle" | "chassis", awake, at_ms }`), `driving`, `est_basis`, `charge.finish_ms`, `charge.charge_id`, `drive`, `awake_reasons`, `software`, `location.place` and `location.address`. With two live inputs, each value is the newest one either sent; for speed, power, gear and position an SMO value up to a minute old still beats a newer Tesla API value (the API's times lag), and the value's `sources` names the one it came from. `heading_deg`, `usable_soc_pct`, `charge.limit_pct`, `charge.to_full_min` (while charging) and the `sentry`, `user_present`, `keep_climate`, `climate` and `battery_preconditioning` flags come from CAN when the car sends them, else from the Tesla API while its newest reading is current; `charge.added_kwh` (while charging) and `car_est_range_km` (the car's own range estimate, `est_battery_range`) come from the Tesla API while its newest reading is current, else from local TeslaMate's MQTT values, and `sources` names the one; `est_range_km` is Sentry Mate's own estimate (`est_basis`). `charge.status`, `charge.phases`, `charge.pilot_a`, `charge.limit_source`, the doors, `trunk`, `frunk`, `charge_port_open` and `display_on` come from CAN only; lock and windows are never on CAN; they and the other values no CAN message carries are in `off_can` (below). `received_ms` is when the newest data came from either input.
- **`off_can`** in `/cars/{car}/now`: the values no CAN message carries, from the API inputs. Each is `{ value, at_ms, sources: [{ kind, label }], stale }` or null: `version` (the version text the car reports), `update_available`, `update_version`, `update_download_pct`, `update_installing` (from the input's update status word; an unknown word gives nothing), `locked` (only as an input read it: never from a lock request), `windows_open` (true when one is open, false only when one input read all four closed), `windows` by seat, `sunroof_state` (`closed`, `open`, `vent` ...), `sunroof_pct`, `scheduled_charge_start_ms`, `scheduled_departure_ms`, `route` (`destination`, `km`, `minutes`, `traffic_min`). Value by value, the first input in the order SMO, the Tesla API, TeslaFi's API, local TeslaMate (lock, version, update, charge schedule, any window open, route) with a current value gives it; a value is `stale` once older than its limit (locked, windows, sunroof: 1 h; update: 6 h; schedule: 12 h; route: 10 min; version: 30 days), and a stale value is kept only when no input has a current one. The VIN is never in it.
- **`software`** in `/cars/{car}/now`: `version` and `version_source` are the car's current version as `/updates` `summary.current_version` gives it (`version_source` as on `/updates`: `teslamate`, `teslafi`, `tesla_api`, `teslafi_api`, `teslamate_local`, `owner`, `build_match`, null). `version_since_ms` is when it was first seen (the newest update's end, or when the input first reported it); `changed_since_ms` is set while the newest update has no name (the build changed since then).
- `state` in the car list and in `now` is one of `driving`, `charging`, `parked`, `asleep`, `unknown`. In `/states` it is `online`, `asleep` or `unknown`, with the awake buses; vehicle bus only is `online` with `buses: ["vehicle"]`.
- `charge.status` is one of `disconnected`, `no_power`, `about_to_charge`, `charging`, `complete`, `stopped`.
- **Tyres** in `/cars/{car}/now`: `tyres_kpa` is front left, front right, rear left, rear right when `tyres_slots_mapped` is true (the input names the wheels: the Tesla API, the chassis bus's 0x31F, or 0x219 with its four sensor locations each naming a different wheel); false: 0x219's four slots in the car's own order, which wheel each is not known. `tyre_recommended_kpa` (front axle) and `tyre_recommended_rear_kpa` are the recommended cold pressures, from `tyre_recommended_source`: `owner` (typed: `config.tyre_pressure_front_kpa` / `_rear_kpa` of `PATCH /cars/{car}`) beats `can` (0x219 page 4, `{ value, at_ms, sources }` as a value read from the car) beats `placard` (the door placard's for the car's model, model year and wheel size, from a built-in table citing the owner's manual; `tyre_recommended_wheel_in` names the size, `tyre_recommended_wheel_from` where that size comes from (`owner`, `can`, `vin`, `tesla_api` or `teslamate`, the car's `wheel_in` fact), and `tyre_recommended_wheel_guess` is true when it is not typed and not the car's own wheel setting read with high confidence (a factory tyre, the Tesla API's wheel name, an import or the build's only factory size), so pages can ask the owner to type the size; all three null unless `placard`); typed and placard values are `{ value, at_ms: null, sources: [] }`; all null when none is known. `tyre_low` (`{ value, at_ms, sources }` with the tyres' time, or null): a tyre more than 10 % under its axle's recommended pressure; while the slots are not mapped every tyre is judged against the lower of the two (no false alarm: a tyre low for the higher axle only is missed). MQTT's `tire_low` and the `tyre_low` attention item say the same.
- `/states` `share_pct`: `parked` is the share of time not driving (known time only: (known − driving) / known, null when no time is known), `asleep` asleep, `awake` online (driving included), `unknown` no data, these three of the whole period. They overlap on purpose and need not add up to 100.
- `/awake-reasons` joins awake spans that touch into one, with the reasons of both and a time-weighted average power.

### Events (`/api/v1/events`)

- Standard server-sent events: `event:` name, `id:` (a counter), `data:` JSON. The stream starts with `retry: 3000`. A comment line every 15 s keeps it open. There is no replay for `Last-Event-ID`; after a reconnect, load what you show again.
- `now`: `{ car, now }`. The first one for a car on a stream carries the whole object; later ones carry only what changed, to be merged field by field. A `{ value, at_ms }` pair is always sent whole.
- `rows`: `{ car, kinds, from_ms, to_ms }` when a drive, charge, parked spell or gap starts or ends. `fleet`: `{ car, change: "renamed" | "added" | "removed" | "list_changed" | "inputs" | "sold", name }` (`inputs`: the car has data from a new live input, such as its first Tesla API reading; `sold`: an admin marked the car sold or not sold). When an admin changes an account's car list, that account's streams get `added` or `removed` per car (`name` null on `removed`), or one `list_changed` with `car: null` when more than 100 changed, then a `prefs` event; a car given back starts again from a whole `now`. `prefs`: the whole preferences object, to that person only. `notice`: one notice.
- **Live figures** (`job`, `health`, `connections`, `storage`): each topic is sent when its value changed (a top-level `read_ms` alone is no change), and at most every 0.5 s per job, every 1 s per car's health and for the connections overview, every 2 s for storage, however busy the server is (a full rebuild decoding thousands of logs a minute still sends at most two `job` events a second). A stream gets only the changes after it opened: a page reads the figure's endpoint when it opens and after every reconnect, then follows the events, and reads the endpoint itself (every few seconds) only while the stream is down. Topics that take the server long to work out are looked at less often (at most a twentieth of its time). Nothing is worked out while no stream is open.
  - `job` (admins only): `{ kind, id, status }`, `status` exactly as the job's status endpoint gives it. `kind`: `full_rebuild` (`id` `""`, `status` as `GET /system/full-rebuild`), `compaction` (`""`, the `compaction` object of `GET /system/storage/detail`), `export` (the export's id, the ExportFile of `GET /system/exports/{export}`), `missing_scan` (`""`, `{ state: "idle" \| "running" \| "done", keys_done, keys_total, found, started_ms, finished_ms }`: the look for CAN logs the server lost, at the start and once a day), `import` (the import's id, as `GET /imports/{import}`), `invoices` (`"tesla"` or `"teslafi"`, the InvoicesBlock of that input: its fetching of Supercharger invoices and charge costs).
  - `health`: `{ car, health }`, `health` as `GET /cars/{car}/health` with no period (last upload, last log check, logs waiting, unknown time, chain gaps, dropped frames, missing logs, keys); to every stream that sees the car.
  - `connections` (admins only): the body of `GET /integrations/overview`.
  - `storage` (admins only): the body of `GET /system/storage` plus `compaction` (as in `/system/storage/detail`; the per-category walk over the data folder is not sent).
  - Lists, totals and statistics follow `rows`: a page reads what it shows again (in place) once a burst of `rows` events for its car has passed.
- A stream ends when its session ends (sign-out, account removed, password changed), when the two-step rules no longer let its account see cars (a rule for everyone that the account hasn't set up yet: checked at once when the rule changes), and when its reader falls 1000 events behind (it would miss a delta); the browser then reconnects, and the page loads what it shows again.

### Time series

- `values` holds one column per field. With one `agg` (or none), the key is the field name. With several, every agg is also under `<field>.<agg>` and the plain key holds the first one.
- Without `agg`, the plain column is the mean (the last value for `lat`, `lon`, `accuracy_m`, `odometer_km`, `heading_deg`), and when buckets are longer than 1 s, `<field>.min` and `<field>.max` come too. That is how downsampling keeps minima and maxima.
- `max_points` is 2 to 20000, default 1000. Buckets are 1 s, 2 s, 5 s, 10 s, 15 s, 30 s, 1, 2, 5, 10, 15, 30 min, 1, 2, 3, 6, 12 h, 1, 2 or 7 days (beyond that, a whole number of days), aligned to UTC, the smallest that fits. The first bucket holds `from_ms`, so it can start before it; the answer still never holds more than `max_points` buckets.
- `state` per bucket is the state that took most of it. `coverage_pct` is the share of the bucket with known data (asleep counts as known). A bucket with no sample is null in every column.
- `/signals` needs `series` (names from `/signals/latest`) and takes `max_points` (2 to 20000, default 2000). Rows of `/signals/latest` carry `has_series`: false for signals with named values (`gear`, `sentry_mode`, `charge_status`), which have a latest value only; asking `/signals` for them is 400.
- **Answers that decode stored logs take turns:** `/signals` and `/signals/latest` decode the car's stored CAN logs while they answer. `/battery`, `/battery/capacity`, `/battery-level`, `/projected-range` and `/efficiency` read the pack's own values of each day, which the server works out ahead in the background (once idle after a start, every 10 minutes, and when an answer finds a day not worked out yet): they wait for no turn. An answer that finds a day not worked out yet waits for that (up to 20 s); past it, it decodes what it needs itself and takes turns like the others. At most 3 answers that decode run at once for the whole server; more wait their turn for up to 20 s, then get `503 busy` (with `Retry-After: 5`). One account has at most 4 running or waiting; one more is `429 throttled` at once. A request that goes away (the client closed it, or it timed out) stops its decoding. One `/signals` answer decodes at most 2 GiB of log lines, shared out over the logs it reads (`logs_read`), so a long period of large logs is a thinner read.
- Drive climate and battery heating are series fields too: `battery_heat_kw` (power the pack spends heating itself, kW; 0 when it is not heating), `climate` (`off`, `on`, `precondition`, `overheat_protect`; text, so its plain column is the last value of the bucket) and `fan_level` (blower step 0 to 10, 0 = off). Null where the car does not send them (older Model S and X, imported history).
- The charge curve is 1 Hz up to `max_points` (default 4000); longer charges come at a coarser `step_ms`, which the answer states.
- Charge curve fields: `power_kw`, `volts_v` and `amps_a` are the pack side (charging power positive). `ac_volts_v` and `ac_amps_a` are the AC line at the inlet (volts and amps of one phase; null on DC), `ac_line_kw` the AC line power, `dc_volts_v` and `dc_amps_a` the DC charger's output (null on AC), `heater_kw` the power the pack spends heating itself. `limit_source` names what sets the current the car may draw: `station` (the pilot), `cable`, `car` (its own maximum) or `setting` (the current set on the screen); null when the car does not say.

### Formats

- **GeoJSON track:** a FeatureCollection with one LineString per stretch without dropped frames. Coordinates are `[lon, lat, elevation_m]`; `properties` holds parallel `t_ms` and `accuracy_m` arrays, plus `speed_kph`, `power_kw`, `soc_pct` when asked in `extensions`. A live drive's track with values from the chosen import (with import gap filling on) adds a parallel `imported` array to that stretch's `properties` (per point, the fields the import gave it: `["elevation_m"]`, or every field for a point of the import's own where the drive's data has a gap of over 10 s) and `value_sources: { field: [source] }` beside `features`. `simplify_m` thins points (Douglas-Peucker) and keeps the arrays aligned.
- **GPX track:** GPX 1.1, one `trkseg` per stretch, `ele` and `time` on every point, extensions in our own namespace.
- **Logbook PDF:** a plain table, landscape, times in the car's time zone, with the continuity warnings and the totals per purpose.

### Battery and efficiency

- **`/battery`:** `capacity.new_source` is the first that exists: `owner` (`capacity_new_kwh` in the car's settings), `early_bms` (the pack's readings in its first 30 days), `imported_charges` (the median of the earliest ten imported charges' readings worked out from the energy they stored, as in `/battery/capacity`), `vehicle_info` (the car's build: the usable kWh when new, else the full pack's, then compared with the full pack now), `imported_charges_energy_added` (no factor to work out the energy stored, and no build: the earliest imported charges' energy added, which reads several % high; note `new_value_from_imported_charges_energy_added`). `range.new_source` is `owner`, `first_30_days` or `vehicle_info` (the EPA rating). `range.full_now_km` is the car's range over its charge level, else `full_now_from_energy_km` (usable energy over the consumption factor, the build's where the car has none yet). `notes` codes: `new_value_typed`, `new_value_from_early_readings`, `new_value_from_imported_charges`, `new_value_from_imported_charges_energy_added`, `new_value_from_vehicle_info`, `cold_battery_locks_part`, `lfp_charge_to_100_weekly`, `imported_history_estimated`, `pack_replaced`, `reading_above_new`, `no_history`. `capacity.degradation_pct` is never below 0 and `health_pct` never above 100: a pack is not healthier than new, so where the capacity now reads above the value when new (a typed value too low, or one from early readings under a noisy reading now) they stop at 0 and 100, `difference_kwh` stays what it is (below 0) and `notes` has `reading_above_new`. `lifetime` adds `standing_kwh` (used while parked) and `basis`; `charged_kwh` is `ac_kwh + dc_kwh + unknown_kwh`, where `unknown_kwh` is the energy of the logged charges whose kind (AC or DC) no input told, as `unknown_kind` in `/totals` (0 from the pack's own counters, which count every charge as one or the other). `capacity.basis` names where full and usable both come from: `pack` (the pack's full pack less the newest buffer it named, the BMS's own figure; usable null when it named none and there are no charge readings) or `charges` (the median of the last charges' readings; full is that plus the buffer, null when no buffer is known). `capacity.usable_basis` says what usable is: `buffer` (the BMS's full pack less its buffer), or for `charges` the readings' basis (`rated_range`, or `energy_added` when any of them is). Usable is never above full. Capacity readings a pack cannot hold are left out (here, in `/battery/capacity` and in the value when new): below 30 % or above 1.3 times the pack's rated size (the owner's value when new, else the car's build; 10 to 250 kWh while neither is known). `usable_soc_pct` is the car's own usable level where an input sends it, else the pack's energy now above its buffer over its usable capacity. `chemistry` is the owner's setting (`source: "owner"`), else what the car's build says (`detected`, with its `confidence` and `evidence`): the same detection as the build card in `/cars/{car}` (`vehicle.chemistry`) and `battery_chemistry.detected` in the car's settings. A car without history answers the same keys with null.
- **Capacity follows the charges:** `group=charge` (the default) gives one reading per finished charge that added at least 10 %: `usable_kwh` = `stored_kwh` / (`end_soc_pct` - `start_soc_pct`) x 100 and `full_pack_kwh` = `usable_kwh` + `buffer_kwh` (the buffer once: the % is the car's screen %, TeslaMate's `battery_level`, which already runs over the usable capacity), from the figures that charge's row shows (imported charges included), with `charge` set to that charge's id. `stored_kwh` is the energy the charge stored, on the same basis as the pack's own capacity: (`end_range_km` - `start_range_km`) x the car's own stored energy per km of rated range (its pack's energy above the buffer over its rated range, the factor `/efficiency` takes from the samples; never a typed or imported factor) (`usable_basis: "rated_range"`). It is not `energy_added_kwh`: that is the energy that went into the pack (pack side: SMO's from the CAN counter, imported and API charges the car's own `charge_energy_added`), and part of it is lost as heat in the cells or runs the car while it charges, so energy added over the % added reads several % above the pack's capacity (the grid energy, wall side, is more again and is never used). Only where the car has no pack energy readings at all is `stored_kwh` the energy added (`usable_basis: "energy_added"`: it reads high). `energy_added_kwh` is the row's, for comparison. `group=day` gives the pack's own reading per awake day (`method: "bms"`); `group=month` the median of those per month, with `readings`. Imported days have no pack readings. `x=odometer` orders by odometer. Where the pack names no buffer that day, `usable_basis` says what `usable_kwh` is instead: `recent_buffer` (less the newest buffer it named on another day) or `full_pack` (no buffer known at all). A `group=day` page looks at a bounded number of record days; when that runs out before the page is full it answers fewer items (even none) with a `next` that goes on from there, so follow `next` until it is null. `trend.projection` is `{ warranty_pct, full_pack_kwh_at_warranty, odometer_km, t_ms, method: "linear" }` or null when the pack is not losing capacity.
- **Days are the car's own:** wherever these resources bucket by day or week (`/battery-level` and `/projected-range` with `bucket=day` or `week`, `/temperatures` `daily`), a bucket runs from local midnight to local midnight (weeks from Monday), so the day the clocks change is 23 or 25 hours long and `t_ms` is always a local midnight. `bucket_ms` then names the nominal length (86400000 for a day). Hour buckets and buckets of a number of ms are fixed lengths.
- **`/battery-level`:** `from_ms` defaults to 30 days back. `bucket` defaults to `hour` up to 31 days, else `day`; the answer names `bucket` and `bucket_ms`. `moving` lines have one value per bucket (a window of daily means ending that day; `window` defaults to `7d`); `moving=false` gives empty lists. `band.high_pct` is 100 for an LFP pack. `charge_limit` is `[{ t_ms, pct }]`, a step line. `stats` is `{ mean, median, min, max }`.
- **`/projected-range`:** columns like `/series` (`t_ms`, `values`, `bucket_ms`, `coverage_pct`, `state`). `bucket` is `hour`, `day`, `week` or a number of ms; without it, the smallest that fits `max_points`.
- **`/parked`:** a spell is a stay parked off a charger at one spot, newest first, until the car drives, charges or moves (updates and gaps where it did not move stay inside). Rows also carry `car`, `duration_ms`, `clipped`, `range_lost_km`, `range_lost_per_hour_km`, `source`, `sources` and `source_label`. `energy_method` is `counter` (the pack's own energy counters) for CAN rows, `range` for imported ones. `summary` adds `hours`; `summary.energy_kwh` sums the spells whose energy is known, and is null when there are spells and none of them has a known energy (0 with no spell); `summary.cost` is `{ amount, currency, basis }` at the home price, or null.
- **`/efficiency`:** `min_distance_km` defaults to 1, `temp_group_c` to 5 (1 to 20). A group's `temp_c` is its lower edge; `temp_to_c` its upper edge (both rounded to 0.1 °C: a drive is in the group whose index `floor(outside_avg_c / temp_group_c)` equals `round(temp_c / temp_group_c)`). `min_distance_km` applies to `net_wh_per_km`, `distance_km`, `drives` and the groups; `gross_wh_per_km` always covers every drive of the period (`all_drives`) plus all parked energy, so it stays what owning the car costs; it is null while the parked energy is not known (`parked_kwh` null). `factor.source` is `energy_and_range`, or `owner` when the car's settings override it (then `as_of_ms` is null). The car's own factor is the median of the daily means of its energy over its range over its last 14 sample days (`readings` counts the samples), so it holds still between requests; `/projected-range` uses the same value. Energy per km (`net_wh_per_km`, `gross_wh_per_km`, a group's `wh_per_km`) counts only the distance of drives with energy, as `/drives` does; `without_energy` counts the drives left out of it. A period after now answers the empty result.
- **`/temperatures`:** `daily` rows also carry `t_ms`, the local midnight that starts the day; `coverage_pct` is the share of that day (as far as the period goes) the car was awake. Lowest and highest, in the summary and each day, take every reading (sampled at least once a minute while awake), so they are never above the lowest or below the highest point `/series` gives for the same period. A car that does not send a value (the old Model S has no cabin temperature) has nulls there.

### Reports

- **`/logbook`:** rows also carry `start_place_id` and `end_place_id` (the matched place, or null), `relation`, `purpose_source` (`owner` or `rule`, null without a purpose), `purpose_rule` (the rule id when a rule gave it) and `in_progress`. `continuity_gap_km` is the odometer distance between the end of the drive before (in the period) and the start of this one; null on the first row. Drives between them without an odometer are passed over, their distance taken off (a drive with neither odometer nor distance in between leaves it null). Rows show the values the chosen import fills (start and end place, odometer, purpose), as `/drives` does. `prev_end_ms` is when that drive before ended (null on the first row): where a missing stretch starts.
  - **A page at a time:** with `limit` (1 to 500, default 50), `after` (the `next` of the page before), `offset` (the first row, 0 based) or `at_ms`, the answer is `{ from_ms, to_ms, items: [row], next, offset, total, count, counts_by_purpose: { business, commute, private, none }, totals_by_purpose, continuity: { rows, first_seq, first_start_odometer_km, last_seq, last_end_odometer_km, logged_km, missing_km, gaps, worst: [row] }, rules_used: { rule: n }, truncated }`. `items` start at `offset` among the rows the filters show; `total` is how many they show, `count` every row of the period. The counts, totals, `continuity` (gaps over 50 m; `worst`: the 4 largest) and `rules_used` (rows each rule gives its purpose) always cover the whole period, whatever the filters. A cursor stays with the filters and order it came with (`400 bad_input` on `after` otherwise); `offset` and `at_ms` do not count as filters, so a page reached by either gives a `next` that goes on from it.
  - **Filters and order:** `purpose` (`business`, `commute`, `private`, or `none` for drives without one) `q` (words that every row shown has in its places, addresses, relation or note, in any case) and `gaps=true` (only drives after distance not logged, over 50 m) narrow the rows; `sort` (`seq`, the default: by start; `distance`; `gap`, the missing distance before; `odometer` at the start; `from` and `to`, the place else the address; `purpose`) and `dir` order them, ties by `seq`, a missing value last either way. `at_ms` (with `sort=seq` only, else `400`) starts the page at the first row on the far side of that time: starting at or after it oldest first, before it with `dir=desc`; the last row when none is.
  - **Kept:** the server works the period's rows out once (addresses, places, purposes, the continuity check) and keeps them while the car's rows, the places, settings, the shown sides of overlaps, the purposes and the rules stay the same, so paging, filtering and the CSV read no drive again.
- **CSV:** every row, or with `purpose`, `q`, `gaps`, `sort` or `dir` every row they show in that order (never one page), sent as it is written (no `Content-Length`, not compressed). The PDF always holds every row.
- **`/statistics`:** rows are newest first and clipped to the period: the first and last rows can be part periods. `label` is `2026-11-16` (day), `2026-W47` (ISO week), `2026-11` (month), `2026` (year) or `All`. Rows also carry `time_zone`, `energy_used_kwh` (driving) and `energy_standing_kwh` (parked). Money is per currency: `cost_by_currency: [{ currency, amount }]`, `price_per_kwh: [{ currency, value }]`, `cost_per_100km: [{ currency, amount }]`; these are the priced charges only (a typed cost, a place's price, free Supercharging, an invoice, an import's cost), `charges_priced` of `charges`. A charge without a cost is estimated where it can be (`charges_estimated`): at its place's price as it is now, else the car's `default_price_per_kwh` (`/cars/{car}/settings`) on its grid energy, else the energy added; the estimates are `cost_estimated_by_currency`, never in `cost_by_currency`. `cost_total_by_currency` is both together per currency, `cost_total_per_100km` that over `distance_logged_km` (empty under 1 km) and `cost_total_per_day` over the row's days (at least one). `distance_odometer_km` is the car's odometer at the row's end less at its start, from its clean odometer series: readings are kept only where they go up in time with the car's others at a pace a car can drive and stay under 2,000,000 km, so another car's rows, a value in the wrong unit or a "not available" value are left out (`completeness.odometer_dropped` counts those of the row's period); `/mileage`, `/totals` (`odometer_first_km`, `odometer_last_km`) and `/compare?metric=odometer` read the same series. The answer names `period` and, for several cars, `cars`. Drives count by start time, charges by start time: the months add up to the Drives and Charges lists for the same period.
- **`/mileage`:** rows also carry `period_end_ms` and `label`; `projection` adds `basis_days`. `distance_km` is by odometer; `not_logged_km` is what the car drove in gaps.
- **`/gaps`:** `cause` is `no_log` and `not_recorded` as they are, `chain_gap` for a log missing inside a charge (`inside: { charge }`), and `unknown` for a log that was left out (it failed its check, could not be read or names another car's VIN) or lost frames. Rows also carry `duration_ms`, `gap_reason` (the timeline's word, which says which: `failed_check` for a log whose signature, hash or chain did not hold; `unreadable` for a stored log that could not be decoded; `other_vin` for a log whose frames name another car's VIN than the car's; `dropped_frames`; `not_recorded`; `no_log`), `source`, `sources`, `source_label` and `inside`. A gap still going has `end_ms: null`.
- **`/compare`:** `{ metric, unit, cars, series: [{ car, name, time_zone, t_ms: [], values: [] }] }`, one point per day with data, or per ISO week when the period is longer than 120 days (`capacity` in kWh, `full_range` and `odometer` in km, `wh_per_km` in Wh/km). With `wh_per_km`, `min_distance_km` (default 0) leaves out drives shorter than that, as on `/efficiency`, and only the distance of drives with energy counts, as on `/drives`. A car the account cannot see makes the whole request 404, so pages ask only for cars they could open.
- **Visits:** a visit is one stop, from arriving to leaving; the stop going on now has `left_ms: null`. For a car with only imported history (no CAN rows) its last stop also has `left_ms: null`, but its days, dwell, `last_ms` and the place's `last_visit_ms` end where that history ends, never today. Rows also carry `label` (the place name, else the short address), `time_zone`, `unknown_ms`, `source`, `sources` and `source_label`. `sort` is `arrived_desc` (default), `arrived_asc` or `dwell_desc`. `q` matches the place name and the address. `city=` takes a `city_key` (`US/California/San Francisco`).
- **Visit groups** (`/visits/places`, `cities`, `regions`, `countries`) carry `level` and the address parts of their level; `sort` is `visits` (default), `dwell`, `last` or `name`. `/visits/summary` adds `visits` and `cars`; `days` counts each car's days. The summary and every group row also carry `first_car` and `last_car`: the car of the first arrival and of the last moment there, so a page can show `first_ms` and `last_ms` in that car's zone.
- **`/tracks`:** `max_points` (2 to 200000, default 10000) is shared over the drives by duration, at least two points each, and the answer never holds more; too many drives for the points gives `400` on `max_points`. The answer adds `points` (the number sent) and each drive's `source`, `sources` and `source_label`.
- **`/updates`:** rows also carry `car`, `build_id` and `until_ms` (when the next update came; null for the current one). `detected_by: "fingerprint"` is a "Tesla update installed" found from the modules' firmware fingerprints (below): `start_ms` is the last time the old fingerprints were seen and `end_ms` the first time the new ones were (also `between_ms: [from, to]`; never in progress: `end_ms` is always set), placed between the last drive or awake span with the old set and the first with the new one. One install is one update: after an install the modules restart and a fingerprint can change several times (even back to the old value) before the set settles, so changes less than 30 minutes after the one before (within an hour of the first new value) are grouped, each field's change from its value before the install to its value once settled (a value that went back is no change; an install that changed nothing is no update), and the update's fingerprint set is the settled one. Updates stored before this are grouped again on the next start or rebuild, and a typed name (or a cleared one) on any of them stays with the install (a typed one over a cleared one). When a whole UTC day inside `between_ms` had no fingerprint readings at all, `readings_gap` is true: the update came somewhere in there, so `start_ms` and `end_ms` are both where the new set was first seen (the row never stretches over the days nobody read) and `duration_ms` is null; pages say "between X and Y (no readings in between)" from `between_ms`, and look for the drive before `between_ms[0]` and after `between_ms[1]`. The vehicle bus whose fingerprints count is the interface the log's sidecar bus map names (`can0` when it names none); `changes` lists each changed field with its module (`module` id, `module_name`), `old` and `new` as lowercase hex; `changed_modules` the module ids; `build_id` names the whole fingerprint set after it (16 hex digits); `source` is `can` and `sources` SMO. Its `version` is null until it is named: typed by an admin (`named_by: "owner"`), else from a live input (`named_by: "auto"`, `version_source` that input: `tesla_api`, `teslafi_api` or `teslamate_local`): the first version an input started reporting from `between_ms[1]` (the new set first seen) until 24 h after it; else the newest it changed to inside `between_ms` that is not the one it reported before; else the one it was reporting when the new set appeared and still reported after it (even when it reported it before the window too), from the inputs in order the Tesla API, TeslaFi, local TeslaMate; a name from an input beats a `build_match` one. A typed name wins over both, and a cleared name stays cleared (no input or build match names it again). PATCH `{ version }` takes `2026.38.4` style versions, or null to forget a typed version; on a fingerprint update the version then also names every other update whose new fingerprint set is the same (`version_source: "build_match"`, `named_by: "auto"`; the one typed on is `version_source: "owner"`, `named_by: "owner"`). Clearing a name leaves that update without one even when its set is named elsewhere, and takes the name off the updates that had it from this one. A typed name (or a cleared one) stays with its update when later logs change it: one more changed field joining it gives it a new `id` and `build_id`, and so does an earlier update with the same changes going (a window cleared); the name moves with it. `named_by` and `between_ms` are null on the other updates, `changes` empty. `version_source`: `teslamate` / `teslafi` imported from that backup, `tesla_api` / `teslafi_api` / `teslamate_local` read by that live input (the Tesla API, TeslaFi, local TeslaMate), `owner` typed by an admin, `build_match` the same fingerprints as a named update; null with no version. `summary.current_version` (with `_source` and `_since_ms`; with `build_changed_since` set, `_since_ms` is when the last named version began, before the change, or null) is the car's whatever the period: the version typed on the newest update; else the live input's version when it read it after the newest update started; else the newest update's; else the car settings' typed version (`software_version_typed`). `summary.last_update` is the newest update whatever the period (null: none), so a page can say when the last one was when the period has none.
- **`/firmware`:** Tesla's version number is not on CAN, but the main modules broadcast fingerprints of their code about once a second on the vehicle bus (`can0`, or the interface the log's sidecar bus map names the vehicle bus): the front body controller (`vcfront`, 0x301 `VCFRONT_info`), the battery (`bms`, 0x300 `BMS_info`), the rear drive unit (`dir`, 0x335) and the front drive unit (`dif`, 0x656). Each is a multiplexed message (mux in byte 0, Intel order), decoded as raw integers: app and boot CRCs, git hashes, build type and configuration, the headlights' (`VCFRONT_hcmlAppCRC`, `VCFRONT_hcmrAppCRC`) and the oil pump's CRCs. `field` is the DBC's signal name; `hex` is lowercase, zero-padded to the field's width (`bits`): 14 digits for a 56-bit hash, 8 for a 32-bit CRC, 4 for a 16-bit configuration, 1 for a 3-bit build type (56-bit hashes do not fit a JS number: compare them as text, or with BigInt). Only the vehicle bus counts (gateway copies on the chassis bus are not read); zero (a field the module does not fill, e.g. the app git hashes of a 2026 Model Y) and SNA (every bit set) are not values; a value is taken only once it was seen 3 times within one awake span, so a corrupt frame never shows nor makes an update. `fields` lists the fields the car's logs carried, in the DBC's order; `first_seen_ms` of the current value is when it was first seen (after the update that brought it), `history` every value, oldest first. All four modules are always listed (empty `fields` for a car whose logs had none, e.g. an older Model S). `updated_ms` is when a fingerprint was last seen (null: none yet); `updates` counts the fingerprint updates. `bridge_hints` counts the bridge's `# firmware changed: ...` log lines (a hint only: the decode of the frames is what counts). Everything here is made again from the stored logs on a rebuild (old logs too); typed names are kept apart and survive it. Watch accounts read it for their cars.
- **`/firmware/history`:** rebuilt from the stored data like `/firmware`: one `kind: "module"` row per fingerprint a module had (`fingerprint` is its main field, the app CRC, as lowercase hex; `previous` the one before it, null for the first), from the fingerprint updates' old -> new per module. `id` is `<module>:<first_seen_ms>`; `fields` every field's value in that stretch, in the DBC's order; `until_ms` when the next one was first seen (null: `current`), `duration_ms` = `last_seen_ms - first_seen_ms`; `update` is the update marker it came with (`version`, `version_source` as on `/updates`, a name from a live input included; null for the first one seen) and `version` the same name; `changed_in` the first drive after the change and the log the new value was first seen in (null for the first fingerprint). **A module's first segment** has no update, so it is named only by what was said while it ran: an import's version row (its update row, which lasts until the next update row or the end of what that import covers) or a live input's readings (their first to last time) that overlap it, all the same version and with no update row of another version and no module build change inside it, name it outright (`version`, `version_source` `teslamate`, `teslafi`, `tesla_api`, `teslafi_api` or `teslamate_local`); a reading counts whether or not it is an update, and a later import row or reading of the same version counts too. Else, when the newest version said before it (an import or an input; it ended before the segment began) has no update row of another version and no module build change between its start and the segment's start, and nothing else is said inside the segment, `name_inferred` is `{ version, from: "last known before" }` and `version` stays null (an inference, never a name; a fingerprint seen again later under another name gets neither). Two versions said inside it, or an update with no version between, leave it unnamed (`version` and `name_inferred` null; pages say "no input reported a version name while this ran"). A name an admin typed on it wins (`version_source` `owner`). `version_source` is the update's for the other rows, `name_inferred` null on them. The current fingerprint of each module is the current `hex` of its main field in `/firmware`. The `version` of a fingerprint (in the rows and in `spans`) is the name its update shows however it was named (typed, from a live input, a build match), so it changes when the update is named later. Car versions without fingerprints are `kind: "version"` rows: imported (TeslaMate, TeslaFi) updates (`id` `version:<update id>`, `source` `teslamate` or `teslafi`), and the versions the live inputs read (`id` `version:live:<first_ms>`, `update` null, `source` and `update`-less `version` from that input: `tesla_api`, `teslafi_api` or `teslamate_local`; one row per stretch of a version, a reading of the version the row before says, with no fingerprint update between, joins it). `module`, `fingerprint`, `previous`, `changed_in` null, `fields` empty; `first_seen_ms` the update's start or the first reading; `until_ms` when a newer version started: the next version row, or an update found from fingerprints (the build changed), whichever is first; `current` (null `until_ms`) only while none came after it. `?module=` keeps that module's rows only (no version rows; anything else is 400 `bad_input` on `module`). Paged like every list (`limit` 1..500, default 50), newest first by `first_seen_ms` (ties by `id`). `modules` (always the four, in order, with how many `fingerprints` each had and its `current` one, null: never seen), `spans` (every module fingerprint, oldest first: the versions-over-time strip) and `range` (first and last fingerprint seen, null: none) are neither filtered nor paged. The answer has `car` and `time_zone`. Watch accounts read it for their cars.
- **Timeline update rows** also carry `version` and `version_source` (as `/updates`; `version` null when a fingerprint update is not named yet), and the text filter `q` matches the version. Update rows found from fingerprints also carry `detected_by: "fingerprint"` and `changed_modules` (both left out of every other row). `q` also matches the plain words for the codes, not only the codes: the kinds (`software update`, `gap in the data`, `charging` ...), the gap reasons (`no log arrived for this time`, `frames were dropped` ...) and the awake reasons (`someone in the car`, `sentry mode` ...), so a page's Find box finds a row by the words it shows.
- **`/cars/{car}/events`:** rows are `{ id, type, at_ms, topic, retained, payload }`, newest first; `payload` is exactly what MQTT would publish, in the server's units, with positions only when location publishing is on; its `car` is a number there (`"car": 7` for `c7`), and its `drive` or `charge` is the row's id as text, as everywhere in the API (`"drive": "6090227792"`): an imported row's id is over 2^53 and a JSON number that large loses digits in a browser, Home Assistant or Node-RED. An unknown `types` value gives `400`.

### Places

- **Matching** is live: a renamed, moved or removed place changes the name on every drive, charge, stop, timeline row, event and `now` at once. Of the places whose circle holds a point, the nearest centre wins (the lowest id on a tie). Filters by place use the same live match as the rows they filter (`places=` on drives and charges, `place=` on the timeline and on visits): a new place finds its drives at once, a removed one finds nothing. On drives, charges and the timeline an unknown place id gives `400`.
- **Costs stay put:** a charge keeps the cost it had when it ended. Changing a place's price changes only charges still going; `POST /places/{place}/reprice` applies the place's prices to past charges (each charge at the price of its own day) and answers `{ place, from_ms, to_ms, only_without_cost, dry_run, charges, repriced, unchanged, examples, cost_before, cost_after }`. A cost typed on a charge is never repriced. A past charge that had no cost (no place, or a place without a price) keeps having none when a place with a price is saved over it, until a reprice prices it.
- **Prices by date:** a place holds any number of prices, each from its first day (`from`, a date in the place's time zone, else the car's; `null`: from the start) until the next one of the same source starts, so a charge is costed at the price in force on the day it started, and a reprice (`POST /places/{place}/reprice`) takes each charge's price of its own day. `prices` lists them oldest first; `price` is the one in force today. `source: "typed"` is a price an admin gave; `source: "invoice"` is worked out by the server from Supercharger invoices matched to charges at the place (Tesla's charging history has no position, so a session is at the place of the charge it was matched to): the median price per kWh billed (`rateBase`) over the place's 10 most recent sessions, in their currency, from the day of the earliest of them at that price, with `invoice: { sessions }`; newer invoices that move the median add a price from their day on. A typed price always wins: an invoice price is used only on days no typed price covers, and is never written over one. The server works them out again by itself when it starts, when an input keeps new or changed sessions (the Tesla API's charging history, TeslaFi's charge costs), and when charges are rebuilt over the time of a session (the matches may move); the same sessions give the same prices. When a place's invoice prices change, its charges that have no cost get one (as a reprice of charges without a cost; a typed cost, an invoice's own cost and a typed place price still win); kept costs stay put. Each change is in the audit log as `place-invoice-priced` (by the server, target `place:<id>`), with the price, its first day and how many sessions it is the median of. Each entry's `price` is any price the API takes (one price, time-of-use rates, a session fee, …): the date sits beside it. **Writes:** `prices: [{ from, price }]` replaces the typed prices (at most 50; `from` a real date or `null`, two prices may not start on the same day; field errors are named `prices.N.from`, `prices.N.price.per_kwh`, …); entries sent with `source: "invoice"` are the server's and left as they are. `price` alone (the older way) replaces the typed price in force today (one from the start when there is none) and keeps the others; `price: null` takes every typed price off. Sending both is `400` on `prices`. A place saved before prices had dates has its one price from the start.
- **Free Supercharging:** a DC charge that starts on a day of the car's `free_supercharging` ranges (days in the car's time zone) costs `0` with `source: "free_supercharging"`, whatever cost was kept for it, unless a cost was typed on it. The charger's name is not decoded yet, so every DC charge counts, except one at a saved place with a typed price whose name does not say Supercharger (a price from invoices does not count). The zero is in that place's currency, else the first priced place's; with no priced place at all the charge has no cost.
- **Writes:** POST needs `name`, `lat`, `lon`; `kind` defaults to `other`, `radius_m` to 100 (10 to 5000), `time_zone` to the nearest known place's. PATCH needs `version` and sends only what changes. DELETE takes an optional `?version=`. Create, change and delete answer the place (or `{ deleted, id }`) plus `effect`: the same counts as the preview. `price.rates[].days` is `all`, `mon-fri` or `sat,sun` style; `from` and `to` are `HH:MM` (`24:00` ends the day). A price needs at least one of `per_kwh`, `per_minute`, a rate or `session_fee`; send `price: null` for none. Each rate needs `per_kwh` or `per_minute` (422 on `price.rates.N.per_kwh`), and rates that leave some hours of the week out need the price's own `per_kwh` or `per_minute` for those hours (422 on `price.per_kwh`), so no hour is priced as free.
- **Tiered prices** (`price.tiers`, block prices as some power companies bill them: say up to 1,000 kWh a month at 0.16, 1,000 to 2,000 at 0.10, above 2,000 at 0.05): `steps` are 1 to 8 `{ from_kwh, per_kwh }` in the place's currency, the first from `0`, each next higher (up to 1,000,000 kWh), prices 0 to 10; `cycle_day` is the day of the month a billing cycle starts at midnight in the place's time zone, `1` (the calendar month, the default) to `28`; `base_kwh` (default `0`) is the household's own use per cycle, counted first, for a meter that also counts the house (the car's kWh then start in a higher step). Tiers take the place of `per_kwh` (send one or the other: 422 on `price.per_kwh`); field errors are on `price.tiers.steps.N.from_kwh`, `price.tiers.steps.N.per_kwh`, `price.tiers.cycle_day` and `price.tiers.base_kwh`. A charge's kWh follow on from the cycle's total before it: `base_kwh` plus the kWh of the charges at the place that started earlier in the cycle (every car's, the rows shown, each its grid energy, else what went into the pack; two that start at the same moment go by car, then id). Its energy is walked in time order and split where it crosses a step, each part at its step's price. A time-of-use rate still sets the price for its hours (its kWh count toward the steps all the same); the steps price every other hour. The session fee and a price per minute are added as without tiers. The breakdown's step parts are named `Step N` with their range (`from_kwh`, `to_kwh`, null for the last), and `cycle` says which cycle and how many kWh came before (`before_kwh`, the household's use included); `cycle` is null without tiers. As with every price, the cost is kept when the charge ends: a later price change, or an earlier charge rebuilt, reaches it only through a reprice (which compares amounts: a charge whose amount comes out the same keeps its kept breakdown). The place keeps one set of steps (no price history by date): to bill past cycles at old steps, reprice only the span the new steps apply to.
- **`/places/preview`** takes a draft place (with `id` to preview an edit) or `{ place, delete: true }` and answers `{ drives_named, drives_unnamed, charges_named, charges_unnamed, drives_taken, charges_taken, taken_from, charges_repriced, examples, place, delete }`. `charges_repriced` counts the past charges a reprice after saving would change. `drives_taken` and `charges_taken` count the drives and charges that move from another place to this one (they are part of the named counts), and `taken_from: [{ place: { id, name }, drives, charges }]` names those places, most taken first; create, change and delete answer the same in `effect`. A draft of a new place counts as newer than every saved place, so it loses a tie (the same distance to two centres) to the older place, as it will once saved. The counts cover only drives and charges that move between places: a rename alone moves nothing, and every drive and charge that stays at the place (its `counts`) shows the new name. `example_rows` (up to 8, also in the `effect` of create, change and delete) says what each example is: `{ kind: "drive" | "charge", id, car, start_ms, change: "named" | "unnamed" | "repriced" }`, so a page can link to it. It changes nothing and may be used by any account; a watch account may name only places its cars have used (others are `422` on `place` or `id`, as if there were no such place).
- **Lists:** `sort` is `name` (default), `visits`, `last_visit` or `created`; `total` is sent. Places also carry `address` and `created_ms`.
- **`/places/suggestions`:** `{ items: [{ lat, lon, radius_m, visits, dwell_ms, cars, label, address, last_visit_ms, kind }], next: null }`, where no saved place is, most visited first. **`/places/at`:** `{ lat, lon, place: Place | null, candidates: [{ id, name, kind, distance_m, radius_m }], rule: "nearest_centre", address }`.

### Integrations

- **`settings/mqtt`:** PUT sends the whole setting with `version`; leave out `password` to keep it, send null to remove it. The kept password goes only to the broker it was typed for: a PUT that changes `host`, `port`, `tls` or `pin_sha256` while a password is saved must send `password` again (or null), else `422` on `password`, so an admin session can't send the saved login to a broker of its own. GET gives `password: null` and `password_set`. Rules (422): a password needs `tls`; a `pin_sha256` (64 hex digits, colons allowed) needs `tls`; `namespace` and `ha_discovery.prefix` take no `+`, `#`, leading `$` or empty level; `ha_discovery.url` is `https://` or null.
- **`settings/mqtt/status`** adds `enabled`, `broker` and `tls`. **`/preview`** (`car` defaults to the first car the account sees) adds `car`, `name`, `units`, `device`, and each entity's `state_topic` and `config_topic`; a value the car did not send is not published, and position topics are empty while location publishing is off. **`/test`** takes no body (it uses the saved settings) and answers `{ ok, error, message, latency_ms, at_ms }`; `error` is `no_host`, `connection_refused` or `pin_mismatch`. `last_error` in `/status` is always such a code (also `auth_failed`, `tls_failed`, `timeout`, `invalid_settings`), whether a test or the running publisher failed; `last_error_message` says it in words.
- **MQTT topics** name a car by its API id: `<namespace>/cars/c7/soc`, `<namespace>/cars/c7/event`, Home Assistant device `<namespace>_c7`. One retained topic per value, as text in the server's units (`true`/`false` for on/off values): `state`, `driving`, `charging`, `place`, `latitude`, `longitude`, `location`, `gear`, `in_park`, `speed`, `power`, `heading` (while driving), `elevation`, `odometer`, `soc`, `soc_usable`, `range`, `range_ideal`, `range_estimated`, `energy_remaining`, `battery_temp`, `inside_temp`, `outside_temp`, `lv_voltage`, `tire_pressure_fl`/`_fr`/`_rl`/`_rr`, `tire_low`; the build: `paint`, `wheels`, `spoiler`, `roof`; modes: `sentry_mode`, `service_mode`, `display_mode` (`off`, `on`, `sentry`, `dog`, `camp`), `installing`, `healthy`; openings and people: `doors_open`, `door_front_left`, `door_front_right`, `door_rear_left`, `door_rear_right`, `trunk_open`, `frunk_open`, `user_present`; climate: `climate_on`, `preconditioning_cabin`, `preconditioning_battery`; charging: `plugged_in`, `charge_status` (`disconnected`, `no_power`, `about_to_charge`, `charging`, `complete`, `stopped`), `charge_kind`, `charge_power`, `charge_limit`, `charge_port_open`, `charge_energy_added` (the pack's lifetime charge counter in kWh, `total_increasing` in Home Assistant), and while charging `charger_current`, `charger_voltage`, `charger_phases`, `charge_current_request`, `charge_current_limit`, `time_to_full` (min); navigation: `navigating`, `energy_at_destination` (kWh, only while navigating); and `updated`. Home Assistant discovery gives each a `sensor`, or a `binary_sensor` for the true/false ones. From the API inputs (the Tesla API, TeslaFi's API, local TeslaMate; see `off_can` above), for what CAN does not carry: `version`, `update_available`, `update_version`, `update_download` (%), `locked` (Home Assistant's lock entity), `windows_open`, `window_driver_front`, `window_passenger_front`, `window_driver_rear`, `window_passenger_rear`, `sunroof_state`, `sunroof_open` (%), `scheduled_charge_start`, `scheduled_departure` (ISO 8601 UTC), `route_destination`, `route_distance`, `route_minutes`, `route_traffic_delay` (min); `installing` is CAN's word, else the inputs'. A value gone stale, or published and no longer known (`energy_at_destination` once the route ended, the while-charging values once the car stops sending them), is published empty, which clears the broker's copy (Home Assistant shows it unknown). Also `since` (when the car's state began, ISO 8601 UTC) and `trim`. The VIN is never published. Drive and charge events go out once each as the server records them (an end once the car's data goes on past it); a save that turns Home Assistant discovery off, or changes `namespace` or `ha_discovery.prefix`, first clears from the broker what the old layout left (its discovery configs, and with a new namespace its retained values).
- **`/network`:** `inbound` rows also carry `tls`. Geocoding is listed but off while address lookup is offline. `release_check` is `api.github.com`, `enabled` with the setting, `last_used_ms` the last request to it. The Tesla API input adds one `tesla` row per Tesla host the accounts use (`enabled` while one is read), or one row for `owner-api.teslamotors.com`, off, when there is no account.
- **Tesla accounts (`/integrations/tesla`):** two ways to add one. **Sign in at Tesla:** `POST /integrations/tesla/sign-in` gives the address of Tesla's sign-in page; the admin opens it, signs in there (Tesla's own page asks for the password, the two-step code and any captcha: this server never sees them), and the browser ends on an address that does not load (`tesla://auth/callback?code=...`, or `https://auth.tesla.com/void/callback?code=...` with `redirect: "void"`). The admin copies that whole address into the page, which sends it as `pasted_url`. A sign-in lasts ten minutes and is used once; at most five are open at a time (`409 too_many_sign_ins`). **A refresh token** from another tool: `POST /integrations/tesla/accounts`. Either way the server checks it with Tesla before anything is kept: `422 tesla_refused` when Tesla says no, `502 tesla_unreachable` when Tesla can't be reached, `409 account_exists` when the same cars are on another account here. `422 invalid` on `pasted_url` when it is not Tesla's callback address or belongs to another sign-in; `404 no_such_sign_in` when it ran out or was used.
- **Tesla cars:** a new account's cars are not read until an admin matches them (`PUT .../cars`): to a car here (`suggested` names the one with the same VIN prefix), to a new car, or left out. `409 car_taken` when the car is matched to a vehicle of another account. `region: "china"` uses Tesla's China hosts (no streaming there). `location` says when the car's position is asked for: while it drives or charges (the default; the car shows a "location shared" icon while it is asked), always, or never.
- **How often (`poll`):** a driving car's `vehicle_data` every 2.5 s with Tesla's live stream beside it (`driving_ms`, from 2.5 s to 10 min), a charging car every 5 s (`charging_ms`, 5 s to 30 min), an awake car with nothing going on every 60 s (`idle_ms`, 60 s to 60 min), and an asleep or offline car only the list of cars every 30 s (`list_ms`, 30 s to 60 min; the list never wakes a car, and `vehicle_data` is asked again only once it says online). Each default is also the fastest: a value can be made slower, never faster. An awake car with nothing going on is left alone for 21 minutes after 10 quiet minutes so it can fall asleep (only the list is read meanwhile). The pace never slows because SMO is live for the car: the Tesla API keeps reading (and streaming while it drives). Settings saved by an older server with a pace word read as the defaults, `gentle` as driving every 60 s, charging every 2 min, idle every 5 min and the list every 2 min (a `daily_cap` saved with them is ignored).
- **Tesla does the limiting:** this server sets no limit of its own: no daily cap and no gap between requests beyond the intervals above (requests go one at a time per account; the invoices have no cap either). When Tesla answers 429 the account waits as Tesla asks (`Retry-After`, else `RateLimit-Reset`; at least 60 s, 5 minutes with neither, at most 24 h), the wait is kept across restarts, and the user is told: each new wait (a 429 after the last one ended) writes the audit entry `tesla-rate-limited` in the server's name (its summary: "Tesla is limiting requests for the Tesla account …, next try at …") and sends the notice `tesla_rate_limited` on the event stream; while it lasts `/notices` lists it (admins only, `level: "warning"`, `message` "Tesla is limiting requests for the Tesla account "…", next try at <time> UTC. …", `since_ms` the 429, `fix_link: "/settings/integrations#tesla"`, `detail: { account, until_ms }`), the account, the input and its status rows carry `rate_limited_until_ms`, and its `/integrations/connections` row is `problem` with `status_reason: "rate_limited"` and `next_ms` the next try.
- **Tesla status words:** an account's `status` is `checking` (just added), `ok`, `paused`, `sign_in_needed` (Tesla stopped taking its token: sign in again or PATCH a new `refresh_token`; nothing is asked of Tesla meanwhile) or `error` (see `last_error`). A car's `mode`: `off` (not matched, left out, or the account paused), `watching_list` (asleep or offline: only the car list is read), `online_idle`, `letting_sleep`, `charging`, `driving`, `backoff` (Tesla answered with errors, or Tesla is limiting requests (429): nothing is asked until `next_poll_ms`; after 5xx and network errors it waits longer each time, up to 15 minutes, after a 403 an hour). An account's `running` is true while the server keeps a task for it, paused or not.
- **Tesla notices and audit:** `/notices` adds, for admins only, `tesla_sign_in_needed` and `tesla_account_error` (`detail: { account }`), and the server writes an audit entry in its own name when an account turns to either; `tesla_rate_limited` (above, "Tesla does the limiting"). Audit actions: `tesla-account-added`, `tesla-account-removed`, `tesla-account-paused`, `tesla-account-resumed`, `tesla-account-changed`, `tesla-token-replaced`, `tesla-car-matched`, `tesla-poll-changed`, `tesla-sign-in-needed`, `tesla-account-error`, `tesla-rate-limited`. No answer, audit entry or log line holds a Tesla token, a VIN serial or the account's e-mail.

### Server, settings and health

- **`/settings`:** PATCH with `version` sends only the parts that change (`{ units: { pressure: "psi" } }` keeps the other units). Units, range and car order are the defaults of everyone's preferences: a change pushes a `prefs` event to each person, and a person's own choices stay. `release_check.enabled` (default `false`) saves: turning it on checks at once (in the background) and then once a day; turning it off stops it and drops the result (see "Release check" below). `host_names: []` means the running certificate's names (what GET answers then); IPv6 addresses are names too.
- **`/notices`:** `certificate_expiring` carries `detail: { expires_ms, days }`. `release_available` (admins only, while the check is on and its status is `newer`; `level: "info"`, `since_ms` the newest image's date, `fix_link: "/help#about"`, message `A newer build is ready: build 57, Nov 24, 4 changes.`: the run number, never the commit) carries `detail: { version, commit, build, changes, notes_url }`: `version` the short commit, `build` that image's run number (null when unknown), `notes_url` the comparison on github.com; pages link to it only while `settings.outside_links.release_notes` is on. A pack hides it per browser by `detail.commit`, so a later newer build shows again. **`/maps/config`** and **`/geocode/status`** follow `/settings` at once.
- **`/about` `build`:** this build, baked in when it was compiled: `number` the Image workflow's run (the image tag `build-<n>`), `commit` the full sha, `short` its first 7, `built_ms` the build date. A local build has `dev: true` and the other three null. Show it by its number, as `0.1.0 · build 41 · Nov 22` (the date as "Mon D", with the year when not this year; `buildLabel` in `ui/shared/release.js`), the commit only in a hover title (`commit 2f44a52`, `buildTitle`); a build with no number (a local one) as `0.1.0 · dev build`. A newer build is named the same way: `A newer build is ready: build 42, Nov 22, 1 change` (`newestText`; without a run number only the date and the count), its commit in a hover title and the change list.
- **Release check (`/release`):** off by default (`/settings` `release_check.enabled`, admins). While on it checks at once, then 24 hours after the last check (later when GitHub's rate limit said to wait: `next_ms`). It asks GitHub's API (`api.github.com`, through `outbound.proxy`) for the newest successful Image run on `main`, then compares this build's commit with it (docs/security.md says what is sent). `status`: `off` (`newest` and `error` null), `never` (on, not checked yet), `checking`, `up_to_date` (the newest image is this build, or older; `newest` filled, `changes: 0`), `newer` (`newest` has commits this build lacks: `changes` the count, `titles` up to 50 commit titles, oldest first, `more` the rest), `error` (`error.code`: `rate_limited`, `unreachable`, `http`, `bad_answer`, `dev_build` (a local build, nothing to compare, nothing asked), `proxy`, `tls`, `timeout`; the last `newest` is kept). `checked_ms` is when the last check ended, whatever its result. `POST /release/check` checks now (at most one at a time: during one it answers `checking`; while the rate limit says wait it answers `error` `rate_limited` without asking). `pull` is the command to show beside a newer build (`docker compose pull && docker compose up -d`) and `image` the image (`ghcr.io/skittles-fivem/sentry-mate:latest`): the server never pulls, downloads or installs anything. Nothing is kept on disk; a restart checks again.
- **`/about`:** also carries `links: { source, docs }` (each an address or null) and `licence: { name, url }`, Sentry Mate's own licence: `name` null while the project has not chosen one, `url` its full text (null when the server gives none).
- **`/cars/{car}/health`:** `from_ms` defaults to 30 days back. `reasons` codes: `upload_silence` (nothing new for a day; a car that never uploaded is silent too, except one with no CAN Bridge key and no upload token whose history is an import's or an API's: no upload is expected of it, here and in `/fleet/attention`), `trust_failed`, `logs_waiting_trust`, `rebuild_pending`, `logs_missing`, `gps_inputs_disagree` (in the car's last 30 days of history one live input's GPS fixes were far from another's at the same moments and agreed with none; `gps_disagreement` says which: `disagree` and `not_used` input words, `from_ms`/`to_ms` the newest such stretch rebuilt since the server started, null when none). Where an input's fixes are `not_used`, positions there come from the other inputs (SMO's decoded position gives way to an API's, which reports the car's own). The live position follows the same word: while the newest rebuild that compared SMO's fixes with an API's left them out (or, before any has, SMO's newest fix is further from an API's of about the same time than the car can be), `/cars/{car}/now`'s `location`, its `place`, the fleet's place, MQTT's position topics and the `now` events take the freshest position an API reported (its `at_ms` and `sources` say when and which), or none; a rebuild that finds SMO's fixes agreeing again (its GPS layout put right) uses them again. `missing_logs` ("Missing on the server", over the car's keys, from the server's scan at start-up and once a day: [cars-and-bridge.md](cars-and-bridge.md#did-each-log-arrive-intact)): `count` the logs and sidecars the server should have but no longer does and asks the car for (`logs_missing` while above 0), `oldest_ms` the start (from its name) of the oldest of those, `found_ms` when the first was found missing, `asked` / `asked_ms` whether and since when the car is asked to send them again (its pings list them in `wanted`), `gone` those the car says it no longer has either (lost for good: their time stays unknown time), `gone_oldest_ms` the oldest of those, `scanned_ms` the last scan (null before the first). `log_checks`: every log of the car's keys (all time, not the period) as the CAN Bridge app is told it now (the `check` and `check_reason` of the upload API's status call, [cars-and-bridge.md](cars-and-bridge.md#did-each-log-arrive-intact)), counted: `verified`, `pending`, `failed` and the failed ones per `check_reason`; `failed_runs` the runs of failed logs one after another, oldest first, each with the start (from its name) of its first and last log, how many logs and how many per reason (at most the newest 200; `runs_total` counts them all). The same as `sentry-mate log-checks --car`. `last_log_trust` adds `log_start_ms`; keys add `preferred`, `device` (the admin's name for the key, null while unnamed), `device_label` (that name, else the automatic label; see `/can-keys`) and `logs_waiting`; `unknown_spans` are `[{ start_ms, end_ms, reason }]` (`end_ms` null while still unknown; `reason` is the timeline's word, as `gap_reason` of `/gaps`: `no_log`, `not_recorded`, `failed_check`, `unreadable`, `other_vin` or `dropped_frames`), with their total in `unknown_ms`. `last_upload_ms` (the car's, and each key's) is the CAN Bridge's last contact: its last request the upload server accepted (a ping, a status question or an upload chunk with its token; the newest of the car's keys'), so it shows a bridge that is online whatever the server is still working through; when no contact is known (none since this was added) it is when the newest log arrived. `newest_log_ms` (the car's, and each key's) is when the newest log arrived whole, not the time in its name nor when the server worked on it (null when not known). `chain_gaps`, `dropped_frames` and `unknown_spans` each hold at most the newest 500 of the period; `chain_gaps_total`, `dropped_frames_total` and `unknown_spans_total` count them all (`unknown_ms` too is of them all).
- **What starts a rebuild**, how far each reaches and why none fires twice: [`docs/rebuilds.md`](rebuilds.md). A car's GPS layout change reads its positions again (only the logs whose positions came from the Screenmate's own GPS frames are decoded again), a source order change joins its inputs again (nothing decoded again); a rebuild a saved setting asks for waits 3 s, so saves in a row are one.
- **`/rebuild`** takes `from_ms` and `to_ms` up to 4102444800000 (2100-01-01; later is `422 invalid`) and answers `{ car, job, status: "done", from_ms, to_ms, kinds, logs_read, logs_total, took_ms }` and pushes a `rows` event; `rebuild_pending` stays true for a few seconds after. `409 full_rebuild_running` while a full rebuild runs. The request waits for the job for up to 60 s; a job that takes longer is answered `status: "running"` (`logs_read` of `logs_total` so far, `took_ms` null) and carries on: the car's `rebuild_pending` (`/cars/{car}/health`, the `health` event) says when it is done, and `rows` events come as its windows are made. A job that was cancelled is `status: "cancelled"`. One that failed is `500 rebuild_failed` with why in the message (a stored log that can no longer be read: what it held was cleared and is not made again; a damaged table of the car), and the admins get the notice `rebuild_failed` (`level: "warning"`, `detail: { car, job, kind }`, `fix_link: "/settings/server"`) until a later rebuild of the car ends well or the server starts again. The audit entry `car-rebuild` is written when the job ends, by how it ended ("Rebuilt …", "The rebuild of … failed: …", "… was cancelled") and for the period asked for (`the whole history`, `everything up to 2026-11-20 UTC`, `everything from 2026-11-19 UTC on`, `2 days from 2026-11-19 UTC`), also when the request went away meanwhile or stopped waiting. A day of the samples decoded from the logs that no longer opens is set aside and made again by the rebuild (its window widened over that day); see [`docs/rebuilds.md`](rebuilds.md).
- **Damaged files (`data_damaged`):** a file of a car's history that no longer opens (a disk fault, a copy cut short) is never read as empty: what needs it answers `500 server_error`. The first time anything meets one, the admins get the notice `data_damaged` (`level: "error"`, `fix_link: "/settings/server"`, `detail: { files: [{ car, file, why, since_ms, mend: "rebuild" | "backup" }] }`, `file` the path under the data folder) while the file is there: `mend: "rebuild"` for the samples and charge points decoded from the stored logs (a rebuild of the car makes them again), `backup` for a table or an import's or an API's series, which also hold what no log gives (imported rows, typed costs and purposes): no rebuild, full or not, replaces those by itself, and the message says to put the car's folder back from a backup with the server stopped.
- **Full rebuild (`/cars/{car}/full-rebuild`, `/system/full-rebuild`):** for when the history is wrong and the server will not mend it by itself (a decoder fixed, rules changed). It throws away everything worked out for one car or every car and makes it again from the raw inputs the server keeps: every stored CAN log decoded again with the server's DBC sets and decoder (samples, positions, charge points, firmware fingerprints), the Tesla API's, TeslaFi's and local TeslaMate's stored data fused in again, then the timeline (states, drives, charges, visits, updates found from fingerprints), the pack's day readings (battery and efficiency figures) and every kept working value of the car (the long periods' day parts, charge fills, the vehicle's build days) dropped, so nothing stale is answered; places are matched and statistics worked out from the new rows as they are read. Imports are kept as the rows they left (an import's source file is not kept). It never deletes or changes the raw inputs (CAN logs, sidecars, signatures and trust records, the APIs' stored data, imported rows) nor what an owner entered (charge costs, places and their prices, typed versions and firmware names, drive purposes, car settings and record, overlap choices, sold status, source order). The new history is built beside the old one (a folder `.full-rebuild` in the data folder, never carried by a move or an export; about as much disk as the car's history without its CAN samples, for a while) and each car is switched to it at once when it is done: pages read the old history until then (new logs keep coming into it and are decoded again after the switch), and a failure, a cancel or a crash before the switch leaves it as it was. One at a time, one car after another: an ask while one runs joins it (its cars added). A restart carries on where it was; one after an update that changed the decoding again takes the cars now out of date into the same run. The POST asks for the admin's own password again (`confirm_password`, and `code` with two-step sign-in; `403 password_needed`, `403 wrong_password`, `401 wrong_code`; only over HTTPS, as every request). Status: `state` is `idle` when none ever ran; `phase` the step of the car under way (`car`): `copying` its raw inputs beside its history, `decoding` its logs (`logs`, `bytes`: added up over the cars, each counted as it starts; `bytes.copied` what was copied for the car under way), `days` its pack readings (`days`), `switching`. `rate_bytes_per_s` and `eta_ms` (null until known) are of the phase under way; `last_progress_ms` when it last moved on, `stalled` true after two minutes without progress. `errors` (at most 50): logs that could not be worked on (each says why: mostly a stored file the server can no longer read), days whose readings failed, and why the job failed; `error` is that why. `logs.failed` counts every such log, also past the 50 listed, and `logs.done` and `logs.total` count every log of the cars, the ones decoded before a restart too (the rates are of the logs decoded since). A log that reads but does not decode, or that failed its check, is no error: it is left out as in any history. A log the history in use was made from that can no longer be read (its stored file or day pack is damaged) fails the full rebuild instead, with the log's name in `error`: the old history still has what the log held, a new one would not, so the old one is kept; a log that could not be read before either is only listed. `by` the admin who asked (null for one the server started). `version`: `server` the decoding this server makes histories with (`decode-3.rules-1.dbc-614c9494`), `stale_cars` the cars whose history was made with another (or before versions were kept), `auto` the setting. A new server version that decodes stored data differently finds those cars at its start: their logs are not decoded again in place for that alone, and with `full_rebuild.auto` on (the default) a full rebuild of them is planned once for that version (`reason: "version"`, `hold.kind: "grace"`, the notice `full_rebuild_planned`) and starts by itself 10 minutes later unless an admin starts it now, puts it off until tonight or pauses it (PATCH); a plain restart plans nothing, and one that failed or was cancelled is offered again, never retried by itself. Off, the notice `full_rebuild_offered` (warning) offers it. `full_rebuild_failed` (warning) shows after a failed one until the next one ends well. Each links to `/settings/server#full-rebuild`. The audit log has `car-full-rebuild` when one starts, ends, fails or is cancelled. Live: a `rows` event of every kind over all time for each car switched.
- **`/overlaps`:** two kinds of rows, newest first. `kind: "live"`, `id: "overlap:<start_ms>"`: a span of live history (SMO's or the Tesla API's states that are not unknown) holding imported drives or charges. `kind: "imports"`, `id: "imports:<start_ms>"`: a span where both import sites have history (their states, drives and charges cover the same time, widened over the drives and charges that reach into it; a drive or charge of one poll, which ends where it starts, still covers its moment, and a hole of under two hours in one site's history, such as TeslaFi leaving the car to fall asleep, counts as covered) and each has a row starting in it; it may hold live history too, which still wins there. Rows are `{ id, kind, start_ms, end_ms, shown_source, default_source, default_reason, live: { drives, charges }, imported: { drives, charges }, sites: { teslamate: { drives, charges }, teslafi: { drives, charges } }, sources, version, shown, can: { drives, charges }, teslamate: { drives, charges } }` (`shown`, `can` and `teslamate` are the old names, kept for one release; on an `imports` row `shown` is `teslamate`, the imported side). `imported` (and the old `teslamate`) counts each real drive and charge once, as the lists show them: where both imports cover the time, only the shown site's rows (on an `imports` row the site `shown_source` names, on a `live` row the site its `imports` span shows); `sites` has each site's own counts. A choice belongs to the time it covers, not to its start: a later import that moves a span's start (and with it its id) keeps the choice made for it. `default_source` is what the span shows when no one chose (`live`, or on an `imports` row the bigger import) and `default_reason` why that import: `more_drives_and_charges`, `more_samples` (the same drives and charges, more positions), or `tie` (TeslaMate's, the older format most owners came from); null on a `live` row. `version` is the car's overlap choices' version (every row carries the same; any flip moves it on). PATCH `{ id, shown, version }`: of a `live` span `shown` is `live` or `import` (also spelt `import:teslamate`, `import:teslafi`: the imported side, whose site in an `imports` span is that span's choice), or the old `can` or `teslamate`, and `version` may be left out; of an `imports` span `shown` is `import:teslamate` or `import:teslafi` (`live` is `422 invalid`) and `version` is required (`400` without it). A stale `version` is `409 stale_version` with the current one. The flip is in the audit log (`car-overlap`); Drives, Charges, Timeline, Statistics, Series and Travel then show that side for the span. It answers the list plus `changed`.
- **Storage:** `/cars/{car}/storage` answers `{ kinds: [{ kind, label, bytes }], total_bytes, items: [{ series, source, date, bytes }], next }`, newest day first, only days with data; `kinds=logs,series,curves,rows` filters the days. `from_ms` and `to_ms` filter them too (a log by its start, a stored day when it meets the period; the per-kind bytes stay the whole history's). A log's `date` is the car's own day; series and curves are stored per UTC day, so their rows carry that UTC date. `/system/storage` is the sum of the cars (imported history apart), plus offline map tiles; TeslaMate backups uploaded to an import are their own kind, `import_uploads`, not the server's `server` (accounts, settings and places); `growth` is the last 30 full days (only days with new data are listed), `growth_per_day_bytes` their sum over the days from the first one listed to today (at most 30: days without new data count too), and `full_in_days` is free space over that. `/system/storage/detail` says where the space on disk goes: `categories`, largest `disk_bytes` first, each with a stable `key` (`logs.raw`, `logs.sidecars`, `logs.packs`, `logs.ledger`, `series.can.snapshots`, `curves.can.snapshots`, `rows.snapshots`, `kv.engine`, `kv.day-parts`, `imports.uploads`, `server.accounts`, `server.tiles`, ...), a `group` (`logs`, `series`, `rows`, `kv`, `imports` or `server`), a `label` in plain words, its `files`, their `bytes` and what they take on disk (`disk_bytes`, whole blocks); `total_bytes` and `total_disk_bytes` are their sums and `free_bytes` may be null. `compaction` is the packing of data that is no longer written: lossless (every value stays readable exactly), and the logs' signed originals are kept byte for byte inside the day packs. It runs by itself while the server is idle (`automatic`), and `POST /system/storage/compact` starts a pass at once. `status` is `idle`, `running` or `failed` (`error` then says why, else null); while running `step` is `logs`, `series`, `records` or `imports` (the uploaded backups of finished imports, packed where they are plain text; else null), `step_number` its place of `steps` (the engine's three, then `imports`: 4 on a server), and `phase` `counting` (the step is finding out what it has to do: `total` is 0 until it knows) or `packing`; `done` of `total` count its progress in `unit`s (`days`: a car's day of logs, or a day of a car's series; `records`; `files`: uploaded backups). `pass_saved_bytes` is what the pass under way freed on disk so far, `rate_per_s` the units a second of this step since it knew its total (null before its first unit) and `eta_ms` the time this step still needs at that rate (null while counting), `progress_ms` when its last unit finished (or the step began), and `stalled` true once no unit finished for 2 minutes (a unit takes seconds: the server is very busy, or the pass is stuck). All of these are null when no pass runs (`stalled` false; `steps` is always given). `unit_errors` counts the units of the pass under way (else of the last pass) that could not be packed and were left exactly as they were, `last_unit_error` says why the last one could not (else null); a pass with such units still ends `idle`, and the next pass tries them again. `started_ms`, `finished_ms` and `last_saved_bytes` (what the last pass freed on disk; 0 when nothing was left to pack) are null before the first pass; `saved_bytes` is what every pass freed together. A page reads the detail again every 2 s while a pass runs.

### Import

- **Upload:** POST `{ name, bytes_total, compression? }` (or an `Upload-Length` header) answers 201 with the import, `upload_url` and `chunk_max_bytes` (just under 1 MB). Each PATCH body is the next chunk (`Content-Type: application/offset+octet-stream`) with `Upload-Offset`, `Upload-Length` and `Upload-SHA256` (hex or base64). A wrong offset gives `409 wrong_offset` with the offset to send from; a chunk that does not match its SHA-256 gives `422 checksum_mismatch`. One import at a time: another POST while one is unfinished gives `409 import_running`. A chunk that is stored (here and in a restore) gives back the request it took from the address's request rate, so a big file sent quickly is not slowed to the rate's pace; a refused chunk counts.
- **Several files:** POST `{ files: [{ name, bytes_total }, ...] }` (1 to 500 files, each 1 byte to 64 GB) makes one import of them all. Every import has `files: [{ index, name, bytes_total, uploaded_bytes, upload_url }]` (`upload_url`: `/api/v1/imports/{import}/files/{index}`), and the create's `upload_url` is file 0's; the import's own PATCH is file 0. Each file's chunks go to its own address with that file's `Upload-Offset` and `Upload-Length`; different files may be sent at the same time. The import's `name` is the first file's plus " and N more files", `bytes_total` and `uploaded_bytes` the sums. Once every file is complete it goes to `checking`. Several files are taken for TeslaFi's data only (one check, one car matching, one report, with `report.uploads: [{ name, compression, packed_bytes, unpacked_bytes, files, files_skipped, rows_read, rows_used, rows_skipped }]` one per file in order); several files that are a TeslaMate backup or a CAN export fail the check with `one_file_only`, a file among TeslaFi ones that is not TeslaFi's with `not_a_teslafi_export` naming it. A page resuming after a reload matches its files to `files` by name and `bytes_total` and continues each from its `uploaded_bytes`.
- **Status** moves `uploading` -> `checking` (pass 1) -> `ready` -> `importing` (pass 2) -> `done`, or `failed` with `error`. `ready` means checked and waiting for the cars to be matched and the import started. While checking or importing, `bytes_read` grows. Answers also carry `id`, `name`, `compression`, `uploaded_bytes`, `started_ms`, `checked_ms`, `finished_ms` and `cars_to_match`.
- **Cars:** GET `/imports/{import}/cars` answers `{ import, items: [{ tm_car, name, vin_prefix, drives, charges, first_ms, last_ms, match, suggested }], next }` once the whole file is uploaded (`409 not_checked` before). A car here with the same VIN prefix is suggested and matched at first, unless that car is suggested for another car of the backup too (cars of the same model, year and plant share the prefix): then none of them is. PUT `{ items: [{ tm_car, match }] }` changes only the cars it names; one car here takes at most one imported car.
- **Which car (whole VINs):** a car keeps a keyed hash of each whole VIN an import brought it (never the VIN or its
  serial), so cars of the same model, year and plant (the same VIN prefix) are told apart: an imported car goes to the
  car here with its whole VIN, else to the one car with its prefix whose whole VIN is not known to be another; a prefix
  alone never matches a car whose whole VIN differs.
- **Moves and rows that need a car:** every import has `moves: [{ kind: "rehomed" \| "assigned", at_ms, from_car,
  from_name, to_car, to_name, hold, rows, drives, charges, owner_entries, first_ms, last_ms }]` (rows of it moved
  from one car to another, or to wait for a car: `to_car` null and `hold` its id) and `needs_car: [ImportHold]` (its
  rows that wait for a car, or waited). `ImportHold` is `{ hold: "h1", import, tm_car, name, source, status:
  "waiting" \| "ignored" \| "assigned", why: "no_vin" \| "odometer", from_car, to_car, rows, drives, charges, first_ms,
  last_ms, odometer_km: [first, last] \| null }`. A move takes what the owner entered on the rows with them (a
  charge's cost, a drive's purpose and note); nothing is deleted, `ignore` keeps the rows aside and they can still be
  given a car. Each move is an audit entry (`import-rows-moved`; `import-rows-ignored` for ignore and wait), and the
  cars that lost or got rows are rebuilt. Once after an update, the server reads each done TeslaFi import's kept files
  again with this matching (nothing is read into a car) and moves the rows an older server put on the wrong car
  (`kind: "rehomed"`): to the one car of their name whose own history their odometer and time fit, else to wait for
  a car. Without an import's files, a car's imported drives whose odometer reads above the car's own later drives
  (three or more in a row) are moved to wait for a car (`why: "odometer"`).
- **Currency:** TeslaMate stores no currency. Imported charge costs and geofence prices take the `currency` sent with Start; without one, imported charges keep no cost and imported places no price. A per-minute geofence price becomes a place price with `per_minute` (and its `session_fee`) and no `per_kwh`.
- **Start** needs `ready` and every car matched, each car here to one imported car at most (`409 not_ready`, `409 cars_unmatched`). Chunks of one upload are stored one at a time: a chunk sent again while the first try is still being stored gets `409 wrong_offset`. The report counts only cars not left out. DELETE discards the job (history already imported stays). `/setup/status` sets `import_running` while an import is unfinished, with a fix `{ cause: "import_running", link, import }`.
- **Report per car (TeslaMate):** `report.cars` is `[{ tm_car, name, match, drives, charges, read, imported, skipped: { reason: n } }]` and `report.imported` says whether the rows are stored yet. `read`, `imported` and `skipped` count that car's rows over every table (`imported` is 0 until the import ran; read minus skipped is what it would store). Each table's figures in `report.tables` are the sum of its cars', plus rows that belong to no car (`geofences`). A car whose match is `leave_out` (a car with no drives and no charges starts so) is not in `report.cars` and its rows are not in the report's counts (TeslaFi's `rows`, `found`, `tables` and `cars_count` too); it stays in `/imports/{import}/cars` so it can be matched again. A count the file does not have (a table missing from the backup, no dated rows) is null, never 0. The `skipped` reason codes are `already-imported`, `open` (still going when the backup was made), `unknown-car`, `car-left-out`, `unknown-charge`, `bad-value` (`bad_values` names the column), `wrong-field-count` and `too-long`.

#### TeslaFi's data

The same upload takes TeslaFi's raw data: in TeslaFi, Settings > Account > Advanced > "Download TeslaFi Data" gives
one CSV per car and calendar month (`TeslaFi<M><YYYY>.csv`, each row a poll of the car). Upload one month, several
months in one `.zip` (in any order), or a file gzipped or xz'd. A file is TeslaFi's when its header is (a `Date`
column and at least four of `data_id`, `shift_state`, `charging_state`, `battery_level`, `odometer`, `latitude`,
`longitude`, `state`, `carState`, `battery_range`, `car_version`; columns are found by name, in any order, and
unknown ones are passed over), never by its name: `kind: "teslafi"`. TeslaFi's drives or charges list (Drives >
Drive Search And Download, Charges > Charge Search And Download: one row per drive, no positions) fails with
`teslafi_summary`; a zip's other files are passed over and named in `files_skipped`. Nothing is sent to TeslaFi:
the file is all there is.

- **What is made of the polls:** positions (every poll with a place or a battery figure) and charge-curve points; a
  drive from the gear (`shift_state` D or R, or moving), ended by P, by standing still in gear 10 minutes, by a
  charge, or by 15 minutes without a poll; a charge from `charging_state: "Charging"` (AC or DC from
  `fast_charger_present` and `fast_charger_type`; `energy_added_kwh` is how far TeslaFi's `charge_energy_added`
  rose over the charge's polls (the car keeps counting while it stays plugged in, so a charge that resumes after a
  pause starts above 0 and only what came on top counts), the grid energy of an AC charge its charger power summed
  over the same polls, a DC one's unknown; no cost: TeslaFi's monthly files keep none);
  the car's state from `state` (`online`, `asleep`; `offline` is unknown, never sleep); a software update where
  `car_version` changes. Every row has `source: "teslafi"`, `sources: [{ kind: "import", site: "teslafi", label:
  "Imported from TeslaFi" }]`, and is kept with the other imported rows: overlaps with live history are settled as a
  TeslaMate import's are (live shown at first; `/overlaps` flips a span), and where a TeslaMate import covers the same
  time only one import is shown (an `imports` span of `/overlaps`). Drive energy is `energy_basis:
  "estimated"` (TeslaFi's power once a minute, summed).
- **Units:** TeslaFi's base columns are the Tesla API's (`odometer`, ranges and `speed` in miles; temperatures in
  °C), its `...F` columns the owner's display units. Each file's units are worked out from its first rows
  (`odometerF` beside `odometer`, `inside_tempF` beside `inside_temp`, `gui_distance_units`,
  `gui_temperature_units`; a cabin over 60 is °F); with nothing to tell, miles and °C. `report.units` says what was
  used: `{ distance: "mi" | "km", distance_from, temperature: "c" | "f", temperature_from }` (`from`: `detected`,
  `default` or `setting`). Start's `distance_unit` (`mi`, `km`; also `miles`, `kilometers`, any case) and
  `temperature_unit` (`c`, `f`; also `celsius`, `fahrenheit`) override them.
- **Time zone:** TeslaFi writes local wall time without a zone, so the file cannot tell it: the check reads the
  times in the time zone of the car it is matched to (else the server's default) and the report says so
  (`report.time_zone: { name, from: "car" | "default" | "setting", asked: true, dst_repeated_rows }`). A page asks
  the owner to confirm it (TeslaFi's own setting, Settings > Account) and sends `time_zone` (an IANA name such as
  `Europe/Berlin`: any IANA name, else `422 invalid`) with Start; the check keeps its own zone, the import's report
  (and its `cars[]` figures) are the import's. In the hour the clocks go back the rows are read in their order
  (the second pass through that hour is the later one); a wall time the clocks skip is passed over (`dst_gap`).
- **Cars:** each car is told apart by its VIN (else `vehicle_id`, else its name, as rows of this import show them,
  never across to a car with another VIN): a row without its VIN goes with the car whose rows have the same
  `vehicle_id` (or name). Rows without a VIN whose `vehicle_id` and name show up nowhere with one (some exports put a
  made-up id on them each day) go with a car that showed a VIN only when that is plain: their odometer carries on from
  that car's readings before and after them (at most 1 km lower, 50 km higher) and their time meets none of that car's
  rows. Such a car of the file is not listed (it takes that car's match); otherwise it needs a car (`needs_car: true`,
  `match: "needs_car"`: its rows are held at the import and wait in `needs_car` for an admin to choose their car, a
  new car or to leave them aside; the car of its name whose history its odometer and time fit is suggested and
  matched at first). Days of such rows that carry on from one another are one (`rows` and the counts are all of
  them). When no row shows a VIN the file is one car. Matched as a TeslaMate car is, by its whole VIN or its VIN
  prefix (`tm_car` is the file's own car number, 1 up; `name` is TeslaFi's `display_name`).
- **Never doubled:** each car keeps the stretches of time already imported (with what was under way at their edges).
  A row inside one is passed over (`already_imported`): importing the same files again adds nothing, and a month
  downloaded before it ended, then again whole, adds only the rest. A drive or charge over the end of a month is
  joined with its other half once both months are in, whichever came first (`found.replaced` counts the halves
  taken away), and the car's state at a file's last poll lasts to the next file's first poll as it would inside
  one file (asleep until the car is seen again, online when that poll came within the hour), so the same polls give
  the same history however they are split into files. Stopping part way loses nothing: starting it again replaces what it stored. Each stretch keeps the
  time zone and units it was read in: a stretch read again in another zone (its rows looked for in its own) or other
  units is replaced, everything it stored taken away before its rows are stored again (`found.read_again` counts
  those stretches, with a warning), so an import in the wrong zone or units is corrected by importing the files
  again with the right ones. Read the neighbouring months again too, so a drive over a month's end is whole.
- **Report** (`report.kind: "teslafi"`, `report.imported` false after the check, true after the import):
  `files`, `files_skipped: { name: why }`, `rows: { read, used, skipped: { reason: n }, bad_values: { column: n },
  windows_1252 }`, `found: { drives, charges, states, updates, positions, charge_points, replaced, read_again }`
  (what the file gives; stored once imported), `tables: { positions, drives, charging_processes, states, updates }`
  each `{ read, imported, found, skipped }` (`imported` 0 until the import ran), `cars: [{ tm_car, name, vin_prefix, match,
  drives, charges, first_ms, last_ms, rows, tables }]` (`rows`: the car's polls read; `tables`: the car's own figures
  per table, as the report's `tables`, so `tables.positions` says how many of its polls were stored and skipped), `cars_count`, `cars_left_out`, `span: { from_ms, to_ms }` (the rows
  used), `units`, `time_zone`, `compression`, `packed_bytes`, `unpacked_bytes`, `missing_columns` (read here, not in
  the files: read as empty), `unknown_columns` (how many columns were passed over), `warnings`. The `skipped`
  reasons: `already_imported`, `duplicate` (the same time twice), `out_of_order`, `bad_time` (no readable `Date`, or a
  date that cannot be right: 1970 or before 2008, more than a day after now, or one row far ahead of the rows after
  it, so a damaged line never makes the months up to its date count as imported), `dst_gap`, `car_left_out`,
  `too_many_cars` (past 64 cars in one upload), `wrong_field_count`, `too_long` (a line over 1 MB). When a hundredth
  of the rows or more (and at least 10) were `out_of_order`, a warning says so.
- **Failures** (`error.code`): `not_a_teslafi_export` (no TeslaFi file in the upload), `teslafi_summary`,
  `unreadable` (a damaged gzip, xz or zip, or one that unpacks to far more than a real file does: past 16 MiB, over
  500 times its packed size for gzip and a zip's entries, 4000 times for xz; a month the car stood asleep packs 100
  to 200 times, with xz up to some 1,300), `read_failed`, `store_failed`.
- **Memory:** the files are read once per pass as a stream, a line at a time, never whole: a few years of polls
  (hundreds of MB) take a few MB.

#### Sentry Six Manager's CAN export

The same upload takes the `.zip` that Sentry Six Manager's `GET /api/can/export/bundle?key=&from=&to=` streams
(its Nerd panel: Logs + ids.csv): each log of that car key exactly as the CAN Bridge uploaded and signed it
(`<key>/<name>.log.xz`, its sidecar `<key>/<name>.log.xz.json`), with `candump=1` a candump text copy
(`<key>/<name>.log`, not signed: skipped and counted), then `ids.csv` and `manifest.json` (`{ vehicleKey, from, to,
madeAt, logs, ids, note }`). A name ending in `.zip` (or `compression: "zip"`) sets `compression` to `zip`; the
kind comes from the file itself once it is in: TeslaFi's CSVs (alone, packed, or in a zip: of its first 16 entries,
folders, macOS's files and other files passed over, a CAN export's logs ending the look) are TeslaFi's
data (`kind: "teslafi"`), any other file that starts like a zip is read as a CAN export (`kind:
"sentry_manager_can"`), anything else as a TeslaMate backup (`kind: "teslamate"`). `kind` is null until the check.

- **What happens to each log:** what a live upload gets. Before anything is stored, the log is checked against its
  sidecar's signature and against the signing key its car key is paired with (a key never seen before is paired
  with the first signed log, as on its first upload). Only a log that is signed and unchanged since is stored; it
  then goes into the same store (its size limits, the car's log count, the free space, the whole file's SHA-256),
  is judged by the same judge (signature, pairing, hash chain) and decoded by the same engine, so its rows are the
  car's own CAN data (`source: "can"`), not imported rows. A car key a car has goes to that car; a new one is
  handled as a new key's first upload is (a new car, the only car, or waiting on Settings: Cars, by the server's
  setting for new keys). Stored logs go through the data folder's write gate, as uploads do.
- **Never doubled:** a log already here (the same name and SHA-256) is counted in `already_here`, not stored again
  (its sidecar is added when only the sidecar was missing). Stopping part way (DELETE, a restart: the job goes back
  to `ready` with `error.code: "interrupted"`) loses nothing; starting it again (or importing the same zip again)
  skips what is here.
- **No cars to match:** `cars_to_match` is 0 once checked, `/cars` answers `items: []`, and Start takes no body
  fields that matter (`currency` is ignored).
- **Report** (`report.kind: "sentry_manager_can"`, `report.imported` false after the check, true after the import):
  - `logs: { read, imported, to_import, already_here, refused, sidecars_added, bytes }` (`to_import` from the check,
    `imported` from the import);
  - `refused: { reason: n }` and `refused_logs: [{ name, reason, message }]` (the first 100). Reasons: `unsigned`
    (no CAN Bridge signature), `failed_check` (changed since it was signed, or signed for another log name or car
    key), `signed_by_another_key` (not the key this car key is paired with: trust the new key on Settings: Cars
    first), `no_sidecar`, `bad_sidecar`, `different_file_here` (another log of that name is here), `being_uploaded`
    (an upload of it is under way; an upload that stopped part way is finished from where it stopped instead),
    `too_large`, `car_full`. A refused log is never stored. A log here already without its sidecar takes the zip's
    sidecar only if it passes the same check (`sidecars_added`); else it is counted refused, with its reason, and
    stays as it is. The check counts as the import would: a log twice in the zip once (then `already_here`);
  - `cars: [{ key, logs, imported, already_here, refused, first_ms, last_ms, car, car_name, status, other_signing_keys,
    chain: { signing_key, count, first, last, issues, restarts }, chain_gaps, chain_forks }]` per car key. `status`:
    `car` (goes to `car`), `new_car` (the check: no car has it, a new car is made for it), `only_car` (the check: it
    goes to the one car here, `car`, unless its VIN turns out to be another car's), `waiting` (an admin chooses on
    Settings: Cars), `working` (still being decoded when the report was made). `chain` is the key's hash chain after
    the import as Settings: CAN Bridge keys reports it for uploads (from the check: the logs here with the zip's
    signed logs it would add); a gap or a fork shows there as it does for live uploads;
  - `span: { from_ms, to_ms }` (the logs' start times), `manifest: { vehicle_key, from, to, made_at, logs }` (null
    when the zip has none), `files: { entries, candump_text, ids_csv, sidecars_without_log, other }`, `warnings`
    (after the import, also one per car key no upload token is tied to: make the bridge's token on that car);
- **Failures** (`error.code`): `not_a_can_export` (a zip with no `manifest.json` naming a car key and no CAN
  Bridge log), `unreadable` (not a zip, a damaged entry (each entry's CRC-32 is checked), encrypted, or packed with
  a method other than stored or deflate, or a deflated entry that unpacks to over 100 times its size past 16 MiB: a
  zip bomb), `read_failed`, `store_failed` (for example no free space: logs stored before stay), `stopped`,
  `internal_error` (a fault in the import itself; logs stored before stay).
- **Memory:** the zip is read once per pass as a stream, never whole: at most one log (in memory up to 16 MB,
  beyond that sealed to a spool file under the import's folder, removed after) and a few sidecars at a time.

### Moving and first-run setup

- **The set-up code.** A server with no account prints a one-time set-up code in its log on every start until it is set up, for example `first-run set-up code: SETUP-7KQ2-9XW4-M3TD-QH8C-2ZPV` (made up: `SETUP-` and five groups of four; the dev server's is `SETUP-DEV-0000`). It is also in `SETUP-CODE.txt` in the keys folder. Whoever reaches a fresh server first can do nothing with it without that code, which only someone who can read the server's log has. On TrueNAS the log is the app's **Logs** button; with plain Docker, `docker logs sentry-mate`. The code is compared in constant time; case, spaces, dashes and the `SETUP-` in front do not matter. On `POST /setup/claim`, ten wrong codes from one address within 60 s give `429` until the oldest is 60 s old. `POST /setup` counts its wrong codes apart, like wrong passwords: five from one address give `429` for 30 s.
- **The claim** is a cookie, so the browser keeps it across reloads and uploads carry it by themselves: `HttpOnly`, `SameSite=Strict`, `Path=/`, an hour from its last use (each `/setup/*` call renews it). The real server names it `__Host-sentry-mate-setup` and adds `Secure`; the dev server names it `sentry-mate-setup`. One browser holds it at a time: a new claim (the code again) ends the one before. A move or restore under way does not stop when the claim changes hands.
- **Polling, not a stream.** The set-up pages have no session, so they poll `GET /setup/job` (or `GET /setup`) once a second while a job runs; Settings polls `GET /system/move` and `GET /system/exports/{export}` the same way (the export's `progress` and `checksum` say how far it got, its speed and whether it `stalled`). The answers are small. (This replaces the event streams of `docs/plans/move-server.md`, section 6.)
- **A recent password** for the dangerous actions: making a move code, undoing a move and making an export file send the account's own `password` again, and `two_step` (the 6-digit code) when the account has two-step on. Missing (or not text): `400 bad_input` (`fields.password: "Required."`), as for any field a request needs. Wrong (an empty one too): `403 wrong_password` or `403 wrong_two_step`, with `fields`; throttled like sign-in for that account. A 403, not a 401: the person stays signed in. Cancelling a code or a move needs no password (it only makes things safer).
- **The recovery key is shown once**: in the answer of `POST /setup/fresh` (and `POST /setup`). The page shows it with Copy and Download and a tick "I have saved it", which calls `POST /system/recovery-key/saved`: the server then deletes its `RECOVERY-KEY.txt` and the `recovery_key_unsaved` notice goes. Until then the file stays in the keys folder, so a browser closed too early loses nothing: Settings: Server and access shows the key again behind the password (`POST /system/recovery-key/show`), with the same Copy, Download and tick. Once the file is deleted, no answer shows that key again. A key lost after that is replaced, not shown: `POST /system/recovery-key/new` (password again) answers a new one this once, and it waits in `RECOVERY-KEY.txt` for its own tick in the same way. These three answers are the only ones that carry a recovery key. Passwords, codes and keys travel only over HTTPS: the real server has no plain HTTP port.
- **Progress** (`SetupJob.progress`, `/system/move` `progress`): `files_*` and `bytes_*` count the copy so far; `cars_done` of `cars_total` are the cars whose files are all over (`cars_total` null until the size is known, as for `files_total`). Any of them can be null when not known: the real server gives `cars_*` as null for now, and on the old server `round` and `files_done` too. `bytes_per_s` and `eta_s` come from two looks a few seconds apart while the copy runs (null before that, and outside `copying` and `catching_up`). A move that carries on keeps what it counted.
- **While a move into this server runs** its web pages stay up and show the job. At the switch the server stops its web side for a few seconds and starts again by itself; the claim holds through that, so the page then reads the job's `done` and `result`.
- **The move's log** (`log` of `GET /system/move` and of the move-here SetupJob): what the move did on that server,
  step by step, oldest first, each line `{ at_ms, text }`, the newest 500 kept with the move's state, so a reload (and,
  on the new server, the switch and its restart) keeps it. The old server's begins again with each new move code:
  the code made, the new server connected, how much was sent (every tenth), the last-round pause (and a pause that
  ended, a copy that differed), the copy matched and the data moved, `Inputs stopped on this server: ...`, `Done:`;
  a cancel, the end of a move not heard from and an undo each add a line. The new server's: moving here from the
  address, connected (both versions, the files and bytes to copy), round 1 copying, `Copying file N of M (kind)` (at
  most one every 2 s; the kind in words, such as "a CAN log", never a path), round 1 done, `Round K caught up X files
  (size)`, the pause asked for and had, what it waited for (`Waiting: ...`, once per new problem) and that it carried
  on, the last round, switching, switched, the old server told, and `Inputs started here: ...` on its first start
  after the switch. Nothing secret is in it: no code, key, token, session or path, no address but the other
  server's (which the page shows already). The pages show it as it grows (they poll these anyway) and offer it as a
  plain-text file, one line each: `2026-11-17 14:02:05 UTC  text`.
- **The move code is shown once**, in the answer of `POST /system/move`. `GET /system/move` gives only its `id` (8 hex digits) and times. A page that lost it makes a new one (a code still waiting is replaced; one being used needs `replace: true`).
- **After a move or a restore** the new server has the old server's accounts and data, and nobody is signed in: the person signs in with their account from the old server. The CAN Bridge keeps its token and certificate SHA-256 (`result.cert_sha256`); only its server address changes, unless the new server took the old one's address (`result.same_machine` is true when the old server ran on the same machine: the page then says to give the new app port 10100 back once the old one is stopped).
- **A moved server** (`/system/move` state `moved` or `done`) keeps its web pages up but takes no changes: every POST, PUT, PATCH and DELETE answers `409 moved`, except the move itself (cancel, undo), export files, showing the recovery key and saying it is saved, signing in and out, and the person's own sessions and preferences. Reading still works. After an undo it takes changes again at once. `/notices` adds, for admins only, `move_code_waiting` (`detail: { expires_ms }`), `moving` and `moved` (`detail: { to, at_ms, switched_ms }`).
- **Old server states** (`/system/move`): `none`; `offered` (a code waits); `expired` (it expired unused: make a new one); `copying` (a new server copies; `progress` and `peer`); `paused` (the last round: uploads wait a few seconds); `moved` (the new server is switching: keep this server on); `done` (the new server took over: this server can be turned off). `skipped` lists files this server can't read (not carried).
- **Restore uploads** follow the import upload (`Upload-Offset`, `Upload-Length`, `wrong_offset`), but `Upload-SHA256` is optional: the export file checks itself. The real server opens the chunks as they arrive (nothing is stored twice) and saves its place at a sealed-chunk boundary, so after a restart `received` (and `409 wrong_offset`) can be a little before the last byte sent: the page sends from there. Choosing the same file again after a reload carries on.
- **Problems while a move runs** are in `problem.code`: `unreachable` (the old server does not answer; it tries again by itself), `no_space` (this disk is full; it carries on when there is room), `disk`, `slow_down`, `changing_fast` (something big runs on the old server), `cancelled` (cancelled on the old server: the copy so far is kept, a new code from the same server carries on), `bad_session`, `not_proven`, `disk_times` (this disk keeps file times only roughly: use another one). `message` is the server log's line, in plain words. While a restore runs: `export_damaged` and `export_cut_short` (the file is at fault: `failed`, nothing kept; download or copy it again), `no_space`.

### Additions

- `/api/v1/cars/{car}/charging-stats` is `/api/v1/charging-stats` for one car.
- `/me` gives `cars: "all"` for an account that sees every car, as in `/accounts`.
- `/me/sessions` rows also have `device`. `DELETE /me/sessions` ends every other session; this one stays (sign out with `DELETE /session`).
- `interface_size` is a percent, 50 to 200. `ui_pack` defaults to the pack being served. Choosing one ends `/original` in that browser; `/about`'s `ui_pack` is the pack this browser is served (`original: true` while `/original` is on).
- `map_colors` (`dimmed`, the default, or `original`) is the person's "Map colours": in the dark theme `dimmed` draws raster map tiles darker (never inverted, so streets, labels and water stay readable) and `original` as the tile server made them. The light theme always shows the original colours. A pack repaints its maps in place when it changes.
- `map_style` (`default`, or a preset id: `satellite`, `satellite_us`, `osm`, `opentopomap`) is the person's pick on a map page's Map / Satellite switch. `default` (and any style the admin doesn't allow) draws the admin's chosen source; the switch offers only `/maps/config` `tiles.styles`.
- **Map presets:** `/maps/config` `tiles.presets` lists `{ id, name, short, kind: "map" | "satellite", url, attribution, max_zoom, terms, overlays, region }`, satellite (Esri World Imagery, max zoom 19, with its place names and roads overlays) first, then `satellite_us` (USGS, US only, max zoom 16), `osm` and `opentopomap`. `/settings` `tiles.preset` is the admin's pick (a preset id, `custom` for `online_url`, or null: never picked, so `osm` (the OpenStreetMap street map) applies, also over the old implicit OpenStreetMap / OpenTopoMap default; a saved pick is kept); PATCHing a preset id also sets `online_url`, `attribution` and `max_zoom`, and PATCHing `online_url` without `preset` makes it that preset or `custom`. `tiles.labels` (default true) draws the overlays; `tiles.styles` (preset ids, default `["osm", "satellite"]`) are the styles viewers may switch to. `/maps/config` gives the effective `online_template`, `attribution`, `max_zoom`, `overlays`, `imagery` (photos: never dimmed) and `styles` (the chosen one first; empty while offline) and `hosts`, every host the pages may load map pictures from (the CSP's `img-src` / `connect-src` and `/network`'s `tiles` row `hosts`).
- `follow_screen` (true or false, default true) is the person's "Follow screen size" switch. Packs size the interface as Auto x `interface_size`: Auto grows with the screen while `follow_screen` is true and is 1 when it is false.
- `/setup/status` adds `fixes: [{ cause: "no_token" | "token_unused" | "key_waiting" | "logs_waiting_trust" | "import_running", link }]` (`key_waiting` also has `key`, `import_running` also `import`: the import's id, its `link` is `/settings/import`). A watch account hears only about its own cars: `tokens` counts its cars' tokens only, `keys_waiting` is 0 and there is no `key_waiting` fix (keys with no car and tokens for a new car are an admin's to read).
- `/cars/{car}/trip` also lists the `drives` and `charges` it counted; `truncated` is true when `drives`, `charges` or `markers` stop at 5,000 (the figures count everything). A charge of no known kind (no input told AC or DC) counts in `added_unknown` and `charging_unknown`, never as AC. `energy_kwh.gross` (the drives' energy and the parked energy) and `wh_per_km.gross` are null while the parked energy is not known (`/parked` `summary.energy_kwh` null). `wh_per_km` counts only the distance of drives with energy, as `/drives` does. `speed_kph` is the drives' distance over their own time (a drive that runs past the period's end counts whole in both); `time_ms.driving` is the time inside the period.
- In `/charging-stats`: `heatmap.start` and `heatmap.end` are 7 rows (Monday first) of 24 hours in the car's local time. A run is two or more charges, each starting within a day of the one before. `share_above_80_pct` is the share of charges that ended above 80 %; `share_below_20_pct` of those that started below 20 %.
- **A drive's gaps** (`flags.gap_ms`, the detail's `gaps`, and where its track breaks into stretches): a stretch between two of its samples longer than 10 s, or than 150 s where either is an API's reading alone (the Tesla API, TeslaFi's API and a local TeslaMate are read seconds to minutes apart), looked for only where the records doubt the drive's data. The list and the detail read the same seconds, so they agree. The detail's `speed_bands` and `regen_kwh` count the same steps.
- Drive detail (`/cars/{car}/drives/{drive}`) takes `speed_band_kph=` (the width of `speed_bands`, 1 to 100, default 10; 16.09344 gives 10 mph bands) and answers `speed_band_kph` with it. It adds `start_ideal_range_km` and `end_ideal_range_km` (the first and last ideal range of the drive; `start_range_km` and `end_range_km` are rated), `prev_charge` and `next_charge` (the ids of the charges that started just before and just after the drive's start; `next_charge` is null while the drive goes on) and `est_wh_per_km` with `est_basis: "wh_per_km_30d"` (the consumption of the 30 days of drives before it, which Sentry Mate's own range estimate divides `energy_remaining_kwh` by).
- The track answers (GPX and GeoJSON) carry `Content-Disposition: attachment; filename="<car>-drive-<YYYY-MM-DD-HHMM>.<gpx|geojson>"`, the start in the car's zone and the car's name with anything but letters, digits, `.`, `_` and `-` turned into `-`.
- `/series`: `setpoint_left_c` and `setpoint_right_c` can be `"LO"` (full cooling) or `"HI"` (full heat). A bucket that holds only such words gives the last word in every agg; otherwise the aggs use the numbers only.
- **Upload tokens for a new car** (`/upload-tokens`): a fresh install has no car, and a car's own tokens need its page, so an admin makes a token here. The first log sent with it makes a new car (named after its model and VIN prefix until someone names it) and ties the token and the logger's key to that car. A first upload never takes a car key that is in use already (another token is tied to it, or logs of it are here): that answers `403 wrong_car`, and so does a status request about such a key, so a token handed out for one car can't upload into, ask about or block another car's logs. A token made on a car's page (`/cars/{car}/upload-tokens`) may also take that car's own keys: that is how a car's lost or revoked token is replaced; from then on the token is listed under `/cars/{car}/upload-tokens` and no longer here. `/setup/status` counts these tokens too (for an admin).
- `/can-keys` takes `car=` (the keys tied to that car; an unknown or hidden car gives `404 no_such_car`), so a page lists one car's keys without reading every key.
- **Efficiency basis on `/cars/{car}/drives`:** `efficiency=hill_corrected` changes both `wh_per_km` and `efficiency_pct` of each row (the rated consumption against the consumption with the climb taken off; null when that is not above 0), and `summary.wh_per_km`. `summary.efficiency` names the basis used. `energy_kwh` stays the energy measured at the pack.
- **`/cars/{car}/drive-stats`:** `per_day` holds every local day of the car from the later of the period start and the car's first data to the period end (or now), days without driving as 0; `days` is their number, and `projection.basis_days` is the same count. `max_speed.last_30d` and `last_7d` cover the 30 and 7 days to the period end (or now) whatever the period, and ignore `exclude_places`; `max_speed.period` follows both. `top_destinations` leaves out drives still going and drives whose data stopped (they have no destination yet). Only the period and `exclude_places` filter the stats; the list filters of `/drives` do not.
- **`/places?car=`:** `counts` and `last_visit_ms` are that car's (an unknown or hidden car gives `404 no_such_car`); every place the account sees is still listed. `sort=drives` orders by drives (most first), then visits.
- **`/cars` items carry `now.ideal_range_km`** beside `now.range_km` (rated), so a car list can show the range the person chose (`range: "ideal"` in `/me/preferences`) without one `/now` read per car.
- **`POST /places/{place}/reprice`** also answers `example_rows` (up to 8, the same shape as the preview's: `{ kind: "charge", id, car, start_ms, change: "repriced" }`), so a page can link each example to its charge; `examples` stays as before.
- **`/fleet/versions` items carry `time_zone`** (the car's own zone), so the list of every car can show each row's dates where that car is, not in the zone of the car being viewed.
- **Audit rows carry `car`:** the id of the car the changed item belongs to (a `car:<id>` target's own car, and the car of a `drive:`, `charge:`, `trip:` or `update:` target), else null. A drive, charge or update id is only unique within its car, so a page needs it to link the entry to the item.
- **`/network` carries `certificate: { names, sha256, own }` and `upload_address`:** the names in the certificate the server runs with now (`localhost` first in one the server made), its SHA-256 (colon-separated upper-case hex pairs, as the CAN Bridge app wants it) and the address the CAN Bridge sends logs to (`https://<first name>:10100/api/can/logs`, the first name other than `localhost`, an IPv6 address in brackets). Saving `host_names` in `/settings` does not change them; they change when a new certificate is made (`POST /network/certificate`). A page compares an address with these, not with `host_names`. `own` is true when the server runs with its owner's own certificate (put in `data/tls`), which `POST /network/certificate` never replaces: a page offers no "Make a new certificate" then, and says how to change the files instead. Only such a certificate ever expires soon (`certificate_expiring`): one the server makes is valid until the year 4096.
- **A new certificate** (`POST /network/certificate`, admin): the server makes a new self-signed certificate with the same generator as on its first start, for `localhost` and the saved `host_names` (with none saved: the running certificate's names that are host names or addresses, so a name with a space or a wildcard given in `SENTRY_MATE_NAMES` never goes in), seals its key like the first one, and writes the new pair beside the old one (each file whole and synced) before it renames them into place, so a power cut never leaves the server without a certificate (the next start finishes or drops a swap cut short). Both ports (web and uploads) serve it from the next connection on; connections open already finish on the old one. It answers `{ names, sha256, upload_address }` and is recorded in the audit log (`certificate-made`, target `server:certificate`). It takes the admin's own `password` again and, when the account has two-step sign-in on, `two_step` (the code), as a move code does (missing: `400 bad_input`; wrong: `403 wrong_password` / `403 wrong_two_step`). Refused with `409`, before the password is checked (so a two-step code is not used up on it): `setup_busy` while a move or a restore into this server runs, `move_under_way` while a move code waits here or a new server copies from here (it pins this certificate's SHA-256), `moved` after the data moved away, and `own_certificate` when the server runs with its owner's own certificate (a `cert.pem` and `key.pem` put in `data/tls`, told apart by not being self-signed by the server), which it never replaces (`/network` says so in `certificate.own`). The SHA-256 changes: each CAN Bridge refuses uploads until its "certificate SHA-256" is set to the new one, and browsers ask again to accept the certificate.
- **`/settings` carries `outbound: { proxy }`:** one proxy (`http://`, `https://` or `socks5://` host with an optional port, no name or password in it; null for none) that the server uses for everything it fetches itself: online address lookups and map tiles it downloads. Viewers' browsers loading online tiles do not go through it.
- **`/me/preferences` `language` defaults to `"auto"`** for an account that never picked one, so dates and numbers follow the browser's languages; a page says "your choice" only for any other value.
- **Charge rows carry `efficiency_note`** (string or null): why `efficiency_pct` and `losses_kwh` are null although `energy_added_kwh` and `energy_grid_kwh` are both shown (they were measured over different parts of the charge). Show it as the title (tooltip) of the empty efficiency and losses cells; see Charging efficiency under Rows.
