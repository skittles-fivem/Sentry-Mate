# Sentry Mate API: what the pages need

This is the `/api/v1` the pages in [`parity/ui-parity.md`](parity/ui-parity.md) need. It merges the needs of every page into one set of resources, without duplicates. Each resource names the pages that use it.

## Conventions (every endpoint)

- **Ids are strings.** Car, drive, charge, state, update, place, visit, token, key and import ids are all strings. Drive and charge ids pass 2^53, so a JSON number would lose digits.
- **Units are metric, named in the field.** `_m`, `_km`, `_kph`, `_kw`, `_kwh`, `_wh_per_km`, `_c` (degrees Celsius), `_kpa` (tyre pressure; stored bar x 100), `_v`, `_a`, `_pct`, `_ms` (durations and times). The API never converts. The UI applies the person's unit preferences.
- **Times** are milliseconds since the epoch, UTC (`*_ms`). Every car-scoped response also carries the car's `time_zone`, and anything grouped by day, week, month or year is grouped in that zone (ISO weeks). A car's zone is the one an admin set for it; when none is set, the zone its newest position is in (looked up offline in the time zone boundaries built into the server: the position goes nowhere), else the server's `default_time_zone`. `/cars` items say which (`time_zone_source`).
- **Lists are paged by cursor.** `limit` (default 50, max 500) and `after` (an opaque string from the previous page's `next`). A list response is `{ items: [...], next: string | null }`. Optional `total` only where it is cheap.
- **Period filter** on every time-based resource: `from_ms` and `to_ms`. A row belongs to the period by its start time unless the resource says otherwise. Rows that cross an edge are clipped where noted, never dropped.
- **Several cars:** report resources accept `cars=all` or `cars=1,7` where the page offers it; each row then has `car`.
- **Access:** every car-scoped route checks the account's car list. An unknown car and a car the account may not see give the same answer: `404 { error: { code: "no_such_car" } }`.
- **Errors** use one shape: `{ error: { code, message, fields? } }`. `400` bad input (with `fields`), `401` not signed in, `403` not allowed (role), `404` unknown or hidden, `409` conflict (stale `version`), `422` invalid value, `429` with `Retry-After`.
- **Changes** need the CSRF header, are recorded in the audit log, and admin-only changes say so below. An entry names what was changed: a CAN Bridge key move is `key-assigned` (the car it went to) and `key-unassigned` (the car it left), with `target` `key:<car>:<key>`; `key-preferred`; `token-created` and `token-revoked` with `target` `token:<car>:<id>` (`token:<id>` for a new car's token). A change no handler words itself is a plain `change` entry with the request's ids filled into its route (and `car` set when the route names one). `POST /places/preview` changes nothing and writes no entry, and the same `/me/preferences` change by one account within 10 minutes is one entry.
- **Sources:** every row says where it came from. `sources` is a list (never empty on a row) of `{ kind: "smo" | "tesla_api" | "teslafi_api" | "teslamate_local" | "import", site?, label }`: `smo` is SMO (the Screenmate CAN Bridge's signed logs), `tesla_api` the Tesla Owner API this server reads, `teslafi_api` TeslaFi's polls this server reads, `teslamate_local` the owner's local TeslaMate (its MQTT topics), `import` history brought in from another site (`site: "teslamate"` or `"teslafi"`). `label` is a short line a page can show ("Data from SMO", "Data from the Tesla API", "Data from TeslaFi", "Data from local TeslaMate", "Imported from TeslaMate", "Imported from TeslaFi"). A row that several inputs saw lists them all, SMO first, and `source_label` says it in one line ("Data from SMO and the Tesla API"). Live values carry `sources` too (one entry), and so do `/cars` items (what the car has data from), `config` values (empty when an admin typed the value), `/series` and other column answers (what gave the points), `/storage` days and `/overlaps`. Estimated values carry a `basis` (for example `energy_basis: "measured" | "estimated"`). A drive or charge with Tesla API data alone has `energy_basis: "estimated"` (the API's power read every few seconds to a minute, summed).
- **Values filled from an import:** where the live inputs (SMO, the Tesla API, TeslaFi's API, local TeslaMate) all have nothing for a value at a time, the import shown for that span (TeslaMate's or TeslaFi's, as [Overlaps](#conventions) chooses) fills it, with `source=all` only and while the car's `import_gap_fill` (else the server's `import_gap_fill.enabled`, on by default) says so. A filled row is still its own source's row (its `source` word is kept); its `sources` add the import ("Data from SMO; imported from TeslaMate") and `value_sources: { field: [source] }` names each filled field (an empty object when the row has only its own values). Drives fill `start` (never `end`: a live drive without one is one whose data stopped, and keeps its "Data stopped here"), `start_odometer_km`, `end_odometer_km`, `start_soc_pct`, `end_soc_pct`, `start_range_km`, `end_range_km`, `outside_avg_c`, `cabin_avg_c`, `climb_m` and `descent_m`; charges `position` (and `odometer_km`), `start_soc_pct`, `end_soc_pct`, `start_range_km`, `end_range_km`, `outside_avg_c` and `battery_avg_c`. Distance, energy, costs and `energy_basis` are never filled, so totals and consumption stay the live row's own. Columns (`/series`) carry `value_sources: { field: [source] }`: every input or import that gave that column a value. `/now` is the car's newest values and is never filled (an import is history).
- **Old `source` word (deprecated, kept for one release):** rows still carry `source`: `can` when SMO is among `sources`, `teslamate` for an imported row, `tesla_api` for a row from the Tesla API alone (a new word). `/overlaps` keeps `shown: "can" | "teslamate"` and the `can` and `teslamate` counts beside the new fields. The packs read these today; they should move to `sources`, `shown_source`, `live` and `imported`. A later release drops them.
- **`source=` filter** on lists, series and totals: `smo`, `tesla_api`, `teslafi_api`, `teslamate_local`, `import` (any site), `import:teslamate`, `import:teslafi`, or `all` (the default). The one-word `source` of an imported row is its site (`teslamate`, `teslafi`). The old words still work: `can` is `smo`, `teslamate` is `import:teslamate`. A row matches `smo`, `tesla_api`, `teslafi_api` or `teslamate_local` when that input is among its `sources`.
- **Null means unknown.** A missing value is `null`, never `0`. Live values carry their own `at_ms`.
- **CSV:** every list resource also answers `Accept: text/csv` or `?format=csv` with the same filters.

- **Passwords.** `POST /setup`, `POST /setup/fresh`, `POST /accounts` and `PUT /me/password` refuse only an empty password and one over 1,024 bytes (`422 invalid` on the field); any other is taken, for the first admin as for everyone. `PATCH /accounts/{account}` refuses one over 1,024 bytes the same way, but takes an empty `password` as "keep the current one" (`200`, the password and the account's sign-ins unchanged). Pages warn before they send one that `passwordAdvice()` (`ui/shared/password.js`, the same reasons as the server's `password_advice`) has reasons for (shorter than 12 characters, close to the account name, one of the most common, repeating itself) and let the person use it anyway. Argon2id, the sign-in throttles, HTTPS only and two-step sign-in are what keep a weak one out of reach.
- **Asking again before a change.** Account changes (`POST`/`PATCH`/`DELETE /accounts[/{account}]`, `DELETE /accounts/{account}/two-step`, `PUT /two-step-policy`) take the acting admin's own password (`confirm_password`, or the `X-Sentry-Mate-Password` header); `PUT /me/password`, `DELETE /me/two-step` and `POST /me/two-step/recovery-codes` take one's own `password`. When the acting account has two-step sign-in on, each also needs `code` (from the authenticator app, or a recovery code; or the `X-Sentry-Mate-Code` header), the same as exports and interfaces for everyone do: without it, or wrong, `401 wrong_code`. A code works once; one `PATCH` that changes several things takes one code. Missing and wrong codes count toward the code throttle.
- **Signing in from outside** while the two-step rule keeps an account without it at home: the right password gets the same `401 wrong_credentials` as a wrong one (and counts as a failed try), so the answer never confirms a guess. The audit log still records `sign-in-refused`.
- **A password change signs everyone else out**, sign-ins still running at that moment included: a sign-in whose password was checked before the change gets `401 wrong_credentials` (or `sign_in_expired` at the code step) instead of a session.
- **Right passwords are limited too:** at most 20 sign-ins with a right password per account and minute (home and outside counted apart), then `429 throttled`; and one password check at a time per account, so no account (or loop of its own sign-ins) can keep the server's few password checks busy for the others.

## Integrations: Tesla

## Integrations: TeslaFi

The TeslaFi input, for owners who pay for TeslaFi: this server reads TeslaFi's own polls of the car (about one a minute while it is awake; as fast as every 15 s with the `often` pace) from TeslaFi's API with the owner's TeslaFi token, as a third live input beside SMO and the Tesla API. It is off until an admin adds a token: before that the server makes no connection to TeslaFi at all. It only reads: the server can ask `feed.php` (TeslaFi's latest poll) and `feed.php?command=lastGood` (the last poll of the car awake) and nothing else, never a wake (`wake_up`, `wake`, a `wake=` parameter) or a command, and no answer ever returns the token. It connects only to `www.teslafi.com` on 443, the token in the `Authorization` header (never in a URL), redirects never followed, over TLS 1.3 (TLS 1.2 only if TeslaFi's host offers no 1.3: `tls` says which one was used). Data from TeslaFi is labelled `teslafi_api`, "Data from TeslaFi"; where SMO or the Tesla API cover the same time, theirs win, value by value (SMO, then the Tesla API, then TeslaFi). Everything here is admin only, reads included; every change asks for the admin's password again (and the two-step code) and writes an audit entry.

- **Pace:** one read a minute while TeslaFi says the car drives or charges, every 3 minutes parked, every 10 minutes asleep; while SMO or the Tesla API sends live data for the car, every 10 minutes at most. At most one request every 10 s and 1,500 a day per account (then nothing until midnight UTC), the checks of a token when it is added or replaced included: they count for the day and the first read after them waits 10 s. An account whose car is not known yet asks once, 10 s after a latest poll that names no car, for the last poll awake; then it keeps the pace above. Errors wait 60 s, doubling to 15 minutes; a 429 waits what TeslaFi asks (1 minute to 1 hour). A poll already handed on (the same `data_id`) is not handed on again. After a change of `time_zone` TeslaFi's times are read in the new zone at once, and no poll is dropped for seeming older than the last one read in the old zone. These reads come from TeslaFi's own database: they do not wake the car and do not count against TeslaFi's monthly command limit.
- **Refused token:** TeslaFi answers a token it does not take with `200 {"response":{"result":"unauthorized"}}`: the account's `status` becomes `token_refused`, nothing more is asked until an admin gives a new token, an audit entry `teslafi-token-refused` is written and the notice `teslafi_token_refused` is shown to admins (`/notices`); repeated errors give `teslafi_account_error`.
- **Pace** (`poll`, one setting for every TeslaFi account): TeslaFi only has new data as often as TeslaFi itself polls the car, so reading faster than that would only read the same poll again. `often` reads about as fast as TeslaFi refreshes: driving or charging every 15 s, awake and parked every 60 s, asleep every 3 min, at most 6,000 requests a day per account. `normal` (the default): 60 s, 3 min, 10 min, 1,500 a day. `gentle`: 2 min, 5 min, 20 min (20 min also while SMO or the Tesla API is live for the car; 10 min otherwise), 1,500 a day. Whatever the pace: at most one request every 10 s per account, TeslaFi's `429` and `Retry-After` are always obeyed (at least 60 s, at most an hour), other errors back off from 60 s doubling to 15 min, and a poll already handed on (the same `data_id`) is not handed on twice. A new pace takes effect at once (the pollers start again, keeping the day's count and any wait).
- **Values:** TeslaFi's keys are the column names of its data download, so its answers are read with the TeslaFi import's rules: Tesla's units (miles, °C) unless the answer itself shows others, `Date` in the account's `time_zone`, `NULL` and empty strings as no value. A new VIN in TeslaFi's polls (another car on the TeslaFi account) is added as a car not matched yet; its polls never go to the car matched before.
- **Audit actions:** `teslafi-account-added`, `teslafi-account-changed`, `teslafi-account-paused`, `teslafi-account-resumed`, `teslafi-token-replaced`, `teslafi-car-matched`, `teslafi-account-removed`, and in the server's name `teslafi-token-refused`, `teslafi-account-error`. None holds the token.
- **`/network`** lists one `teslafi` row (`www.teslafi.com`, `enabled` while an account is read; off when there is none). **`/system/health`** has `teslafi: { accounts, cars, requests_today, last_error }`. `source=teslafi_api` filters rows and series to TeslaFi's data; `sources` name it `{ kind: "teslafi_api", label: "Data from TeslaFi" }`.

## Integrations: Local TeslaMate

The local TeslaMate input, for owners who already run TeslaMate on their own network: this server subscribes to TeslaMate's MQTT topics (`<prefix>/cars/+/#`, QoS 0) as a fourth live input beside SMO, the Tesla API and TeslaFi, and can catch up from TeslaMate's PostgreSQL database now and then for what MQTT missed (off by default). It is off until an admin adds it: before that the server makes no connection to it at all. It only reads: on MQTT it subscribes and never publishes (no will, no retain), on the database it only runs `SELECT`s, and no answer ever returns a password. Data from it is labelled `teslamate_local`, "Data from local TeslaMate"; where SMO, the Tesla API or TeslaFi cover the same time, theirs win, value by value (SMO, then the Tesla API, then TeslaFi, then local TeslaMate, then imports). Rows the database catch-up brings in are stored as a TeslaMate import (`import:teslamate`, "Imported from TeslaMate"). Everything here is admin only, reads included; every change (and every test) asks for the admin's password again (`confirm_password`, or the `X-Sentry-Mate-Password` header, and `code` when the admin has two-step sign-in on) and writes an audit entry.

## Moving and first-run setup

Moving a server and setting up a new one need no shell: the old server makes a move code (or an export file) in Settings: Server and access, and the new server's first page takes it. It does what the `move` and `import` commands do (`docs/moving.md`; how each call maps to the `moving` crate is in `docs/plans/move-server.md`, "From the web UI"). The real server answers these over HTTPS only, like every other call: set-up codes, passwords, move codes and recovery keys never travel over plain HTTP.

The `/setup/*` calls need no sign-in: a fresh server has no account yet. Instead the browser first **claims** the server with the one-time set-up code the server prints in its log, and holds the claim in a cookie. Every other `/setup/*` call needs that claim (`401 not_claimed` without it). Once the server is set up they answer `409 setup_done` (except `GET /setup`, and `GET /setup/job` for the browser that still holds the claim, so the page can show the result; the claim lasts through the restart a restore's switch makes).

## Deliberately absent

- No endpoint wakes the car, pauses logging or sends a command: Sentry Mate is read-only to the car.
- No endpoint ever returns a Tesla token, wakes the car or sends it a command. The Tesla API input only reads.
- No raw SQL, database tuning or index statistics.
- No VIN serial anywhere: only the VIN prefix is stored.

## Decisions

Points this document left open, decided while building the dev server (`ui/devserver`). Pages can rely on them.

### Requests and answers

- **CSRF header:** every POST, PUT, PATCH and DELETE carries `X-Sentry-Mate: 1`. Without it: `403 { error: { code: "csrf" } }`. Sign-in and set-up need it too.
- **Session cookie:** `HttpOnly`, `SameSite=Strict`, `Path=/`, 30 days. The real server names it `__Host-sentry-mate` and adds `Secure`. The dev server names it `sentry-mate` without `Secure`, because it is plain HTTP on 127.0.0.1.
- **The server's clock:** every `/api/` answer carries `X-Sentry-Mate-Now-Ms`, the server's "now" in epoch ms. Pages count "5 min ago" and resolve the period presets from it (`api.now()`), so a server whose clock differs from the browser's (the dev server's virtual clock) still shows the right times.
- **Car-scoped answers** carry `car` and `time_zone` at the top (the zone `/cars` names for the car, with its `time_zone_source`). In answers that mix cars, every row carries its own `car` and `time_zone`.
- **Ids:** cars are `c1`, `c2`, ...; places `p1`, ...; drive, charge and update ids are decimal strings above 2^53. Timeline rows use `<kind>:<start_ms>`.
- **Creating** answers `201` with the new object. **Deleting** answers `200` with a small JSON body (`{ deleted: true, id }`, or the changed object), never an empty body.
- **Versions:** objects that need `version` on a change (PATCH `cars/{car}`, `cars/{car}/settings`, `accounts/{account}`, `places/{place}`, `settings`; PUT `settings/mqtt`; optional `?version=` on DELETE `places/{place}`) return it on GET. The server makes one change at a time, so of two changes sent with the same version one wins and the other gets 409. A stale one gives `409 { error: { code: "stale_version", version } }` with the current version.
- **400 or 422:** a wrong type, an unknown field or a bad query value is `400 bad_input`. A well-formed value that breaks a rule (an unknown time zone, an empty password) is `422 invalid`. Both name the fields in `fields`, keyed by path (`units.distance`, `free_supercharging.0.from_date`).
- **Error codes** in use: `bad_input` 400; `not_signed_in`, `wrong_credentials`, `wrong_code`, `sign_in_expired`, `not_claimed` 401; `csrf`, `not_allowed`, `wrong_setup_code`, `password_needed`, `wrong_password`, `wrong_two_step` 403; `no_such_car`, `no_such_drive`, `no_such_charge`, `no_such_account`, `no_such_session`, `no_such_token`, `no_such_key`, `no_such_rule`, `no_such_trip`, `no_such_update`, `no_such_place`, `no_such_overlap`, `no_such_import`, `no_such_job`, `no_such_export`, `export_gone`, `no_such_tesla_account`, `no_such_sign_in`, `no_such_vehicle`, `no_offline_map`, `no_such_tile`, `not_found` 404; `method_not_allowed` 405 (with `Allow`); `stale_version`, `name_taken`, `last_admin`, `setup_done`, `import_running`, `not_uploading`, `wrong_offset` (with `offset` and an `Upload-Offset` header), `not_checked`, `not_matchable`, `not_ready`, `cars_unmatched`, `setup_busy`, `recovery_key_saved`, `move_code_used`, `move_under_way`, `moved`, `not_moved`, `finished`, `export_preparing`, `not_empty`, `account_exists`, `car_taken`, `too_many_sign_ins`, `own_certificate` 409; `too_large` 413 (bodies over 1 MB); `invalid`, `checksum_mismatch`, `move_code_wrong`, `move_code_expired`, `move_too_old`, `move_not_home_network`, `move_not_offered`, `not_an_export`, `export_too_new`, `export_cut_short`, `wrong_recovery_key`, `tesla_refused` 422; `old_server_unreachable`, `tesla_unreachable` 502; `throttled` 429 (with `Retry-After`); `server_error` 500; `busy` 503 (with `Retry-After`), `offline_map_unreadable` 503.
- **Who may read:** "(admin)" after the methods of a row means changes need an admin. Reading is admin-only too for accounts, the audit log, upload tokens, CAN Bridge keys, `settings/mqtt`, `network`, `system/storage`, `system/health`, `system/move`, `system/exports`, imports and `integrations/tesla`. A watch account may read the rest for the cars it sees; places only where its cars have been. There is no separate export permission: whoever may read a resource may also take it as CSV, GPX or PDF (the "export permission" for GPX tracks is this read access). It never meets a hidden car's id either: `car_order` and `pinned_cars` in `/me/preferences` (and the `prefs` event), and `car_order` in `/settings`, list only the cars the account sees, so a car taken off its list drops out of its order and pins.
- **Sign-in throttle:** five wrong tries for one name within 60 s, or 30 from one address whatever the names, then `429` until the oldest of those tries is 60 s old. Ten wrong set-up codes from one address within 60 s on `POST /setup/claim` are throttled the same way; `POST /setup` counts its own (see "The set-up code").

### Lists, periods and CSV

- **Cursors** are opaque strings (base64url of the last row's sort key and a hash of the filters). A cursor sent with other filters or another sort gives `400` on `after`. Start again without it. So does a cursor the server did not give out, made or changed by hand.
- **Bodies:** a `Content-Length` that is not a whole number gives `400` on `Content-Length`. An id in a body that is not text (a car, a place) is a wrong type: `400`.
- `limit` is 1 to 500, default 50. `total` is sent only where it is cheap: `/cars` without `search` or `state`, and `/accounts`.
- **Period:** `from_ms` is inclusive, `to_ms` exclusive, both epoch ms. A missing edge means the start of the history or now. Some resources default to a window when `from_ms` is missing: `series` and `activity` 24 hours, `signals` 1 hour, `trip` 7 days, `battery-level` and `health` 30 days. The window ends at `to_ms` when it is given (else now). Rows belong to the period by their start and keep their own start, end and id; only where a resource says it clips (`/parked`, `/activity`, shares) are they cut at the edges. Local days, weeks and hours use the car's `time_zone` as it is now: when an admin changes it (or, for a car whose zone is not set, when its position moves to another zone), every grouping of that car (statistics, visits and their days, charging heatmaps, storage) follows at once.
- **`cars=`** on report resources: absent or `all` means every car the account sees. A list with an unknown or hidden car gives `404 no_such_car`.
- **CSV:** `?format=csv`, or `Accept: text/csv` without JSON in it. A CSV answer carries every matching row, not one page. Nested fields become dotted columns (`start.place.name`), lists of plain values are joined with `;`, null is an empty cell. The file starts with a UTF-8 byte order mark and comes with `Content-Disposition: attachment`. Columns (series, curves, signals) give one row per `t_ms`. Asking CSV of something that is not a list gives `400` on `format`. Text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`, so a spreadsheet shows it instead of running it as a formula; numbers are written as they are.
- **Car list sorts:** `sort=last_activity` (default newest first), `name` (A to Z), `soc` (highest first), and `custom`: the person's `pinned_cars`, then their `car_order`, then the rest by last activity. `search` matches the name, the model and the VIN prefix.

### Vehicle info

`/cars/{car}` `vehicle` is worked out offline (built-in tables, no lookup) from the VIN's first 11 characters, the car's own CAN configuration (the gateway's `0x7FF` pages, the pack's 0x352 and 0x332 readings, the message the VIN came in), the Tesla API's `vehicle_config`, a TeslaMate import's car row, and what an admin typed in `config`.

- **Fields**, each a fact `{ value, source, confidence, note? }` (`value`, `source` and `confidence` null when nothing says it): `maker`, `built_in` (country code), `model` (`"Model Y"`, `"Cybertruck"`), `model_year`, `plant`, `platform` (Model S and X: `"legacy"` \| `"refresh"`), `body`, `restraint`, `seats` (a hint from the restraint set), `battery_type` (what VIN position 7 says), `chemistry` (`"lfp"` \| `"nca_nmc"`), `pack`, `pack_code` (`"4 (PACK_75_KWH)"`, or the raw number), `nominal_kwh` and `usable_kwh` (`{ min, max }`, kWh: one value from the pack's own reading now, a range from the table when new), `motors`, `drive` (`"RWD"` \| `"AWD"`), `performance`, `trim` (`"Model Y Long Range AWD"`), `epa_range_km` (the EPA's rating when new, US test cycle, US-built cars only), `wheel`, `wheel_in`, `paint`, `roof`, `spoiler`, `steering` (`"left"` \| `"right"`), `region` (the map region: `"US"`, `"EU"`, `"CN"` ...), `supercharging_access`.
- **Beside them:** `vin_prefix`, `year_kind` (`"model_year"`, or `"build_year"` for Shanghai and Berlin cars, whose 10th VIN character is the calendar year built), `trim_candidates` (the EPA trims the car can be when the inputs don't settle on one), `epa_name`, `epa_id`, `wheel_options_in` (the factory sizes when the car's own is not known), `disagreements: [{ field, values: [{ value, source }] }]` (two inputs said different things; the first value is the one shown), `unknown_codes: [{ field, source, at, code }]` (a VIN position such as `"vin:8"` or a CAN signal whose code the tables don't know: no value is given, never a guess), `notes` (plain sentences).
- **`source`:** `"owner"` \| `"can"` \| `"vin"` \| `"tesla_api"` \| `"teslamate"`. A value from a table through the VIN (the EPA range, a pack's energy when new) is `"vin"` with a `note` naming the table row's source. A US-built car's `chemistry` from the VIN is only the usual pack for its model, year and drive: `"vin"` at `"low"` confidence.
- **Precedence**, per fact: what an admin typed, then the car's CAN configuration, then the VIN (the pack's brick count is not read for the chemistry until its rules are checked on real logs); the Tesla API's words come before the VIN's tables for `trim`, `wheel`, `paint`, `roof` and `spoiler`, after it elsewhere; an import comes last. Values in another site's own words (`"74d"`, `"Pinwheel18"`) are shown but never compared.
- **`confidence`:** `"high"` (Tesla's filing or service manual, the EPA's dataset, the car's own configuration), `"medium"` (several sources agree), `"low"` (one source, to be checked).

### Rows

- **In progress:** a drive, charge or gap still going has `end_ms: null`, its figures up to now, and `flags.in_progress: true`. The current state span in `/states` has `end_ms: null`.
- **Where:** a Drive's `start` and `end` are `{ lat, lon, place: { id, name } | null, address: { short, locality, region, country_code }, label }`. `label` is what to show: the place name, else the short address. A drive whose data stopped has the last known point and the label "Data stopped here". Timeline points are the same with `address` as the short text.
- **Purpose** on a Drive is `{ value: "business" | "private" | "commute", relation, note, source: "owner" | "rule" }` or null. An owner's choice wins over a rule.
- **Overlaps:** where live history (SMO or the Tesla API) and imported history both exist, lists with `source=all` show only the side chosen for that span (live at first). Where a TeslaMate import and a TeslaFi import both have rows, only one import is shown there (with `source=all` and `source=import`): at first the one with more drives and charges in the span, then more positions, else TeslaMate's. Lists, details, totals, series, the timeline and statistics follow both choices, so no drive is shown twice. `source=smo`, `source=tesla_api`, `source=import:teslamate` or `source=import:teslafi` shows that source only, whatever was chosen. An overlap row is `{ id, kind, start_ms, end_ms, shown_source, default_source, default_reason, live: { drives, charges }, imported: { drives, charges }, sites: { teslamate: { drives, charges }, teslafi: { drives, charges } }, sources, version }` (`kind`: `live` or `imports`; `shown_source`: `live`, or the imported side by its site, `import:teslamate` or `import:teslafi`, `import` on a `live` span when both sites' rows are in it) plus the old `shown: "can" | "teslamate"`, `can` and `teslamate` (kept for one release). PATCH takes `shown` in either spelling.
- **Power signs:** `power_kw` in `now` and in series is the pack's power: positive out of the pack (driving, heating), negative into it (charging, regenerating). Charge figures and the charge curve's `power_kw` are charging power, positive.
- **Tyres** are always ordered front left, front right, rear left, rear right.
- **Price per kWh:** basis `grid` is the cost over the grid energy (AC, by the meter). Basis `pack` is the cost over the energy added to the pack (fast charging, where the grid energy is unknown). `fast_charger.billed_kwh` is what the charger delivered (about the car's inlet energy).
- **Entered rates come back as entered:** after `PUT .../cost` with `mode: "per_kwh"`, `price_per_kwh.value` and the breakdown's `per_kwh` are the amount sent (up to 5 decimals), not the total divided back; with `mode: "per_minute"` the breakdown's `per_minute` and `minutes` are the rate sent and the charging minutes. Only `cost.amount` and `total` are rounded (to 2 decimals).
- **Attention items** carry `detail` as an object in metric units, for example `{ tyre, pressure_kpa, recommended_kpa, source }` (`tyre_low`: the lowest tyre, `tyre` null while which wheel each sensor is is not known; `source` as the Now's `tyre_recommended_source`), `{ last_upload_ms }`, `{ soc_pct }`, `{ door }`, `{ reason, log_start_ms }`, `{ last_data_ms }`. The page writes the sentence.
- **Stale** means no upload for more than one hour.
- **Saved trips** belong to the account that saved them; a watch account may save its own. Purposes and purpose rules change car data and need an admin.
- **Upload tokens and CAN keys** are admin-only, reading included. DELETE on a token revokes it (it stays listed with `revoked: true`). The secret comes once, in the POST answer.

### Live values

- In `/cars/{car}/now`, every value read from the car is `{ value, at_ms }` or null: the signals, each `location` part, each tyre, each flag and door, each `charge` part. The snapshot's own facts are plain: `state`, `since_ms`, `at_ms` (the newest sample), `received_ms`, `delay_s`, `stale`, `buses` (each `{ bus: "vehicle" | "chassis", awake, at_ms }`), `driving`, `est_basis`, `charge.finish_ms`, `charge.charge_id`, `drive`, `awake_reasons`, `software`, `location.place` and `location.address`. With two live inputs, each value is the newest one either sent; for speed, power, gear and position an SMO value up to a minute old still beats a newer Tesla API value (the API's times lag), and the value's `sources` names the one it came from. `heading_deg`, `usable_soc_pct`, `charge.limit_pct`, `charge.to_full_min` (while charging) and the `sentry`, `user_present`, `keep_climate`, `climate` and `battery_preconditioning` flags come from CAN when the car sends them, else from the Tesla API while its newest reading is current; `charge.added_kwh` comes only from the Tesla API. `charge.status`, `charge.phases`, `charge.pilot_a`, `charge.limit_source`, the doors, `trunk`, `frunk`, `charge_port_open` and `display_on` come from CAN only; lock and windows are never on CAN; they and the other values no CAN message carries are in `off_can` (below). `received_ms` is when the newest data came from either input.
- **`off_can`** in `/cars/{car}/now`: the values no CAN message carries, from the API inputs. Each is `{ value, at_ms, sources: [{ kind, label }], stale }` or null: `version` (the version text the car reports), `update_available`, `update_version`, `update_download_pct`, `update_installing` (from the input's update status word; an unknown word gives nothing), `locked` (only as an input read it: never from a lock request), `windows_open` (true when one is open, false only when one input read all four closed), `windows` by seat, `sunroof_state` (`closed`, `open`, `vent` ...), `sunroof_pct`, `scheduled_charge_start_ms`, `scheduled_departure_ms`, `route` (`destination`, `km`, `minutes`, `traffic_min`). Value by value, the first input in the order SMO, the Tesla API, TeslaFi's API, local TeslaMate (lock, version, update, charge schedule, any window open, route) with a current value gives it; a value is `stale` once older than its limit (locked, windows, sunroof: 1 h; update: 6 h; schedule: 12 h; route: 10 min; version: 30 days), and a stale value is kept only when no input has a current one. The VIN is never in it.
- `state` in the car list and in `now` is one of `driving`, `charging`, `parked`, `asleep`, `unknown`. In `/states` it is `online`, `asleep` or `unknown`, with the awake buses; vehicle bus only is `online` with `buses: ["vehicle"]`.
- `charge.status` is one of `disconnected`, `no_power`, `about_to_charge`, `charging`, `complete`, `stopped`.
- **Tyres** in `/cars/{car}/now`: `tyres_kpa` is front left, front right, rear left, rear right when `tyres_slots_mapped` is true (the input names the wheels: the Tesla API, the chassis bus's 0x31F, or 0x219 with its four sensor locations each naming a different wheel); false: 0x219's four slots in the car's own order, which wheel each is not known. `tyre_recommended_kpa` (front axle) and `tyre_recommended_rear_kpa` are the recommended cold pressures, from `tyre_recommended_source`: `owner` (typed: `config.tyre_pressure_front_kpa` / `_rear_kpa` of `PATCH /cars/{car}`) beats `can` (0x219 page 4, `{ value, at_ms, sources }` as a value read from the car) beats `placard` (the door placard's for the car's model, model year and wheel size, from a built-in table citing the owner's manual; `tyre_recommended_wheel_in` names the size); typed and placard values are `{ value, at_ms: null, sources: [] }`; all null when none is known. `tyre_low` (`{ value, at_ms, sources }` with the tyres' time, or null): a tyre more than 10 % under its axle's recommended pressure; while the slots are not mapped every tyre is judged against the lower of the two (no false alarm: a tyre low for the higher axle only is missed). MQTT's `tire_low` and the `tyre_low` attention item say the same.
- `/states` `share_pct`: `parked` is the share of time not driving (known time only: (known − driving) / known, null when no time is known), `asleep` asleep, `awake` online (driving included), `unknown` no data, these three of the whole period. They overlap on purpose and need not add up to 100.
- `/awake-reasons` joins awake spans that touch into one, with the reasons of both and a time-weighted average power.

### Events (`/api/v1/events`)

- Standard server-sent events: `event:` name, `id:` (a counter), `data:` JSON. The stream starts with `retry: 3000`. A comment line every 15 s keeps it open. There is no replay for `Last-Event-ID`; after a reconnect, load what you show again.
- `now`: `{ car, now }`. The first one for a car on a stream carries the whole object; later ones carry only what changed, to be merged field by field. A `{ value, at_ms }` pair is always sent whole.
- `rows`: `{ car, kinds, from_ms, to_ms }` when a drive, charge, parked spell or gap starts or ends. `fleet`: `{ car, change: "renamed" | "added" | "removed" | "list_changed" | "inputs" | "sold", name }` (`inputs`: the car has data from a new live input, such as its first Tesla API reading; `sold`: an admin marked the car sold or not sold). When an admin changes an account's car list, that account's streams get `added` or `removed` per car (`name` null on `removed`), or one `list_changed` with `car: null` when more than 100 changed, then a `prefs` event; a car given back starts again from a whole `now`. `prefs`: the whole preferences object, to that person only. `notice`: one notice.
- A stream ends when its session ends (sign-out, account removed, password changed), when the two-step rules no longer let its account see cars (a rule for everyone that the account hasn't set up yet: checked at once when the rule changes), and when its reader falls 1000 events behind (it would miss a delta); the browser then reconnects, and the page loads what it shows again.

### Time series

- `values` holds one column per field. With one `agg` (or none), the key is the field name. With several, every agg is also under `<field>.<agg>` and the plain key holds the first one.
- Without `agg`, the plain column is the mean (the last value for `lat`, `lon`, `accuracy_m`, `odometer_km`, `heading_deg`), and when buckets are longer than 1 s, `<field>.min` and `<field>.max` come too. That is how downsampling keeps minima and maxima.
- `max_points` is 2 to 20000, default 1000. Buckets are 1 s, 2 s, 5 s, 10 s, 15 s, 30 s, 1, 2, 5, 10, 15, 30 min, 1, 2, 3, 6, 12 h, 1, 2 or 7 days (beyond that, a whole number of days), aligned to UTC, the smallest that fits. The first bucket holds `from_ms`, so it can start before it; the answer still never holds more than `max_points` buckets.
- `state` per bucket is the state that took most of it. `coverage_pct` is the share of the bucket with known data (asleep counts as known). A bucket with no sample is null in every column.
- `/signals` needs `series` (names from `/signals/latest`) and takes `max_points` (2 to 20000, default 2000). Rows of `/signals/latest` carry `has_series`: false for signals with named values (`gear`, `sentry_mode`, `charge_status`), which have a latest value only; asking `/signals` for them is 400.
- **Answers that decode stored logs take turns:** `/signals`, `/signals/latest`, `/battery`, `/battery/capacity`, `/battery-level`, `/projected-range` and `/efficiency` may decode the car's stored CAN logs while they answer. At most 3 of them run at once for the whole server; more wait their turn for up to 20 s, then get `503 busy` (with `Retry-After: 5`). One account has at most 4 running or waiting; one more is `429 throttled` at once. A request that goes away (the client closed it, or it timed out) stops its decoding. One `/signals` answer decodes at most 2 GiB of log lines, shared out over the logs it reads (`logs_read`), so a long period of large logs is a thinner read.
- Drive climate and battery heating are series fields too: `battery_heat_kw` (power the pack spends heating itself, kW; 0 when it is not heating), `climate` (`off`, `on`, `precondition`, `overheat_protect`; text, so its plain column is the last value of the bucket) and `fan_level` (blower step 0 to 10, 0 = off). Null where the car does not send them (older Model S and X, imported history).
- The charge curve is 1 Hz up to `max_points` (default 4000); longer charges come at a coarser `step_ms`, which the answer states.
- Charge curve fields: `power_kw`, `volts_v` and `amps_a` are the pack side (charging power positive). `ac_volts_v` and `ac_amps_a` are the AC line at the inlet (volts and amps of one phase; null on DC), `ac_line_kw` the AC line power, `dc_volts_v` and `dc_amps_a` the DC charger's output (null on AC), `heater_kw` the power the pack spends heating itself. `limit_source` names what sets the current the car may draw: `station` (the pilot), `cable`, `car` (its own maximum) or `setting` (the current set on the screen); null when the car does not say.

### Formats

- **GeoJSON track:** a FeatureCollection with one LineString per stretch without dropped frames. Coordinates are `[lon, lat, elevation_m]`; `properties` holds parallel `t_ms` and `accuracy_m` arrays, plus `speed_kph`, `power_kw`, `soc_pct` when asked in `extensions`. A live drive's track with values from the chosen import (with import gap filling on) adds a parallel `imported` array to that stretch's `properties` (per point, the fields the import gave it: `["elevation_m"]`, or every field for a point of the import's own where the drive's data has a gap of over 10 s) and `value_sources: { field: [source] }` beside `features`. `simplify_m` thins points (Douglas-Peucker) and keeps the arrays aligned.
- **GPX track:** GPX 1.1, one `trkseg` per stretch, `ele` and `time` on every point, extensions in our own namespace.
- **Logbook PDF:** a plain table, landscape, times in the car's time zone, with the continuity warnings and the totals per purpose.

### Battery and efficiency

- **`/battery`:** `capacity.new_source` is the first that exists: `owner` (`capacity_new_kwh` in the car's settings), `early_bms` (the pack's readings in its first 30 days), `imported_charges`, `vehicle_info` (the car's build: the usable kWh when new, else the full pack's, then compared with the full pack now). `range.new_source` is `owner`, `first_30_days` or `vehicle_info` (the EPA rating). `range.full_now_km` is the car's range over its charge level, else `full_now_from_energy_km` (usable energy over the consumption factor, the build's where the car has none yet). `notes` codes: `new_value_typed`, `new_value_from_early_readings`, `new_value_from_imported_charges`, `new_value_from_vehicle_info`, `cold_battery_locks_part`, `lfp_charge_to_100_weekly`, `imported_history_estimated`, `no_history`. `lifetime` adds `standing_kwh` (used while parked) and `basis`; `charged_kwh` is `ac_kwh + dc_kwh`. `capacity.basis` names where full and usable both come from: `pack` (the pack's full pack less the newest buffer it named; usable null when it named none and there are no charge readings) or `charges` (the median of the last charges' readings; full is that plus the buffer, null when no buffer is known). Usable is never above full. A car without history answers the same keys with null.
- **Capacity follows the charges:** `group=charge` (the default) gives one reading per finished charge that added at least 10 %: `full_pack_kwh` = `energy_added_kwh` / (`end_soc_pct` - `start_soc_pct`) x 100 + `buffer_kwh`, from the figures that charge's row shows (imported charges included), with `charge` set to that charge's id. `group=day` gives the pack's own reading per awake day (`method: "bms"`); `group=month` the median of those per month, with `readings`. Imported days have no pack readings. `x=odometer` orders by odometer. Where the pack names no buffer that day, `usable_basis` says what `usable_kwh` is instead: `recent_buffer` (less the newest buffer it named on another day) or `full_pack` (no buffer known at all). A `group=day` page looks at a bounded number of record days; when that runs out before the page is full it answers fewer items (even none) with a `next` that goes on from there, so follow `next` until it is null. `trend.projection` is `{ warranty_pct, full_pack_kwh_at_warranty, odometer_km, t_ms, method: "linear" }` or null when the pack is not losing capacity.
- **Days are the car's own:** wherever these resources bucket by day or week (`/battery-level` and `/projected-range` with `bucket=day` or `week`, `/temperatures` `daily`), a bucket runs from local midnight to local midnight (weeks from Monday), so the day the clocks change is 23 or 25 hours long and `t_ms` is always a local midnight. `bucket_ms` then names the nominal length (86400000 for a day). Hour buckets and buckets of a number of ms are fixed lengths.
- **`/battery-level`:** `from_ms` defaults to 30 days back. `bucket` defaults to `hour` up to 31 days, else `day`; the answer names `bucket` and `bucket_ms`. `moving` lines have one value per bucket (a window of daily means ending that day; `window` defaults to `7d`); `moving=false` gives empty lists. `band.high_pct` is 100 for an LFP pack. `charge_limit` is `[{ t_ms, pct }]`, a step line. `stats` is `{ mean, median, min, max }`.
- **`/projected-range`:** columns like `/series` (`t_ms`, `values`, `bucket_ms`, `coverage_pct`, `state`). `bucket` is `hour`, `day`, `week` or a number of ms; without it, the smallest that fits `max_points`.
- **`/parked`:** a spell is a stay parked off a charger at one spot, newest first, until the car drives, charges or moves (updates and gaps where it did not move stay inside). Rows also carry `car`, `duration_ms`, `clipped`, `range_lost_km`, `range_lost_per_hour_km`, `source`, `sources` and `source_label`. `energy_method` is `counter` (the pack's own energy counters) for CAN rows, `range` for imported ones. `summary` adds `hours`; `summary.cost` is `{ amount, currency, basis }` at the home price, or null.
- **`/efficiency`:** `min_distance_km` defaults to 1, `temp_group_c` to 5 (1 to 20). A group's `temp_c` is its lower edge; `temp_to_c` its upper edge (both rounded to 0.1 °C: a drive is in the group whose index `floor(outside_avg_c / temp_group_c)` equals `round(temp_c / temp_group_c)`). `min_distance_km` applies to `net_wh_per_km`, `distance_km`, `drives` and the groups; `gross_wh_per_km` always covers every drive of the period (`all_drives`) plus all parked energy, so it stays what owning the car costs. `factor.source` is `energy_and_range`, or `owner` when the car's settings override it (then `as_of_ms` is null). The car's own factor is the median of the daily means of its energy over its range over its last 14 sample days (`readings` counts the samples), so it holds still between requests; `/projected-range` uses the same value. Energy per km (`net_wh_per_km`, `gross_wh_per_km`, a group's `wh_per_km`) counts only the distance of drives with energy, as `/drives` does; `without_energy` counts the drives left out of it. A period after now answers the empty result.
- **`/temperatures`:** `daily` rows also carry `t_ms`, the local midnight that starts the day; `coverage_pct` is the share of that day (as far as the period goes) the car was awake. Lowest and highest, in the summary and each day, take every reading (sampled at least once a minute while awake), so they are never above the lowest or below the highest point `/series` gives for the same period. A car that does not send a value (the old Model S has no cabin temperature) has nulls there.

### Reports

- **`/logbook`:** rows also carry `start_place_id` and `end_place_id` (the matched place, or null), `relation`, `purpose_source` (`owner` or `rule`, null without a purpose), `purpose_rule` (the rule id when a rule gave it) and `in_progress`. `continuity_gap_km` is the odometer distance between the end of the drive before (in the same answer) and the start of this one; null on the first row.
- **`/statistics`:** rows are newest first and clipped to the period: the first and last rows can be part periods. `label` is `2026-11-16` (day), `2026-W47` (ISO week), `2026-11` (month), `2026` (year) or `All`. Rows also carry `time_zone`, `energy_used_kwh` (driving) and `energy_standing_kwh` (parked). Money is per currency: `cost_by_currency: [{ currency, amount }]`, `price_per_kwh: [{ currency, value }]`, `cost_per_100km: [{ currency, amount }]`. The answer names `period` and, for several cars, `cars`. Drives count by start time, charges by start time: the months add up to the Drives and Charges lists for the same period.
- **`/mileage`:** rows also carry `period_end_ms` and `label`; `projection` adds `basis_days`. `distance_km` is by odometer; `not_logged_km` is what the car drove in gaps.
- **`/gaps`:** `cause` is `no_log` and `not_recorded` as they are, `chain_gap` for a log missing inside a charge (`inside: { charge }`), and `unknown` for a log that failed its check or lost frames. Rows also carry `duration_ms`, `gap_reason` (the timeline's word), `source`, `sources`, `source_label` and `inside`. A gap still going has `end_ms: null`.
- **`/compare`:** `{ metric, unit, cars, series: [{ car, name, time_zone, t_ms: [], values: [] }] }`, one point per day with data, or per ISO week when the period is longer than 120 days (`capacity` in kWh, `full_range` and `odometer` in km, `wh_per_km` in Wh/km). With `wh_per_km`, `min_distance_km` (default 0) leaves out drives shorter than that, as on `/efficiency`. A car the account cannot see makes the whole request 404, so pages ask only for cars they could open.
- **Visits:** a visit is one stop, from arriving to leaving; the stop going on now has `left_ms: null`. For a car with only imported history (no CAN rows) its last stop also has `left_ms: null`, but its days, dwell, `last_ms` and the place's `last_visit_ms` end where that history ends, never today. Rows also carry `label` (the place name, else the short address), `time_zone`, `unknown_ms`, `source`, `sources` and `source_label`. `sort` is `arrived_desc` (default), `arrived_asc` or `dwell_desc`. `q` matches the place name and the address. `city=` takes a `city_key` (`US/California/San Francisco`).
- **Visit groups** (`/visits/places`, `cities`, `regions`, `countries`) carry `level` and the address parts of their level; `sort` is `visits` (default), `dwell`, `last` or `name`. `/visits/summary` adds `visits` and `cars`; `days` counts each car's days. The summary and every group row also carry `first_car` and `last_car`: the car of the first arrival and of the last moment there, so a page can show `first_ms` and `last_ms` in that car's zone.
- **`/tracks`:** `max_points` (2 to 200000, default 10000) is shared over the drives by duration, at least two points each, and the answer never holds more; too many drives for the points gives `400` on `max_points`. The answer adds `points` (the number sent) and each drive's `source`, `sources` and `source_label`.
- **`/updates`:** rows also carry `car`, `build_id` and `until_ms` (when the next update came; null for the current one). `detected_by: "fingerprint"` is a "Tesla update installed" found from the modules' firmware fingerprints (below): `start_ms` is the last time the old fingerprints were seen and `end_ms` the first time the new ones were (also `between_ms: [from, to]`; never in progress: `end_ms` is always set), placed between the last drive or awake span with the old set and the first with the new one; `changes` lists each changed field with its module (`module` id, `module_name`), `old` and `new` as lowercase hex; `changed_modules` the module ids; `build_id` names the whole fingerprint set after it (16 hex digits); `source` is `can` and `sources` SMO. Its `version` is null until an admin names it. PATCH `{ version }` takes `2026.38.4` style versions, or null to forget a typed version; on a fingerprint update the version then also names every other update whose new fingerprint set is the same (`version_source: "build_match"`, `named_by: "auto"`; the one typed on is `version_source: "owner"`, `named_by: "owner"`). Clearing a name leaves that update without one even when its set is named elsewhere, and takes the name off the updates that had it from this one. A typed name (or a cleared one) stays with its update when later logs change it: one more changed field joining it gives it a new `id` and `build_id`, and so does an earlier update with the same changes going (a window cleared); the name moves with it. `named_by` and `between_ms` are null on the other updates, `changes` empty.
- **`/firmware`:** Tesla's version number is not on CAN, but the main modules broadcast fingerprints of their code about once a second on the vehicle bus (`can0`): the front body controller (`vcfront`, 0x301 `VCFRONT_info`), the battery (`bms`, 0x300 `BMS_info`), the rear drive unit (`dir`, 0x335) and the front drive unit (`dif`, 0x656). Each is a multiplexed message (mux in byte 0, Intel order), decoded as raw integers: app and boot CRCs, git hashes, build type and configuration, the headlights' (`VCFRONT_hcmlAppCRC`, `VCFRONT_hcmrAppCRC`) and the oil pump's CRCs. `field` is the DBC's signal name; `hex` is lowercase, zero-padded to the field's width (`bits`): 14 digits for a 56-bit hash, 8 for a 32-bit CRC, 4 for a 16-bit configuration, 1 for a 3-bit build type (56-bit hashes do not fit a JS number: compare them as text, or with BigInt). Only `can0` counts (gateway copies on `can1` are not read); zero (a field the module does not fill, e.g. the app git hashes of a 2026 Model Y) and SNA (every bit set) are not values; a value is taken only once it was seen 3 times within one awake span, so a corrupt frame never shows nor makes an update. `fields` lists the fields the car's logs carried, in the DBC's order; `first_seen_ms` of the current value is when it was first seen (after the update that brought it), `history` every value, oldest first. All four modules are always listed (empty `fields` for a car whose logs had none, e.g. an older Model S). `updated_ms` is when a fingerprint was last seen (null: none yet); `updates` counts the fingerprint updates. `bridge_hints` counts the bridge's `# firmware changed: ...` log lines (a hint only: the decode of the frames is what counts). Everything here is made again from the stored logs on a rebuild (old logs too); typed names are kept apart and survive it. Watch accounts read it for their cars.
- **`/firmware/history`:** rebuilt from the stored data like `/firmware`: one `kind: "module"` row per fingerprint a module had (`fingerprint` is its main field, the app CRC, as lowercase hex; `previous` the one before it, null for the first), from the fingerprint updates' old -> new per module. `id` is `<module>:<first_seen_ms>`; `fields` every field's value in that stretch, in the DBC's order; `until_ms` when the next one was first seen (null: `current`), `duration_ms` = `last_seen_ms - first_seen_ms`; `update` is the update marker it came with (`version`, `version_source` as on `/updates`; null for the first one seen) and `version` the same name; `changed_in` the first drive after the change and the log the new value was first seen in (null for the first fingerprint). The current fingerprint of each module is the current `hex` of its main field in `/firmware`. Imported (TeslaMate, TeslaFi) updates carry a version and no fingerprints: they are `kind: "version"` rows (`id` `version:<update id>`, `module`, `fingerprint`, `previous`, `changed_in` null, `fields` empty, `first_seen_ms` the update's start, `until_ms` the next imported version's start, `current` on the newest; `source` `teslamate` or `teslafi`). `?module=` keeps that module's rows only (no version rows; anything else is 400 `bad_input` on `module`). Paged like every list (`limit` 1..500, default 50), newest first by `first_seen_ms` (ties by `id`). `modules` (always the four, in order, with how many `fingerprints` each had and its `current` one, null: never seen), `spans` (every module fingerprint, oldest first: the versions-over-time strip) and `range` (first and last fingerprint seen, null: none) are neither filtered nor paged. The answer has `car` and `time_zone`. Watch accounts read it for their cars.
- **Timeline update rows** also carry `version` and `version_source` (as `/updates`; `version` null when a fingerprint update is not named yet), and the text filter `q` matches the version. Update rows found from fingerprints also carry `detected_by: "fingerprint"` and `changed_modules` (both left out of every other row). `q` also matches the plain words for the codes, not only the codes: the kinds (`software update`, `gap in the data`, `charging` ...), the gap reasons (`no log arrived for this time`, `frames were dropped` ...) and the awake reasons (`someone in the car`, `sentry mode` ...), so a page's Find box finds a row by the words it shows.
- **`/cars/{car}/events`:** rows are `{ id, type, at_ms, topic, retained, payload }`, newest first; `payload` is exactly what MQTT would publish, in the server's units, with positions only when location publishing is on. An unknown `types` value gives `400`.

### Places

- **Matching** is live: a renamed, moved or removed place changes the name on every drive, charge, stop, timeline row, event and `now` at once. Of the places whose circle holds a point, the nearest centre wins (the lowest id on a tie). Filters by place use the same live match as the rows they filter (`places=` on drives and charges, `place=` on the timeline and on visits): a new place finds its drives at once, a removed one finds nothing. On drives, charges and the timeline an unknown place id gives `400`.
- **Costs stay put:** a charge keeps the cost it had when it ended. Changing a place's price changes only charges still going; `POST /places/{place}/reprice` applies today's price to past charges and answers `{ place, from_ms, to_ms, only_without_cost, dry_run, charges, repriced, unchanged, examples, cost_before, cost_after }`. A cost typed on a charge is never repriced. A past charge that had no cost (no place, or a place without a price) keeps having none when a place with a price is saved over it, until a reprice prices it.
- **Free Supercharging:** a DC charge that starts on a day of the car's `free_supercharging` ranges (days in the car's time zone) costs `0` with `source: "free_supercharging"`, whatever cost was kept for it, unless a cost was typed on it. The charger's name is not decoded yet, so every DC charge counts, except one at a saved place with a price whose name does not say Supercharger. The zero is in that place's currency, else the first priced place's; with no priced place at all the charge has no cost.
- **Writes:** POST needs `name`, `lat`, `lon`; `kind` defaults to `other`, `radius_m` to 100 (10 to 5000), `time_zone` to the nearest known place's. PATCH needs `version` and sends only what changes. DELETE takes an optional `?version=`. Create, change and delete answer the place (or `{ deleted, id }`) plus `effect`: the same counts as the preview. `price.rates[].days` is `all`, `mon-fri` or `sat,sun` style; `from` and `to` are `HH:MM` (`24:00` ends the day). A price needs at least one of `per_kwh`, `per_minute`, a rate or `session_fee`; send `price: null` for none. Each rate needs `per_kwh` or `per_minute` (422 on `price.rates.N.per_kwh`), and rates that leave some hours of the week out need the price's own `per_kwh` or `per_minute` for those hours (422 on `price.per_kwh`), so no hour is priced as free.
- **`/places/preview`** takes a draft place (with `id` to preview an edit) or `{ place, delete: true }` and answers `{ drives_named, drives_unnamed, charges_named, charges_unnamed, drives_taken, charges_taken, taken_from, charges_repriced, examples, place, delete }`. `charges_repriced` counts the past charges a reprice after saving would change. `drives_taken` and `charges_taken` count the drives and charges that move from another place to this one (they are part of the named counts), and `taken_from: [{ place: { id, name }, drives, charges }]` names those places, most taken first; create, change and delete answer the same in `effect`. A draft of a new place counts as newer than every saved place, so it loses a tie (the same distance to two centres) to the older place, as it will once saved. The counts cover only drives and charges that move between places: a rename alone moves nothing, and every drive and charge that stays at the place (its `counts`) shows the new name. `example_rows` (up to 8, also in the `effect` of create, change and delete) says what each example is: `{ kind: "drive" | "charge", id, car, start_ms, change: "named" | "unnamed" | "repriced" }`, so a page can link to it. It changes nothing and may be used by any account; a watch account may name only places its cars have used (others are `422` on `place` or `id`, as if there were no such place).
- **Lists:** `sort` is `name` (default), `visits`, `last_visit` or `created`; `total` is sent. Places also carry `address` and `created_ms`.
- **`/places/suggestions`:** `{ items: [{ lat, lon, radius_m, visits, dwell_ms, cars, label, address, last_visit_ms, kind }], next: null }`, where no saved place is, most visited first. **`/places/at`:** `{ lat, lon, place: Place | null, candidates: [{ id, name, kind, distance_m, radius_m }], rule: "nearest_centre", address }`.

### Integrations

- **`settings/mqtt`:** PUT sends the whole setting with `version`; leave out `password` to keep it, send null to remove it. The kept password goes only to the broker it was typed for: a PUT that changes `host`, `port`, `tls` or `pin_sha256` while a password is saved must send `password` again (or null), else `422` on `password`, so an admin session can't send the saved login to a broker of its own. GET gives `password: null` and `password_set`. Rules (422): a password needs `tls`; a `pin_sha256` (64 hex digits, colons allowed) needs `tls`; `namespace` and `ha_discovery.prefix` take no `+`, `#`, leading `$` or empty level; `ha_discovery.url` is `https://` or null.
- **`settings/mqtt/status`** adds `enabled`, `broker` and `tls`. **`/preview`** (`car` defaults to the first car the account sees) adds `car`, `name`, `units`, `device`, and each entity's `state_topic` and `config_topic`; a value the car did not send is not published, and position topics are empty while location publishing is off. **`/test`** takes no body (it uses the saved settings) and answers `{ ok, error, message, latency_ms, at_ms }`; `error` is `no_host`, `connection_refused` or `pin_mismatch`. `last_error` in `/status` is always such a code (also `auth_failed`, `tls_failed`, `timeout`, `invalid_settings`), whether a test or the running publisher failed; `last_error_message` says it in words.
- **MQTT topics** name a car by its API id: `<namespace>/cars/c7/soc`, `<namespace>/cars/c7/event`, Home Assistant device `<namespace>_c7`. One retained topic per value, as text in the server's units (`true`/`false` for on/off values): `state`, `driving`, `charging`, `place`, `latitude`, `longitude`, `location`, `gear`, `in_park`, `speed`, `power`, `heading` (while driving), `elevation`, `odometer`, `soc`, `soc_usable`, `range`, `range_ideal`, `range_estimated`, `energy_remaining`, `battery_temp`, `inside_temp`, `outside_temp`, `lv_voltage`, `tire_pressure_fl`/`_fr`/`_rl`/`_rr`, `tire_low`; the build: `paint`, `wheels`, `spoiler`, `roof`; modes: `sentry_mode`, `service_mode`, `display_mode` (`off`, `on`, `sentry`, `dog`, `camp`), `installing`, `healthy`; openings and people: `doors_open`, `door_front_left`, `door_front_right`, `door_rear_left`, `door_rear_right`, `trunk_open`, `frunk_open`, `user_present`; climate: `climate_on`, `preconditioning_cabin`, `preconditioning_battery`; charging: `plugged_in`, `charge_status` (`disconnected`, `no_power`, `about_to_charge`, `charging`, `complete`, `stopped`), `charge_kind`, `charge_power`, `charge_limit`, `charge_port_open`, `charge_energy_added` (the pack's lifetime charge counter in kWh, `total_increasing` in Home Assistant), and while charging `charger_current`, `charger_voltage`, `charger_phases`, `charge_current_request`, `charge_current_limit`, `time_to_full` (min); navigation: `navigating`, `energy_at_destination` (kWh, only while navigating); and `updated`. Home Assistant discovery gives each a `sensor`, or a `binary_sensor` for the true/false ones. From the API inputs (the Tesla API, TeslaFi's API, local TeslaMate; see `off_can` above), for what CAN does not carry: `version`, `update_available`, `update_version`, `update_download` (%), `locked` (Home Assistant's lock entity), `windows_open`, `window_driver_front`, `window_passenger_front`, `window_driver_rear`, `window_passenger_rear`, `sunroof_state`, `sunroof_open` (%), `scheduled_charge_start`, `scheduled_departure` (ISO 8601 UTC), `route_destination`, `route_distance`, `route_minutes`, `route_traffic_delay` (min); `installing` is CAN's word, else the inputs'. A value gone stale is published empty, which clears the broker's copy (Home Assistant shows it unknown). Also `since` (when the car's state began, ISO 8601 UTC) and `trim`. The VIN is never published. Drive and charge events go out once each as the server records them (an end once the car's data goes on past it); a save that turns Home Assistant discovery off, or changes `namespace` or `ha_discovery.prefix`, first clears from the broker what the old layout left (its discovery configs, and with a new namespace its retained values).
- **`/network`:** `inbound` rows also carry `tls`. Geocoding is listed but off while address lookup is offline. `release_check` is `api.github.com`, `enabled` with the setting, `last_used_ms` the last request to it. The Tesla API input adds one `tesla` row per Tesla host the accounts use (`enabled` while one is read), or one row for `owner-api.teslamotors.com`, off, when there is no account.
- **Tesla accounts (`/integrations/tesla`):** two ways to add one. **Sign in at Tesla:** `POST /integrations/tesla/sign-in` gives the address of Tesla's sign-in page; the admin opens it, signs in there (Tesla's own page asks for the password, the two-step code and any captcha: this server never sees them), and the browser ends on an address that does not load (`tesla://auth/callback?code=...`, or `https://auth.tesla.com/void/callback?code=...` with `redirect: "void"`). The admin copies that whole address into the page, which sends it as `pasted_url`. A sign-in lasts ten minutes and is used once; at most five are open at a time (`409 too_many_sign_ins`). **A refresh token** from another tool: `POST /integrations/tesla/accounts`. Either way the server checks it with Tesla before anything is kept: `422 tesla_refused` when Tesla says no, `502 tesla_unreachable` when Tesla can't be reached, `409 account_exists` when the same cars are on another account here. `422 invalid` on `pasted_url` when it is not Tesla's callback address or belongs to another sign-in; `404 no_such_sign_in` when it ran out or was used.
- **Tesla cars:** a new account's cars are not read until an admin matches them (`PUT .../cars`): to a car here (`suggested` names the one with the same VIN prefix), to a new car, or left out. `409 car_taken` when the car is matched to a vehicle of another account. `region: "china"` uses Tesla's China hosts (no streaming there). `location` says when the car's position is asked for: while it drives or charges (the default; the car shows a "location shared" icon while it is asked), always, or never.
- **How often (`poll`):** `normal` reads a parked, awake car every minute, a charging car every 30 s and a driving car every 30 s (every minute while Tesla's live stream runs beside it); `often` halves those waits; `gentle` reads a parked car every 5 minutes, a charging car every 2 and a driving car every minute. In every pace a car that is asleep is never woken (only the list of cars is read, every one or two minutes), an awake car with nothing going on is left alone for 21 minutes after 10 quiet minutes so it can fall asleep, at most one request a second and 3,000 a day go to Tesla per account, and a car whose SMO is live is read only every 5 minutes.
- **Tesla status words:** an account's `status` is `checking` (just added), `ok`, `paused`, `sign_in_needed` (Tesla stopped taking its token: sign in again or PATCH a new `refresh_token`; nothing is asked of Tesla meanwhile) or `error` (see `last_error`). A car's `mode`: `off` (not matched, left out, or the account paused), `watching_list` (asleep or offline: only the car list is read), `online_idle`, `letting_sleep`, `charging`, `driving`, `backoff` (Tesla answered with errors, or the day's 3,000 requests are used up: nothing is asked until `next_poll_ms`; after 5xx and network errors it waits longer each time, up to 15 minutes, after a 403 an hour). An account's `running` is true while the server keeps a task for it, paused or not.
- **Tesla notices and audit:** `/notices` adds, for admins only, `tesla_sign_in_needed` and `tesla_account_error` (`detail: { account }`), and the server writes an audit entry in its own name when an account turns to either. Audit actions: `tesla-account-added`, `tesla-account-removed`, `tesla-account-paused`, `tesla-account-resumed`, `tesla-account-changed`, `tesla-token-replaced`, `tesla-car-matched`, `tesla-poll-changed`, `tesla-sign-in-needed`, `tesla-account-error`. No answer, audit entry or log line holds a Tesla token, a VIN serial or the account's e-mail.

### Server, settings and health

- **`/settings`:** PATCH with `version` sends only the parts that change (`{ units: { pressure: "psi" } }` keeps the other units). Units, range and car order are the defaults of everyone's preferences: a change pushes a `prefs` event to each person, and a person's own choices stay. `release_check.enabled` (default `false`) saves: turning it on checks at once (in the background) and then once a day; turning it off stops it and drops the result (see "Release check" below). `host_names: []` means the running certificate's names (what GET answers then); IPv6 addresses are names too.
- **`/notices`:** `certificate_expiring` carries `detail: { expires_ms, days }`. `release_available` (admins only, while the check is on and its status is `newer`; `level: "info"`, `since_ms` the newest image's date, `fix_link: "/help#about"`, message `A newer build is ready: abc1234, Nov 24, 4 changes.`) carries `detail: { version, commit, build, changes, notes_url }`: `version` the short commit, `build` that image's run number (null when unknown), `notes_url` the comparison on github.com; pages link to it only while `settings.outside_links.release_notes` is on. A pack hides it per browser by `detail.commit`, so a later newer build shows again. **`/maps/config`** and **`/geocode/status`** follow `/settings` at once.
- **`/about` `build`:** this build, baked in when it was compiled: `number` the Image workflow's run (the image tag `build-<n>`), `commit` the full sha, `short` its first 7, `built_ms` the build date. A local build has `dev: true` and the other three null. Show it as `0.1.0 · build 2f44a52 · Nov 22` (the date as "Mon D" in the viewer's locale, with the year when not this year), a local build as `0.1.0 · dev build`.
- **Release check (`/release`):** off by default (`/settings` `release_check.enabled`, admins). While on it checks at once, then 24 hours after the last check (later when GitHub's rate limit said to wait: `next_ms`). It asks GitHub's API (`api.github.com`, through `outbound.proxy`) for the newest successful Image run on `main`, then compares this build's commit with it (docs/security.md says what is sent). `status`: `off` (`newest` and `error` null), `never` (on, not checked yet), `checking`, `up_to_date` (the newest image is this build, or older; `newest` filled, `changes: 0`), `newer` (`newest` has commits this build lacks: `changes` the count, `titles` up to 50 commit titles, oldest first, `more` the rest), `error` (`error.code`: `rate_limited`, `unreachable`, `http`, `bad_answer`, `dev_build` (a local build, nothing to compare, nothing asked), `proxy`, `tls`, `timeout`; the last `newest` is kept). `checked_ms` is when the last check ended, whatever its result. `POST /release/check` checks now (at most one at a time: during one it answers `checking`; while the rate limit says wait it answers `error` `rate_limited` without asking). `pull` is the command to show beside a newer build (`docker compose pull && docker compose up -d`) and `image` the image (`ghcr.io/skittles-fivem/sentry-mate:latest`): the server never pulls, downloads or installs anything. Nothing is kept on disk; a restart checks again.
- **`/about`:** also carries `links: { source, docs }` (each an address or null) and `licence: { name, url }`, Sentry Mate's own licence: `name` null while the project has not chosen one, `url` its full text (null when the server gives none).
- **`/cars/{car}/health`:** `from_ms` defaults to 30 days back. `reasons` codes: `upload_silence`, `trust_failed`, `logs_waiting_trust`, `rebuild_pending`. `last_log_trust` adds `log_start_ms`; keys add `preferred`, `device` and `logs_waiting`; `unknown_spans` are `[{ start_ms, end_ms, reason }]` (`end_ms` null while still unknown), with their total in `unknown_ms`. `last_upload_ms` (the car's, and each key's) is when the newest log arrived, not the time in its name nor when the server worked on it. `chain_gaps`, `dropped_frames` and `unknown_spans` each hold at most the newest 500 of the period; `chain_gaps_total`, `dropped_frames_total` and `unknown_spans_total` count them all (`unknown_ms` too is of them all).
- **`/rebuild`** takes `from_ms` and `to_ms` up to 4102444800000 (2100-01-01; later is `422 invalid`) and answers `{ car, job, status: "done", from_ms, to_ms, kinds, logs_read, took_ms }` and pushes a `rows` event; `rebuild_pending` stays true for a few seconds after.
- **`/overlaps`:** two kinds of rows, newest first. `kind: "live"`, `id: "overlap:<start_ms>"`: a span of live history (SMO's or the Tesla API's states that are not unknown) holding imported drives or charges. `kind: "imports"`, `id: "imports:<start_ms>"`: a span where both import sites have history (their states, drives and charges cover the same time, widened over the drives and charges that reach into it) and each has a row starting in it; it may hold live history too, which still wins there. Rows are `{ id, kind, start_ms, end_ms, shown_source, default_source, default_reason, live: { drives, charges }, imported: { drives, charges }, sites: { teslamate: { drives, charges }, teslafi: { drives, charges } }, sources, version, shown, can: { drives, charges }, teslamate: { drives, charges } }` (`shown`, `can` and `teslamate` are the old names, kept for one release; on an `imports` row `shown` is `teslamate`, the imported side). `imported` (and the old `teslamate`) counts each real drive and charge once, as the lists show them: where both imports cover the time, only the shown site's rows (on an `imports` row the site `shown_source` names, on a `live` row the site its `imports` span shows); `sites` has each site's own counts. A choice belongs to the time it covers, not to its start: a later import that moves a span's start (and with it its id) keeps the choice made for it. `default_source` is what the span shows when no one chose (`live`, or on an `imports` row the bigger import) and `default_reason` why that import: `more_drives_and_charges`, `more_samples` (the same drives and charges, more positions), or `tie` (TeslaMate's, the older format most owners came from); null on a `live` row. `version` is the car's overlap choices' version (every row carries the same; any flip moves it on). PATCH `{ id, shown, version }`: of a `live` span `shown` is `live` or `import` (also spelt `import:teslamate`, `import:teslafi`: the imported side, whose site in an `imports` span is that span's choice), or the old `can` or `teslamate`, and `version` may be left out; of an `imports` span `shown` is `import:teslamate` or `import:teslafi` (`live` is `422 invalid`) and `version` is required (`400` without it). A stale `version` is `409 stale_version` with the current one. The flip is in the audit log (`car-overlap`); Drives, Charges, Timeline, Statistics, Series and Travel then show that side for the span. It answers the list plus `changed`.
- **Storage:** `/cars/{car}/storage` answers `{ kinds: [{ kind, label, bytes }], total_bytes, items: [{ series, source, date, bytes }], next }`, newest day first, only days with data; `kinds=logs,series,curves,rows` filters the days. `from_ms` and `to_ms` filter them too (a log by its start, a stored day when it meets the period; the per-kind bytes stay the whole history's). A log's `date` is the car's own day; series and curves are stored per UTC day, so their rows carry that UTC date. `/system/storage` is the sum of the cars (imported history apart), plus offline map tiles; TeslaMate backups uploaded to an import are their own kind, `import_uploads`, not the server's `server` (accounts, settings and places); `growth` is the last 30 full days, and `full_in_days` is free space over the mean growth.

### Import

- **Upload:** POST `{ name, bytes_total, compression? }` (or an `Upload-Length` header) answers 201 with the import, `upload_url` and `chunk_max_bytes` (just under 1 MB). Each PATCH body is the next chunk (`Content-Type: application/offset+octet-stream`) with `Upload-Offset`, `Upload-Length` and `Upload-SHA256` (hex or base64). A wrong offset gives `409 wrong_offset` with the offset to send from; a chunk that does not match its SHA-256 gives `422 checksum_mismatch`. One import at a time: another POST while one is unfinished gives `409 import_running`. A chunk that is stored (here and in a restore) gives back the request it took from the address's request rate, so a big file sent quickly is not slowed to the rate's pace; a refused chunk counts.
- **Several files:** POST `{ files: [{ name, bytes_total }, ...] }` (1 to 500 files, each 1 byte to 64 GB) makes one import of them all. Every import has `files: [{ index, name, bytes_total, uploaded_bytes, upload_url }]` (`upload_url`: `/api/v1/imports/{import}/files/{index}`), and the create's `upload_url` is file 0's; the import's own PATCH is file 0. Each file's chunks go to its own address with that file's `Upload-Offset` and `Upload-Length`; different files may be sent at the same time. The import's `name` is the first file's plus " and N more files", `bytes_total` and `uploaded_bytes` the sums. Once every file is complete it goes to `checking`. Several files are taken for TeslaFi's data only (one check, one car matching, one report, with `report.uploads: [{ name, compression, packed_bytes, unpacked_bytes, files, files_skipped, rows_read, rows_used, rows_skipped }]` one per file in order); several files that are a TeslaMate backup or a CAN export fail the check with `one_file_only`, a file among TeslaFi ones that is not TeslaFi's with `not_a_teslafi_export` naming it. A page resuming after a reload matches its files to `files` by name and `bytes_total` and continues each from its `uploaded_bytes`.
- **Status** moves `uploading` -> `checking` (pass 1) -> `ready` -> `importing` (pass 2) -> `done`, or `failed` with `error`. `ready` means checked and waiting for the cars to be matched and the import started. While checking or importing, `bytes_read` grows. Answers also carry `id`, `name`, `compression`, `uploaded_bytes`, `started_ms`, `checked_ms`, `finished_ms` and `cars_to_match`.
- **Cars:** GET `/imports/{import}/cars` answers `{ import, items: [{ tm_car, name, vin_prefix, drives, charges, first_ms, last_ms, match, suggested }], next }` once the whole file is uploaded (`409 not_checked` before). A car here with the same VIN prefix is suggested and matched at first, unless that car is suggested for another car of the backup too (cars of the same model, year and plant share the prefix): then none of them is. PUT `{ items: [{ tm_car, match }] }` changes only the cars it names; one car here takes at most one imported car.
- **Currency:** TeslaMate stores no currency. Imported charge costs and geofence prices take the `currency` sent with Start; without one, imported charges keep no cost and imported places no price. A per-minute geofence price becomes a place price with `per_minute` (and its `session_fee`) and no `per_kwh`.
- **Start** needs `ready` and every car matched, each car here to one imported car at most (`409 not_ready`, `409 cars_unmatched`). Chunks of one upload are stored one at a time: a chunk sent again while the first try is still being stored gets `409 wrong_offset`. The report counts only cars not left out. DELETE discards the job (history already imported stays). `/setup/status` sets `import_running` while an import is unfinished, with a fix `{ cause: "import_running", link, import }`.
- **Report per car (TeslaMate):** `report.cars` is `[{ tm_car, name, match, drives, charges, read, imported, skipped: { reason: n } }]` and `report.imported` says whether the rows are stored yet. `read`, `imported` and `skipped` count that car's rows over every table (`imported` is 0 until the import ran; read minus skipped is what it would store). Each table's figures in `report.tables` are the sum of its cars', plus rows that belong to no car (`geofences`). A car whose match is `leave_out` (a car with no drives and no charges starts so) is not in `report.cars` and its rows are not in the report's counts (TeslaFi's `rows`, `found`, `tables` and `cars_count` too); it stays in `/imports/{import}/cars` so it can be matched again. A count the file does not have (a table missing from the backup, no dated rows) is null, never 0. The `skipped` reason codes are `already-imported`, `open` (still going when the backup was made), `unknown-car`, `car-left-out`, `unknown-charge`, `bad-value` (`bad_values` names the column), `wrong-field-count` and `too-long`.

#### TeslaFi's data

The same upload takes TeslaFi's raw data: in TeslaFi, Settings > Account > Advanced > "Download TeslaFi Data" gives
one CSV per car and calendar month (`TeslaFi<M><YYYY>.csv`, each row a poll of the car). Upload one month, several
months in one `.zip` (in any order), or a file gzipped or xz'd. A file is TeslaFi's when its header is (a `Date`
column and at least four of `data_id`, `shift_state`, `charging_state`, `battery_level`, `odometer`, `latitude`,
`longitude`, `state`, `carState`, `battery_range`, `car_version`; columns are found by name, in any order, and
unknown ones are passed over), never by its name: `kind: "teslafi"`. TeslaFi's drives or charges list (Drives >
Drive Search And Download, Charges > Charge Search And Download: one row per drive, no positions) fails with
`teslafi_summary`; a zip's other files are passed over and named in `files_skipped`. Nothing is sent to TeslaFi:
the file is all there is.

- **What is made of the polls:** positions (every poll with a place or a battery figure) and charge-curve points; a
  drive from the gear (`shift_state` D or R, or moving), ended by P, by standing still in gear 10 minutes, by a
  charge, or by 15 minutes without a poll; a charge from `charging_state: "Charging"` (AC or DC from
  `fast_charger_present` and `fast_charger_type`; `energy_added_kwh` is TeslaFi's `charge_energy_added`, the grid
  energy of an AC charge its charger power summed, a DC one's unknown; no cost: TeslaFi's monthly files keep none);
  the car's state from `state` (`online`, `asleep`; `offline` is unknown, never sleep); a software update where
  `car_version` changes. Every row has `source: "teslafi"`, `sources: [{ kind: "import", site: "teslafi", label:
  "Imported from TeslaFi" }]`, and is kept with the other imported rows: overlaps with live history are settled as a
  TeslaMate import's are (live shown at first; `/overlaps` flips a span), and where a TeslaMate import covers the same
  time only one import is shown (an `imports` span of `/overlaps`). Drive energy is `energy_basis:
  "estimated"` (TeslaFi's power once a minute, summed).
- **Units:** TeslaFi's base columns are the Tesla API's (`odometer`, ranges and `speed` in miles; temperatures in
  °C), its `...F` columns the owner's display units. Each file's units are worked out from its first rows
  (`odometerF` beside `odometer`, `inside_tempF` beside `inside_temp`, `gui_distance_units`,
  `gui_temperature_units`; a cabin over 60 is °F); with nothing to tell, miles and °C. `report.units` says what was
  used: `{ distance: "mi" | "km", distance_from, temperature: "c" | "f", temperature_from }` (`from`: `detected`,
  `default` or `setting`). Start's `distance_unit` (`mi`, `km`; also `miles`, `kilometers`, any case) and
  `temperature_unit` (`c`, `f`; also `celsius`, `fahrenheit`) override them.
- **Time zone:** TeslaFi writes local wall time without a zone, so the file cannot tell it: the check reads the
  times in the time zone of the car it is matched to (else the server's default) and the report says so
  (`report.time_zone: { name, from: "car" | "default" | "setting", asked: true, dst_repeated_rows }`). A page asks
  the owner to confirm it (TeslaFi's own setting, Settings > Account) and sends `time_zone` (an IANA name such as
  `Europe/Berlin`: any IANA name, else `422 invalid`) with Start; the check keeps its own zone, the import's report
  (and its `cars[]` figures) are the import's. In the hour the clocks go back the rows are read in their order
  (the second pass through that hour is the later one); a wall time the clocks skip is passed over (`dst_gap`).
- **Cars:** each car is told apart by its VIN (else `vehicle_id`, else its name): a row without its VIN goes with the
  car whose rows have the same `vehicle_id` (or name), never to a car of its own. Matched as a TeslaMate car is, by
  its VIN prefix (`tm_car` is the file's own car number, 1 up; `name` is TeslaFi's `display_name`).
- **Never doubled:** each car keeps the stretches of time already imported (with what was under way at their edges).
  A row inside one is passed over (`already_imported`): importing the same files again adds nothing, and a month
  downloaded before it ended, then again whole, adds only the rest. A drive or charge over the end of a month is
  joined with its other half once both months are in, whichever came first (`found.replaced` counts the halves
  taken away). Stopping part way loses nothing: starting it again replaces what it stored. Each stretch keeps the
  time zone and units it was read in: a stretch read again in another zone (its rows looked for in its own) or other
  units is replaced, everything it stored taken away before its rows are stored again (`found.read_again` counts
  those stretches, with a warning), so an import in the wrong zone or units is corrected by importing the files
  again with the right ones. Read the neighbouring months again too, so a drive over a month's end is whole.
- **Report** (`report.kind: "teslafi"`, `report.imported` false after the check, true after the import):
  `files`, `files_skipped: { name: why }`, `rows: { read, used, skipped: { reason: n }, bad_values: { column: n },
  windows_1252 }`, `found: { drives, charges, states, updates, positions, charge_points, replaced, read_again }`
  (what the file gives; stored once imported), `tables: { positions, drives, charging_processes, states, updates }`
  each `{ read, imported, found, skipped }` (`imported` 0 until the import ran), `cars: [{ tm_car, name, vin_prefix, match,
  drives, charges, first_ms, last_ms, rows }]`, `cars_count`, `cars_left_out`, `span: { from_ms, to_ms }` (the rows
  used), `units`, `time_zone`, `compression`, `packed_bytes`, `unpacked_bytes`, `missing_columns` (read here, not in
  the files: read as empty), `unknown_columns` (how many columns were passed over), `warnings`. The `skipped`
  reasons: `already_imported`, `duplicate` (the same time twice), `out_of_order`, `bad_time` (no readable `Date`),
  `dst_gap`, `car_left_out`, `too_many_cars` (past 64 cars in one upload), `wrong_field_count`, `too_long` (a line
  over 1 MB).
- **Failures** (`error.code`): `not_a_teslafi_export` (no TeslaFi file in the upload), `teslafi_summary`,
  `unreadable` (a damaged gzip, xz or zip), `read_failed`, `store_failed`.
- **Memory:** the files are read once per pass as a stream, a line at a time, never whole: a few years of polls
  (hundreds of MB) take a few MB.

#### Sentry Six Manager's CAN export

The same upload takes the `.zip` that Sentry Six Manager's `GET /api/can/export/bundle?key=&from=&to=` streams
(its Nerd panel: Logs + ids.csv): each log of that car key exactly as the CAN Bridge uploaded and signed it
(`<key>/<name>.log.xz`, its sidecar `<key>/<name>.log.xz.json`), with `candump=1` a candump text copy
(`<key>/<name>.log`, not signed: skipped and counted), then `ids.csv` and `manifest.json` (`{ vehicleKey, from, to,
madeAt, logs, ids, note }`). A name ending in `.zip` (or `compression: "zip"`) sets `compression` to `zip`; the
kind comes from the file itself once it is in: TeslaFi's CSVs (alone, packed, or in a zip: of its first 16 entries,
folders, macOS's files and other files passed over, a CAN export's logs ending the look) are TeslaFi's
data (`kind: "teslafi"`), any other file that starts like a zip is read as a CAN export (`kind:
"sentry_manager_can"`), anything else as a TeslaMate backup (`kind: "teslamate"`). `kind` is null until the check.

- **What happens to each log:** what a live upload gets. Before anything is stored, the log is checked against its
  sidecar's signature and against the signing key its car key is paired with (a key never seen before is paired
  with the first signed log, as on its first upload). Only a log that is signed and unchanged since is stored; it
  then goes into the same store (its size limits, the car's log count, the free space, the whole file's SHA-256),
  is judged by the same judge (signature, pairing, hash chain) and decoded by the same engine, so its rows are the
  car's own CAN data (`source: "can"`), not imported rows. A car key a car has goes to that car; a new one is
  handled as a new key's first upload is (a new car, the only car, or waiting on Settings: Cars, by the server's
  setting for new keys). Stored logs go through the data folder's write gate, as uploads do.
- **Never doubled:** a log already here (the same name and SHA-256) is counted in `already_here`, not stored again
  (its sidecar is added when only the sidecar was missing). Stopping part way (DELETE, a restart: the job goes back
  to `ready` with `error.code: "interrupted"`) loses nothing; starting it again (or importing the same zip again)
  skips what is here.
- **No cars to match:** `cars_to_match` is 0 once checked, `/cars` answers `items: []`, and Start takes no body
  fields that matter (`currency` is ignored).
- **Report** (`report.kind: "sentry_manager_can"`, `report.imported` false after the check, true after the import):
  - `logs: { read, imported, to_import, already_here, refused, sidecars_added, bytes }` (`to_import` from the check,
    `imported` from the import);
  - `refused: { reason: n }` and `refused_logs: [{ name, reason, message }]` (the first 100). Reasons: `unsigned`
    (no CAN Bridge signature), `failed_check` (changed since it was signed, or signed for another log name or car
    key), `signed_by_another_key` (not the key this car key is paired with: trust the new key on Settings: Cars
    first), `no_sidecar`, `bad_sidecar`, `different_file_here` (another log of that name is here), `being_uploaded`
    (an upload of it is under way; an upload that stopped part way is finished from where it stopped instead),
    `too_large`, `car_full`. A refused log is never stored. A log here already without its sidecar takes the zip's
    sidecar only if it passes the same check (`sidecars_added`); else it is counted refused, with its reason, and
    stays as it is. The check counts as the import would: a log twice in the zip once (then `already_here`);
  - `cars: [{ key, logs, imported, already_here, refused, first_ms, last_ms, car, car_name, status, other_signing_keys,
    chain: { signing_key, count, first, last, issues, restarts }, chain_gaps, chain_forks }]` per car key. `status`:
    `car` (goes to `car`), `new_car` (the check: no car has it, a new car is made for it), `only_car` (the check: it
    goes to the one car here, `car`, unless its VIN turns out to be another car's), `waiting` (an admin chooses on
    Settings: Cars), `working` (still being decoded when the report was made). `chain` is the key's hash chain after
    the import as Settings: CAN Bridge keys reports it for uploads (from the check: the logs here with the zip's
    signed logs it would add); a gap or a fork shows there as it does for live uploads;
  - `span: { from_ms, to_ms }` (the logs' start times), `manifest: { vehicle_key, from, to, made_at, logs }` (null
    when the zip has none), `files: { entries, candump_text, ids_csv, sidecars_without_log, other }`, `warnings`
    (after the import, also one per car key no upload token is tied to: make the bridge's token on that car);
- **Failures** (`error.code`): `not_a_can_export` (a zip with no `manifest.json` naming a car key and no CAN
  Bridge log), `unreadable` (not a zip, a damaged entry (each entry's CRC-32 is checked), encrypted, or packed with
  a method other than stored or deflate, or a deflated entry that unpacks to over 100 times its size past 16 MiB: a
  zip bomb), `read_failed`, `store_failed` (for example no free space: logs stored before stay), `stopped`,
  `internal_error` (a fault in the import itself; logs stored before stay).
- **Memory:** the zip is read once per pass as a stream, never whole: at most one log (in memory up to 16 MB,
  beyond that sealed to a spool file under the import's folder, removed after) and a few sidecars at a time.

### Moving and first-run setup

- **The set-up code.** A server with no account prints a one-time set-up code in its log on every start until it is set up, for example `first-run set-up code: SETUP-7KQ2-9XW4-M3TD-QH8C-2ZPV` (made up: `SETUP-` and five groups of four; the dev server's is `SETUP-DEV-0000`). It is also in `SETUP-CODE.txt` in the keys folder. Whoever reaches a fresh server first can do nothing with it without that code, which only someone who can read the server's log has. On TrueNAS the log is the app's **Logs** button; with plain Docker, `docker logs sentry-mate`. The code is compared in constant time; case, spaces, dashes and the `SETUP-` in front do not matter. On `POST /setup/claim`, ten wrong codes from one address within 60 s give `429` until the oldest is 60 s old. `POST /setup` counts its wrong codes apart, like wrong passwords: five from one address give `429` for 30 s.
- **The claim** is a cookie, so the browser keeps it across reloads and uploads carry it by themselves: `HttpOnly`, `SameSite=Strict`, `Path=/`, an hour from its last use (each `/setup/*` call renews it). The real server names it `__Host-sentry-mate-setup` and adds `Secure`; the dev server names it `sentry-mate-setup`. One browser holds it at a time: a new claim (the code again) ends the one before. A move or restore under way does not stop when the claim changes hands.
- **Polling, not a stream.** The set-up pages have no session, so they poll `GET /setup/job` (or `GET /setup`) once a second while a job runs; Settings polls `GET /system/move` and `GET /system/exports/{export}` the same way. The answers are small. (This replaces the event streams of `docs/plans/move-server.md`, section 6.)
- **A recent password** for the dangerous actions: making a move code, undoing a move and making an export file send the account's own `password` again, and `two_step` (the 6-digit code) when the account has two-step on. Missing (or not text): `400 bad_input` (`fields.password: "Required."`), as for any field a request needs. Wrong (an empty one too): `403 wrong_password` or `403 wrong_two_step`, with `fields`; throttled like sign-in for that account. A 403, not a 401: the person stays signed in. Cancelling a code or a move needs no password (it only makes things safer).
- **The recovery key is shown once**: in the answer of `POST /setup/fresh` (and `POST /setup`). The page shows it with Copy and Download and a tick "I have saved it", which calls `POST /system/recovery-key/saved`: the server then deletes its `RECOVERY-KEY.txt` and the `recovery_key_unsaved` notice goes. Until then the file stays in the keys folder, so a browser closed too early loses nothing: Settings: Server and access shows the key again behind the password (`POST /system/recovery-key/show`), with the same Copy, Download and tick. Once the file is deleted, no answer shows that key again. A key lost after that is replaced, not shown: `POST /system/recovery-key/new` (password again) answers a new one this once, and it waits in `RECOVERY-KEY.txt` for its own tick in the same way. These three answers are the only ones that carry a recovery key. Passwords, codes and keys travel only over HTTPS: the real server has no plain HTTP port.
- **Progress** (`SetupJob.progress`, `/system/move` `progress`): `files_*` and `bytes_*` count the copy so far; `cars_done` of `cars_total` are the cars whose files are all over (`cars_total` null until the size is known, as for `files_total`). Any of them can be null when not known: the real server gives `cars_*` as null for now, and on the old server `round` and `files_done` too. `bytes_per_s` and `eta_s` come from two looks a few seconds apart while the copy runs (null before that, and outside `copying` and `catching_up`). A move that carries on keeps what it counted.
- **While a move into this server runs** its web pages stay up and show the job. At the switch the server stops its web side for a few seconds and starts again by itself; the claim holds through that, so the page then reads the job's `done` and `result`.
- **The move code is shown once**, in the answer of `POST /system/move`. `GET /system/move` gives only its `id` (8 hex digits) and times. A page that lost it makes a new one (a code still waiting is replaced; one being used needs `replace: true`).
- **After a move or a restore** the new server has the old server's accounts and data, and nobody is signed in: the person signs in with their account from the old server. The CAN Bridge keeps its token and certificate SHA-256 (`result.cert_sha256`); only its server address changes, unless the new server took the old one's address (`result.same_machine` is true when the old server ran on the same machine: the page then says to give the new app port 10100 back once the old one is stopped).
- **A moved server** (`/system/move` state `moved` or `done`) keeps its web pages up but takes no changes: every POST, PUT, PATCH and DELETE answers `409 moved`, except the move itself (cancel, undo), export files, showing the recovery key and saying it is saved, signing in and out, and the person's own sessions and preferences. Reading still works. After an undo it takes changes again at once. `/notices` adds, for admins only, `move_code_waiting` (`detail: { expires_ms }`), `moving` and `moved` (`detail: { to, at_ms, switched_ms }`).
- **Old server states** (`/system/move`): `none`; `offered` (a code waits); `expired` (it expired unused: make a new one); `copying` (a new server copies; `progress` and `peer`); `paused` (the last round: uploads wait a few seconds); `moved` (the new server is switching: keep this server on); `done` (the new server took over: this server can be turned off). `skipped` lists files this server can't read (not carried).
- **Restore uploads** follow the import upload (`Upload-Offset`, `Upload-Length`, `wrong_offset`), but `Upload-SHA256` is optional: the export file checks itself. The real server opens the chunks as they arrive (nothing is stored twice) and saves its place at a sealed-chunk boundary, so after a restart `received` (and `409 wrong_offset`) can be a little before the last byte sent: the page sends from there. Choosing the same file again after a reload carries on.
- **Problems while a move runs** are in `problem.code`: `unreachable` (the old server does not answer; it tries again by itself), `no_space` (this disk is full; it carries on when there is room), `disk`, `slow_down`, `changing_fast` (something big runs on the old server), `cancelled` (cancelled on the old server: the copy so far is kept, a new code from the same server carries on), `bad_session`, `not_proven`, `disk_times` (this disk keeps file times only roughly: use another one). `message` is the server log's line, in plain words. While a restore runs: `export_damaged` and `export_cut_short` (the file is at fault: `failed`, nothing kept; download or copy it again), `no_space`.

### Additions

- `/api/v1/cars/{car}/charging-stats` is `/api/v1/charging-stats` for one car.
- `/me` gives `cars: "all"` for an account that sees every car, as in `/accounts`.
- `/me/sessions` rows also have `device`. `DELETE /me/sessions` ends every other session; this one stays (sign out with `DELETE /session`).
- `interface_size` is a percent, 50 to 200. `ui_pack` defaults to the pack being served. Choosing one ends `/original` in that browser; `/about`'s `ui_pack` is the pack this browser is served (`original: true` while `/original` is on).
- `map_colors` (`dimmed`, the default, or `original`) is the person's "Map colours": in the dark theme `dimmed` draws raster map tiles darker (never inverted, so streets, labels and water stay readable) and `original` as the tile server made them. The light theme always shows the original colours. A pack repaints its maps in place when it changes.
- `map_style` (`default`, or a preset id: `satellite`, `satellite_us`, `osm`, `opentopomap`) is the person's pick on a map page's Map / Satellite switch. `default` (and any style the admin doesn't allow) draws the admin's chosen source; the switch offers only `/maps/config` `tiles.styles`.
- **Map presets:** `/maps/config` `tiles.presets` lists `{ id, name, short, kind: "map" | "satellite", url, attribution, max_zoom, terms, overlays, region }`, satellite (Esri World Imagery, max zoom 19, with its place names and roads overlays) first, then `satellite_us` (USGS, US only, max zoom 16), `osm` and `opentopomap`. `/settings` `tiles.preset` is the admin's pick (a preset id, `custom` for `online_url`, or null: never picked, so `satellite` applies, also over the old implicit OpenStreetMap / OpenTopoMap default); PATCHing a preset id also sets `online_url`, `attribution` and `max_zoom`, and PATCHing `online_url` without `preset` makes it that preset or `custom`. `tiles.labels` (default true) draws the overlays; `tiles.styles` (preset ids, default `["satellite", "osm"]`) are the styles viewers may switch to. `/maps/config` gives the effective `online_template`, `attribution`, `max_zoom`, `overlays`, `imagery` (photos: never dimmed) and `styles` (the chosen one first; empty while offline) and `hosts`, every host the pages may load map pictures from (the CSP's `img-src` / `connect-src` and `/network`'s `tiles` row `hosts`).
- `follow_screen` (true or false, default true) is the person's "Follow screen size" switch. Packs size the interface as Auto x `interface_size`: Auto grows with the screen while `follow_screen` is true and is 1 when it is false.
- `/setup/status` adds `fixes: [{ cause: "no_token" | "token_unused" | "key_waiting" | "logs_waiting_trust" | "import_running", link }]`. A watch account hears only about its own cars: `tokens` counts its cars' tokens only, `keys_waiting` is 0 and there is no `key_waiting` fix (keys with no car and tokens for a new car are an admin's to read).
- `/cars/{car}/trip` also lists the `drives` and `charges` it counted.
- In `/charging-stats`: `heatmap.start` and `heatmap.end` are 7 rows (Monday first) of 24 hours in the car's local time. A run is two or more charges, each starting within a day of the one before. `share_above_80_pct` is the share of charges that ended above 80 %; `share_below_20_pct` of those that started below 20 %.
- Drive detail (`/cars/{car}/drives/{drive}`) takes `speed_band_kph=` (the width of `speed_bands`, 1 to 100, default 10; 16.09344 gives 10 mph bands) and answers `speed_band_kph` with it. It adds `start_ideal_range_km` and `end_ideal_range_km` (the first and last ideal range of the drive; `start_range_km` and `end_range_km` are rated), `prev_charge` and `next_charge` (the ids of the charges that started just before and just after the drive's start; `next_charge` is null while the drive goes on) and `est_wh_per_km` with `est_basis: "wh_per_km_30d"` (the consumption of the 30 days of drives before it, which Sentry Mate's own range estimate divides `energy_remaining_kwh` by).
- The track answers (GPX and GeoJSON) carry `Content-Disposition: attachment; filename="<car>-drive-<YYYY-MM-DD-HHMM>.<gpx|geojson>"`, the start in the car's zone and the car's name with anything but letters, digits, `.`, `_` and `-` turned into `-`.
- `/series`: `setpoint_left_c` and `setpoint_right_c` can be `"LO"` (full cooling) or `"HI"` (full heat). A bucket that holds only such words gives the last word in every agg; otherwise the aggs use the numbers only.
- **Upload tokens for a new car** (`/upload-tokens`): a fresh install has no car, and a car's own tokens need its page, so an admin makes a token here. The first log sent with it makes a new car (named after its model and VIN prefix until someone names it) and ties the token and the logger's key to that car. A first upload never takes a car key that is in use already (another token is tied to it, or logs of it are here): that answers `403 wrong_car`, and so does a status request about such a key, so a token handed out for one car can't upload into, ask about or block another car's logs. A token made on a car's page (`/cars/{car}/upload-tokens`) may also take that car's own keys: that is how a car's lost or revoked token is replaced; from then on the token is listed under `/cars/{car}/upload-tokens` and no longer here. `/setup/status` counts these tokens too (for an admin).
- `/can-keys` takes `car=` (the keys tied to that car; an unknown or hidden car gives `404 no_such_car`), so a page lists one car's keys without reading every key.
- **Efficiency basis on `/cars/{car}/drives`:** `efficiency=hill_corrected` changes both `wh_per_km` and `efficiency_pct` of each row (the rated consumption against the consumption with the climb taken off; null when that is not above 0), and `summary.wh_per_km`. `summary.efficiency` names the basis used. `energy_kwh` stays the energy measured at the pack.
- **`/cars/{car}/drive-stats`:** `per_day` holds every local day of the car from the later of the period start and the car's first data to the period end (or now), days without driving as 0; `days` is their number, and `projection.basis_days` is the same count. `max_speed.last_30d` and `last_7d` cover the 30 and 7 days to the period end (or now) whatever the period, and ignore `exclude_places`; `max_speed.period` follows both. `top_destinations` leaves out drives still going and drives whose data stopped (they have no destination yet). Only the period and `exclude_places` filter the stats; the list filters of `/drives` do not.
- **`/places?car=`:** `counts` and `last_visit_ms` are that car's (an unknown or hidden car gives `404 no_such_car`); every place the account sees is still listed. `sort=drives` orders by drives (most first), then visits.
- **`/cars` items carry `now.ideal_range_km`** beside `now.range_km` (rated), so a car list can show the range the person chose (`range: "ideal"` in `/me/preferences`) without one `/now` read per car.
- **`POST /places/{place}/reprice`** also answers `example_rows` (up to 8, the same shape as the preview's: `{ kind: "charge", id, car, start_ms, change: "repriced" }`), so a page can link each example to its charge; `examples` stays as before.
- **`/fleet/versions` items carry `time_zone`** (the car's own zone), so the list of every car can show each row's dates where that car is, not in the zone of the car being viewed.
- **Audit rows carry `car`:** the id of the car the changed item belongs to (a `car:<id>` target's own car, and the car of a `drive:`, `charge:`, `trip:` or `update:` target), else null. A drive, charge or update id is only unique within its car, so a page needs it to link the entry to the item.
- **`/network` carries `certificate: { names, sha256, own }` and `upload_address`:** the names in the certificate the server runs with now (`localhost` first in one the server made), its SHA-256 (colon-separated upper-case hex pairs, as the CAN Bridge app wants it) and the address the CAN Bridge sends logs to (`https://<first name>:10100/api/can/logs`, the first name other than `localhost`, an IPv6 address in brackets). Saving `host_names` in `/settings` does not change them; they change when a new certificate is made (`POST /network/certificate`). A page compares an address with these, not with `host_names`. `own` is true when the server runs with its owner's own certificate (put in `data/tls`), which `POST /network/certificate` never replaces: a page offers no "Make a new certificate" then, and says how to change the files instead. Only such a certificate ever expires soon (`certificate_expiring`): one the server makes is valid until the year 4096.
- **A new certificate** (`POST /network/certificate`, admin): the server makes a new self-signed certificate with the same generator as on its first start, for `localhost` and the saved `host_names` (with none saved: the running certificate's names that are host names or addresses, so a name with a space or a wildcard given in `SENTRY_MATE_NAMES` never goes in), seals its key like the first one, and writes the new pair beside the old one (each file whole and synced) before it renames them into place, so a power cut never leaves the server without a certificate (the next start finishes or drops a swap cut short). Both ports (web and uploads) serve it from the next connection on; connections open already finish on the old one. It answers `{ names, sha256, upload_address }` and is recorded in the audit log (`certificate-made`, target `server:certificate`). It takes the admin's own `password` again and, when the account has two-step sign-in on, `two_step` (the code), as a move code does (missing: `400 bad_input`; wrong: `403 wrong_password` / `403 wrong_two_step`). Refused with `409`, before the password is checked (so a two-step code is not used up on it): `setup_busy` while a move or a restore into this server runs, `move_under_way` while a move code waits here or a new server copies from here (it pins this certificate's SHA-256), `moved` after the data moved away, and `own_certificate` when the server runs with its owner's own certificate (a `cert.pem` and `key.pem` put in `data/tls`, told apart by not being self-signed by the server), which it never replaces (`/network` says so in `certificate.own`). The SHA-256 changes: each CAN Bridge refuses uploads until its "certificate SHA-256" is set to the new one, and browsers ask again to accept the certificate.
- **`/settings` carries `outbound: { proxy }`:** one proxy (`http://`, `https://` or `socks5://` host with an optional port, no name or password in it; null for none) that the server uses for everything it fetches itself: online address lookups and map tiles it downloads. Viewers' browsers loading online tiles do not go through it.
- **`/me/preferences` `language` defaults to `"auto"`** for an account that never picked one, so dates and numbers follow the browser's languages; a page says "your choice" only for any other value.
